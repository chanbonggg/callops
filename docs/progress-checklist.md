## 일반 개발환경 작업 순서

합성 데이터·로컬 HTTPS·임시 PostgreSQL·가짜 워커로 진행한다. 이 순서는 GPU가 없는 현재 환경의 작업 제안이며 웹 MVP의 단계별 통과 기준은 그대로 적용한다.

### 1. 통화 목록·상세·전사 검색 UI 반영

- [ ] Figma 01·02·03·19와 현재 화면을 나란히 확인한다. 상대·시각 입력과 분류 폼은 현재 목록에 있고 Figma 19에는 분류 전 상세 시안이 있으므로 조작 위치를 정한다. 공통 메뉴의 ‘전사 검색’은 현재 `/questions`로 연결된다. 키워드 검색 `/search`와 통화 질문 `/questions`의 이름·진입점·활성 표시를 함께 확인한다.
- [ ] 기존 일정·질문·할 일에서 사용 중인 공통 레이아웃·스타일을 재사용한다. 목록은 상태와 거래처·통화 시각을 읽기 쉽게 표시하고, 상세는 원음·요약·근거·일정 후보의 순서를 검토한다. 전사 검색에는 기존 거래처·기간 입력, 결과와 근거 링크를 유지한다.
- [ ] 요약 대기, 전사 없음, 원음 사용 불가, 검색 결과 없음에서 필요한 안내와 다음 동작을 표시한다. 전사 버전·구간 링크와 분류·검색의 기존 인증/CSRF 계약을 회귀 검사한다.
- 완료 기준은 세 화면에 공통 탐색과 모바일 배치가 적용되고, 현재 가능한 조작과 Figma에서 달라진 결정이 이 표에 기록되는 것이다.

### 2. 로컬 브라우저에서 조작 흐름 확인

- [ ] Chrome PC 1090px, 모바일 뷰포트 390px로 로그인 → 통화 목록 → 업무 통화 상세 → 요약 근거 열기 → 인용 원음 재생을 확인한다. 목록 필터 및 전사 검색의 일치·빈 결과도 시험한다. 좁은 320px에서 긴 제목과 주요 조작이 잘리거나 하단 메뉴에 가리지 않는지 확인한다.
- [ ] 같은 브라우저에서 직접 일정 등록 → 수정 → 삭제 확인을 실행한다. 시작/종료 오류를 보낸 뒤 입력이 유지되는지, 두 탭에서 먼저 저장한 결과를 이전 폼이 덮어쓰지 않는지 확인한다. 일정 후보는 근거 확인과 수정·승인/거절을 시험하고 시안 차이를 기록한다.
- [ ] 공통 레이아웃을 수정했다면 할 일 목록과 질문 화면에서도 이동·입력·근거 링크가 작동하는지 확인한다. 검증한 뷰포트, 입력, 결과와 재현 가능한 실패를 기록한다.
- 완료 기준은 **화면 배치**와 **조작 결과**를 각각 확인하고 기록하는 것이다. 갤럭시 실기기와 실제 Whisper 구간 대조는 기기 준비 후 수행한다.

### 3. 통화에서 나온 할 일 승인

- [ ] 가짜 분석 결과에 할 일 후보를 추가하고, 제목·선택 기한·고정 전사 근거를 받는 요청 예시와 오류 조건을 문서화한다. 기한 미정은 null로 유지하고 다른 전사나 존재하지 않는 근거를 거절한다.
- [ ] 로그인한 사용자가 근거를 열고 제목·기한을 보정해 승인 또는 거절하도록 한다. 승인은 revision 검사와 함께 한 트랜잭션에서 기존 `tasks`에 OPEN 항목을 한 건 생성하고 승인 당시 값을 보존한다. 같은 후보 재승인은 기존 항목을 반환한다.
- [ ] `/tasks`에서 기한 미정·초과 표시, 미완료/완료/취소, 수정·완료·취소·재열기를 확인한다. 두 탭 충돌과 재분석이 기존 할 일의 사용자 편집·완료에 미치는 경계를 시험한다.
- [ ] 후보가 만료되면 신규 승인을 차단하고 이미 승인한 할 일의 근거 만료를 표시한다. 사적 전환·통화 전체 삭제에서는 해당 통화에서 나온 할 일을 정리한다. 승인·편집의 동시성, 삭제·만료 뒤 늦은 요청을 임시 PostgreSQL로 검증한다.
- 완료 기준은 합성 통화에서 근거를 확인해 승인한 할 일을 `/tasks`에서 완료·재열기할 수 있고, 중복·만료·삭제 동작을 검증한 것이다. [제품 계약](01-project.md#내부-할-일의-승인-이후-흐름)

### 4. 업무 데이터 만료와 삭제 검증

- [ ] 현행 조회 기한과 실제 사본 청소를 점검하고 `AUDIO_ONLY`, `DERIVED_ONLY`, `RECORDING_ALL` 각각의 대상과 남길 정보를 확인한다. 음성만 만료된 뒤 유효한 전사·후보를 읽을 수 있는지, 파생물 만료 후 인용·검색·신규 승인이 차단되는지 검증한다.
- [ ] 주입한 시계로 만료와 결과 업로드의 경합을 만들고 늦은 결과·청소 실패·중복 수신·워커 미확인 상태를 시험한다. `maintain` 주기 실행과 실제 워커·검색 인덱스 청소는 해당 연동을 검증할 때 확인한다.
- [ ] 현재 코드의 기간과 운영 정책 승인 전 기본안을 구분한다. 30일·90일 기본안과 승인된 할 일의 별도 보관·연장 정책은 [제품 계약의 기간 표](01-project.md#10-미정값과-보관-기본안)를 따른다.
- 완료 기준은 합성 데이터에서 범위별 조회·신규 처리·청소 결과가 명세와 일치하고, 청소에 실패한 사본이 삭제 완료로 표시되지 않는 것이다. [삭제 범위와 검토 가능 범위](01-project.md#삭제-범위와-검토-가능-범위)

작업이 끝나면 이 문서의 해당 화면과 체크 항목에 변경 사항, 시험 환경과 결과, 여전히 남은 검증을 갱신한다. Markdown 기본 검사와 서버 동작을 변경한 경우의 임시 PostgreSQL 검사 절차는 [하네스](harness.md#실행)를 따른다.

## 로컬 구현 이력

- [x] **기획과 범위** — 거래처 영업·일정 생성을 기준 업무로 잡았다. 녹음 수집·업무 지정·전사·요약·근거 답변을 필수로, 일정·할 일 관리와 시험 캘린더 한 개의 양방향 동기화를 선택 구현 목표로 정했다. 통화 당시 합의의 근거를 찾고 바뀐 현재 일정과 구분하는 과제를 차별점으로 잡았다. 웹을 우선하며 Flutter 앱과 이메일 연동은 후속 범위다. [프로젝트 계획](01-project.md) · [웹 MVP 검증 기준](web-mvp/README.md)
- [x] **개발 기반과 웹 전환** — Python 3.12, PostgreSQL, Starlette·Uvicorn으로 개발한다. 기존 Flask 서버 기능을 한 앱의 `auth`, `calls`, `processing`, `search`, `schedule` 모듈로 옮겼다. 마이그레이션, 앱/마이그레이션 DB 역할 분리, 설정 누락 검사, 임시 PostgreSQL 하네스와 모듈별 작업 지침을 마련했다. [P1 기반](p1-foundation.md) · [하네스](harness.md)
- [x] **로그인과 최소 웹 화면** — 단일 사용자 로그인·로그아웃, DB 세션, CSRF, 로그인 시도 제한, 사용자와 워커 권한 분리, 원음 조회 권한을 구현했다. 로그인·통화 목록/상세·검색·일정 검토/목록 화면이 있으며 로컬 HTTPS 검색 흐름을 확인했다. [서버 실행과 인증](p2-p3-server.md#로그인-화면)

## 실제 장비·외부 연결이 필요한 작업

항목별로 필요한 환경이 준비될 때 진행한다. GPU를 사용할 수 있게 되면 데스크톱 환경을 확인하고 저장소의 Whisper 모듈부터 시험한다. 갤럭시·운영 서버·OAuth·n8n의 연결 범위는 각 작업에서 확인한다.

- [ ] **녹음 형식 확대의 실기기 검증** — 서버에 PCM WAV·AAC/ALAC M4A·MP3·AMR-NB/WB 수신을 구현했다. 실제 갤럭시 테스트 녹음의 형식·코덱과 전송 완료 신호를 확인하고, 실제 Whisper 전사와 브라우저 인용 구간 재생을 확인한 조합을 지원 완료로 기록한다. [1단계 형식 검증표](web-mvp/README.md#week-01-형식별-검증표)
- [ ] **실제 AI 결과의 서버 경로** — 가짜 워커의 요약·근거를 기존 분석 결과에 저장하고 통화 상세에 표시하는 경로를 구현했다. 실제 모델 결과의 전사·요약·일정·할 일 스키마 연결과 출력 수락은 데스크톱 D5와 함께 확인한다. [합성 요약 계약](p2-p3-server.md#합성-요약-결과-스키마와-조회) · [3주차](web-mvp/README.md#week-03)
