# 1. 이 프로젝트 — CallOps 개발·배포·연동·운영

작성일 · 2026-09-19 / 갱신 · 2026-11-24

이 문서는 CallOps 기능의 개발뿐 아니라 앱·DB 배포, 녹음 동기화, n8n 워크플로우 작성·연결, Calendar OAuth, 테스트·보관·복구까지 담당한다. 물리적으로 홈서버에서 실행되더라도 CallOps 전용 작업은 이 프로젝트의 책임이다. [서버 문서](03-server.md)는 프로젝트와 독립적인 공용 n8n 자체의 설치·운영만 담당한다. GPU 실행 환경과 장비 운영은 [데스크톱 문서](02-desktop.md)를 따른다.

이 문서에서 “서버 API”, “서버 DB”라고 부르는 것은 홈서버에 배포할 CallOps 애플리케이션과 DB를 의미한다. 이를 공용 n8n 인프라 업무로 분류하지 않는다.

## 1. 문서의 적용 범위와 현재 상태

- 사용자는 기능별 명세를 검토·승인한 다음 해당 기능을 구현하도록 요청했다. 문서 작성은 구현 승인으로 간주하지 않는다.
- 로컬 Git 저장소에는 GitHub `origin` 원격이 연결되어 있다. 공개 범위와 push 상태는 이번 문서 점검에서 확인하지 않았다. GitHub Actions 등 CI는 구성되어 있지 않다.
- 개발일지와 Notion 기록은 별도 요청이 있을 때 작성한다.
- 이 문서는 제품 계약의 기준이다. 승인 범위와 과거 구현 기록은 11절, 현재 상태와 다음 작업은 [전체 진행 체크리스트](progress-checklist.md), 웹 MVP 검증 기준은 [검증 계획](web-mvp/README.md)을 따른다. 구현을 시작할 때는 [P1 실행 안내](p1-foundation.md)와 [서버 실행·API 계약](p2-p3-server.md)을 참고한다.
- 기존 설명의 “암호화 격리”는 “접근 제한 격리”로 정정한다. 사용자가 디스크 암호화와 별도 백업을 MVP에서 보류했다.
- 후보의 승인 상태와 외부 등록 상태를 별도 필드로 나눈다. 등록 실패가 승인을 취소하는 것은 아니다.
- Syncthing 파일 삭제와 tombstone 만료만으로 영구적인 재수집 방지를 보장하지 않는다. 실제 휴대전화 연결 전에 수신 제외·청소 시험을 통과해야 한다.
- 9개 기능 번호는 최초 요청을 유지한다. GPU 통신·heartbeat는 F02/F03에 포함한다.
- 역할 분류를 실행 장소에서 관리 책임으로 정정했다. 기존 서버 문서의 CallOps 작업 S2~S8은 이 문서의 C1~C7로 이동했다. 서버 문서의 S0~S4는 공용 n8n 준비·운영 단계다.
- 2026-09-19 검토 보완: 전사 재조회 계약, 연산 제한시간, 삭제 범위, P2 인증, 장문 정정 병합, 내부 할 일 수명주기, 모델 합격 기준을 반영했다. 이번 승인은 문서 보완 범위이며 코드 구현·설치 승인은 별도다.
- 재검토 보완: 준비/연산/전송 상한 분리, 재분석·재승인의 기존 출력 연결, 외부 작업 취소/늦은 응답, 파일·DB 장애 복구, 삭제 전용 통신, 날짜 검증과 실제 수신 중단 조건을 추가했다. 실제 장비·외부 서비스의 정상 동작은 각 단계 시험으로 별도 검증해야 한다.

## 2. 해결할 업무와 최종 출력

업무 통화에서 나온 약속과 후속 할 일을 빠뜨리지 않되, 사적인 통화를 AI가 처리하거나 불확실한 계약 정보를 확정하지 않게 한다.

```text
갤럭시 원본 → 서버 수신·격리 → 사람의 업무/사적 분류
  업무 → PostgreSQL 작업 → 승인 파일만 GPU 전달 → Whisper → Ollama
       → 서버 결과 검증·보관 → 결과 검토 화면 → 항목별 승인
          일정 → 공용 n8n → Google의 CallOps 캘린더 → 삼성 캘린더 표시
          할 일 → 서버 내부 목록 (외부 서비스 미정)
          계약 언급 → 확인 기록 (계약 효력·확정 의미 없음)
  사적/만료 → 서버 복사본 삭제, 갤럭시 원본 유지
```

| 출력 | 기준 저장소 | 사용자 확인 방식 | 외부 전송 |
|---|---|---|---|
| 원본 음성 | 서버 파일 저장소, 휴대전화 원본 별도 | 로그인된 검토 화면의 필요한 구간 | Google·알림 서비스로 전송 금지 |
| 전사본 | 서버 전용 파일 저장소 | 시간 구간별 텍스트·재생 | 금지 |
| 요약·근거·후보 | CallOps PostgreSQL 제한 테이블 | 통화별 결과 화면 | 전체 내용 전송 금지 |
| 확정 전 일정 | CallOps DB | 확인 필요/승인 대기 목록 | 승인 전 없음 |
| 승인된 일정 | CallOps DB 승인 스냅샷 + Google Calendar | 삼성 캘린더 또는 Google Calendar | 승인한 최소 필드만 |
| 할 일 | CallOps DB | 제목·기한·처리 상태 목록 | 초기에는 없음 |
| 계약 언급 | CallOps DB | 근거와 확인 상태 | 초기에는 없음 |
| 운영 알림 | 전송 상태는 DB | 작업 ID·상태·후보 개수 | 선택한 알림 채널 |

구조화 결과의 기준 저장소는 DB로 정한다. 워커가 보낸 결과 JSON은 전송 형식이며, 별도 요약 파일을 무조건 중복 보관하지 않는다. 전사 파일 위치·해시·스키마 버전은 DB에 기록한다. 수집 메타데이터·n8n 실행 DB에는 전사 원문을 저장하지 않는다. 추출 결과 전용 테이블에는 민감한 근거 문장이 들어갈 수 있으므로 접근을 제한한다.

## 3. 소유권과 저장소 구성

| 대상 | 책임 |
|---|---|
| CallOps 프로젝트 | API·수집·청소·검토 UI·DB·작업 큐·워커 코드·출력 스키마·테스트·CallOps 배포와 데이터 운영·알림 워크플로우와 OAuth/Calendar 연결 |
| 서버의 공용 n8n | n8n 자체·시스템 DB·관리 인증·n8n용 VPN/HTTPS 경로·키 보관·실행 이력 기본 정책·업데이트·복구 |
| 데스크톱 운영 | GPU 드라이버·선택 실행 환경·로컬 모델·CallOps 워커 설치/자동 시작·장비 임시 파일 |

다음 구조는 해당 단계 승인 후 필요한 파일만 생성할 계획이다. 지금 모두 만들지는 않는다.

```text
callops/
  README.md
  .gitignore
  docs/                         # 제품 계약·환경 계획·실행 안내·검증 기준
  src/callops/
    web.py                      # Starlette 앱 조립과 공통 HTTP 설정
    auth/                       # 사용자 세션·CSRF·워커 인증
    calls/                      # 수집·분류·정리·통화 및 전사 상세
    processing/                 # 작업 큐·워커 API·결과 스키마
    search/                     # 승인된 전사의 검색·근거 검색·통화 질문
    schedule/                   # 일정 후보 검토·직접 입력 일정·모의 Calendar와 연결 일정 동기화

    config.py, db.py            # 서버 설정·DB 마이그레이션
  ai-worker/                    # 데스크톱 모델 실행 코드
  migrations/                   # CallOps DB 변경
  n8n/workflows/                # CallOps 흐름만, 자격증명·실데이터 제외
```

공용 n8n Compose는 서버 공용 인프라 디렉터리에서 관리한다. CallOps를 배포·제거할 때 n8n과 다른 자동화가 함께 중지되지 않아야 한다.

서버는 Python 3.12·Starlette·Uvicorn·PostgreSQL로 구성하는 모듈러 모놀리스다. 인증·통화·처리·전사 검색·일정·할 일 모듈을 한 웹 앱에서 실행하고 하나의 PostgreSQL DB를 사용한다. 통화 모듈은 분류와 녹음 수명주기를 담당하며, 처리 모듈은 통화의 승인 상태와 저장 경로를 사용해 작업을 처리한다. 전사 검색은 업무 승인된 통화의 유효한 전사에서 키워드를 찾고 출처 링크를 제공한다. 전사 검색 모듈은 키워드 검색과 근거 검색 함수, 어휘 규칙 기반 통화 질문 화면도 제공한다. 일정 모듈은 합성 후보와 승인 기록, 직접 입력 일정을 관리하고 승인된 일정을 모의 Calendar로 전송하며 연결 일정의 양방향 동기화를 모의 제공자로 처리한다. 할 일은 직접 입력과 통화 후보 승인을 `tasks.py`·`task_candidates.py`가 맡는다. 브라우저 화면은 Jinja로 서버에서 렌더링한다. 서버 워커 API는 가짜 워커로 검증하며 데스크톱 AI는 단독 실행 단계다. DB 의존성은 psycopg 3.3.3이며 로컬 검증은 PostgreSQL 18.0을 사용한다.

## 4. 책임별 개발 순서와 의존 관계

P는 프로젝트 코드 개발, C는 프로젝트 배포·연동·운영, D는 데스크톱 준비, S는 독립적인 공용 n8n 준비다. C의 명령이 Ubuntu에서 실행돼도 프로젝트 작업이다.

| 순서 | 이 프로젝트: 개발과 배포·연동 | 데스크톱 | 공용 n8n과의 관계 | 완료 증거 |
|---|---|---|---|---|
| 0 | P0 명세, C0 CallOps 배포 대상 확인 | D0 사양 확인 | S0~S4 공용 n8n 준비를 독립 진행 가능 | 책임·환경·미정값 |
| 1 | P1 설정/스키마, C1 CallOps 앱·DB·저장소 | 아직 불필요 | 공용 n8n 미완료여도 가능 | 테스트 DB·접근 경계 |
| 2 | P2 수집/UI, C2 가짜 수집·분류·삭제 | 가짜 워커 사용 | 아직 불필요 | 선택 전 AI 0회 |
| 3 | P3 큐/임대, C3 CallOps API·VPN·GPU 경로 | D1~D2 | 아직 불필요 | 중복·늦은 결과 거부 |
| 4 | P4 전사·결과 수락·권한 | D3, D5 | 아직 불필요 | 타임스탬프·ACK |
| 5 | P5 요약/추출·후보 저장 | D4 | 아직 불필요 | 근거·불확실성 |
| 6 | P6 알림 코드/워크플로우, C4 실제 채널 연결·시험 | 결과 재전송 검증 | 준비된 공용 n8n을 프로젝트가 이용 | 알림만 재시도 |
| 7 | P7 Calendar 모의 연동, C5 OAuth·실제 시험·삼성 표시 | 관여 없음 | 프로젝트용 credential/워크플로우 실행 | 미승인 0건·중복 0건 |
| 8 | P8 보관/운영, C6 CallOps 모니터링·복구, C7 갤럭시 마지막 연결 | D6 | 공용 n8n 자체 운영은 독립 유지 | 삭제·원본 유지·장애 복구 |

P2에서는 UI로 직접 분류하므로 실제 알림 채널이나 공용 n8n이 없어도 개발할 수 있다. D0 미확인으로 프로젝트 백엔드 개발을 멈추지 않는다. CallOps가 공용 n8n을 사용하는 시점은 C4부터다.

## 5. 공통 데이터 모델과 상태 계약

| 데이터 | 최소 필드/제약 |
|---|---|
| recordings | id, sha256 UNIQUE, size, counterparty, 원본 시간과 출처/신뢰 여부, 수신 시각, 길이, 저장 키, 분류 상태, 만료 시각, output_decision_version |
| receipts | 동일 콘텐츠의 수신별 ID·제한된 원본 경로·복사본 위치·청소 상태 |
| classification_events | 이전/이후 상태, 사용자, 시각, 요청 ID, 사유 |
| jobs/attempts | recording_id, stage, pipeline_version, state, lease_token, 임대 만료, input_artifact_id, input_artifact_version, input_sha256, preparation_deadline, execution_deadline, upload_deadline, result_request_id/hash/size, 시도 횟수, next_attempt_at, 오류 코드 |
| artifacts | id, 전사 저장 키·해시·불변 버전, 추출 결과 JSONB, recording/job/attempt 연결, expires_at |
| candidates/revisions | 유형, 초안, 근거 구간, 불확실 사유, revision, approval_status, logical_item_id, 재분석 연결/신규 결정 이력 |
| approvals | 사용자, 대상 revision, 승인한 값의 스냅샷·해시, 시각 |
| schedules | 안정적인 일정 ID, 직접 입력 또는 통화 출처, 현재 제목·시작·종료·revision, 채택한 승인 버전, 삭제 시각 |
| tasks | 직접 입력은 id, request_id UNIQUE, 제목, 기한(없으면 null), status, revision, 완료/삭제 시각을 사용한다. 통화 후보 승인 단계에서 recording_id, logical_item_id, source_candidate_id, 승인 revision, 취소 시각과 보관기한을 연결한다. 근거 원문 중복 저장 금지 |
| deliveries | 알림/외부 작업 ID, logical_item_id, 상태, 종료 사유, retry_allowed, 재시도 시각, 외부 ID, 요청 해시 |
| deletion_records | 콘텐츠 해시·scope(AUDIO_ONLY / DERIVED_ONLY / RECORDING_ALL)·복사본·청소 확인·수신 제외·만료 조건 |
| workers | worker_id, heartbeat, 가용 모델, 현재 작업, 최소 운영 지표 |

합성 일정 검토는 `schedule_candidates`와 `schedule_approvals`를 사용한다. 분석 작업과 전사 근거 구간에 후보를 고정하고, 편집 때 revision을 올린다. 승인 시 해당 revision의 제목·시작·종료와 근거 ID의 스냅샷·해시를 저장한다. 승인 스냅샷과 후보는 통화 전체 삭제 또는 근거 기한 도달 후 정리한다. [합성 일정 후보 계약](p2-p3-server.md#합성-일정-후보-검토)

모의 Calendar에서는 `calendar_deliveries`에 승인 revision과 전송 상태를, `mock_calendar_events`에 이벤트 ID와 승인 payload 해시를 저장한다. 기존 일정은 `logical_item_id`로 조회해 중복 생성을 방지한다. [모의 전송 계약](p2-p3-server.md#승인된-일정과-모의-calendar)

직접 입력과 통화 승인 일정의 현재 값은 `schedules`에 저장한다. 여러 후보가 같은 일정에 연결될 수 있고 현재 일정이 채택한 승인 버전은 별도로 가리킨다. 모의 이벤트의 ID는 이 일정 ID에 연결한다. 근거 만료는 과거 승인 정보의 조회와 신규 전송을 막으며, 사적 전환은 내부 일정 내용과 통화 연결까지 정리한다. [일정 수명주기](p2-p3-server.md#승인된-일정과-모의-calendar)

연결 일정의 양방향 동기화는 `012`에서 원격 버전·연결 당시 합의 스냅샷·삭제 상태를 저장한다. 통화에서 나온 할 일 후보는 `010`의 `task_candidates`에 분석 작업·입력 전사와 함께 저장하고, 원음·전사·분석 파일의 부분 만료 상태는 `011`의 삭제 상태 열에 기록한다. [동기화 계약](p2-p3-server.md#연결-일정-양방향-동기화-api) · [할 일 후보 계약](p2-p3-server.md#통화에서-나온-할-일-후보-검토)

큐의 복합 외래 키는 작업의 입력 전사·실행 시도·결과·일정 후보가 같은 통화 범위에 속하도록 검사한다. 활성 실행 시도는 해당 작업에 속해야 한다. [큐 무결성 마이그레이션](../migrations/008_processing_integrity.sql)

SHA-256은 파일 바이트 동일성을 판별한다. 다른 형식으로 재인코딩한 같은 통화는 다른 해시가 되므로 초기 중복 방지 범위에 포함하지 않는다. 생성 시각과 파일명은 고유키가 아니다. DB 시각은 UTC, 화면·Calendar는 명시적 시간대를 사용한다. 파일 수정 시각을 실제 통화 시작 시각으로 단정하지 않는다.

- 분류: `PENDING → DEFERRED / BUSINESS_APPROVED / PRIVATE_EXCLUDED / EXPIRED`.
- 작업: `WAITING_FOR_FILE / WAITING_FOR_WORKER → PREPARING → RUNNING → UPLOADING → SUCCEEDED`, 예외는 `RETRY_WAIT / FAILED_MANUAL / CANCEL_REQUESTED / CANCELLED`.
- 후보 승인: `NEEDS_CONFIRMATION(확인 필요) → AWAITING_APPROVAL(승인 대기) → APPROVED(승인됨) / REJECTED(거절됨)`.
- 내부 할 일: 승인 시 `OPEN(미완료)` 생성, 사용자 조작으로 `DONE(완료) / CANCELLED(취소)`. 승인 상태와 수행 상태는 별개다.
- 외부 반영: `NOT_REQUESTED → PENDING → IN_FLIGHT → SUCCEEDED`, 예외는 `RETRY_WAIT / UNKNOWN / AUTH_REQUIRED / FAILED_MANUAL / CANCELLED`. CANCELLED는 종료 상태이며 사유는 USER_CANCELLED / REVISION_SUPERSEDED / SOURCE_EXPIRED / SOURCE_DELETED로 구분한다.
- 파일 삭제: `REQUESTED → RUNNING → COMPLETE`, 실패는 `RETRY_WAIT`. GPU 오프라인이면 잔여 복사본 확인 전 COMPLETE 금지.

위 화살표는 대표 흐름이다. DEFERRED는 최초 만료를 유지한 채 BUSINESS_APPROVED/PRIVATE_EXCLUDED/EXPIRED로 결정할 수 있다. BUSINESS_APPROVED의 사적 전환은 RECORDING_ALL 삭제와 처리 취소를 함께 요청한다. 이미 만료/삭제된 콘텐츠는 상태만 되돌리지 않고 명시적 재수집·분류 절차를 따른다. 명확한 새 후보는 AWAITING_APPROVAL로 바로 시작하며, 수정한 승인 후보는 재검증 후 승인 대기로 되돌린다. 기존 외부 출력은 7절의 연결 규칙으로 보존한다.

후보 수정은 revision을 증가시키고 이전 승인으로 새 내용을 보낼 수 없게 한다. AI가 반환한 상태나 실행 지시는 신뢰하지 않으며, 서버가 검증 후 상태를 부여한다. 계약 후보의 `APPROVED`는 사용자가 “통화 언급을 확인했다”는 뜻일 뿐 법적 계약 승인이나 발송 권한이 아니다. 화면에서는 “언급 확인됨”으로 표시한다.

## 6. 기능별 상세 기준 — 요청한 12개 항목

공통 상태 변경은 현재 상태와 revision을 확인해 적용한다. 아래의 보관 만료는 삭제 scope에 따라 관련 작업만 차단하며, 통화 전체 취소는 모든 신규 처리·미전송 외부 작업을 차단한다.

아래 F01~F09의 전체 범위는 검토 초안이다. P1~P3에 해당하는 구현 착수 승인은 11절에 기록하며 같은 범위를 다시 승인 요청하지 않는다. 후속 기능은 해당 API·마이그레이션·경계값과 승인 범위를 확인한다. 기술적으로 필요한 값과 아직 미정인 선택은 10절에서 구분한다.

### F01. 갤럭시 녹음 수집·동기화

1. **문제:** 녹음을 빠짐없이 받고 사적 통화를 전사하지 않는다.
2. **시나리오/완료:** 파일 수신 → 분류 → 업무만 대기열. 사적 선택 시 모든 관리 복사본 청소, 휴대전화 원본 유지.
3. **입력:** 선택한 갤럭시 폴더의 m4a/amr/wav 등 확인된 형식. 먼저 서버의 테스트 폴더에서 시작한다.
4. **흐름:** 수신 완료 확인 → 파일 제한·해시 검사 → 독립 격리 복사 → DB 등록 → UI/알림 → 분류 결정.
5. **서비스:** 동기화 도구는 파일 이동, CallOps는 검증·격리, PostgreSQL은 상태, n8n은 알림 담당.
6. **데이터/상태:** recordings, receipts, classification_events. 파일 상태와 분류 상태를 분리한다.
7. **보안:** 파일 확장자 외 실제 형식 검사, 크기·길이 상한, 경로 탈출·심볼릭 링크 차단. 워커·n8n은 격리 폴더 읽기 금지.
8. **실패/재시도:** 안정화 검사만으로 전송 완료를 확정하지 않는다. 도구 완료 신호, 복사 전후 크기·시각과 해시, 판독 성공을 결합한다. DB 장애 중 이미 승인된 만료·삭제를 막지 않도록 로컬 청소 목록을 관리하고, 목록도 신뢰할 수 없으면 신규 수신을 중지한다.
9. **사람 승인:** 업무 버튼은 이 콘텐츠 한 건의 AI 처리만 허용. 이후 일정 승인은 별도이다. 업무 승인 전에 상대·한국 시간 기준 실제 통화 시각을 입력·확인한다. 빈 시각은 미확인으로 남기고 수신 시각으로 대체하지 않는다. 승인 후 정보는 잠그며, 입력 변경과 재분석 연결은 후속 구현한다.
10. **테스트:** 쓰다 멈춘 파일, 이름 바꾼 중복, 빈 파일, 형식 위장, 사적 선택, 미응답, 서버 재시작, 서버 삭제 후 휴대전화 유지.
11. **운영:** 미분류 수·최장 대기·수신/삭제 실패·용량을 확인. 미분류 음성은 향후 백업 도입 시에도 기본 제외.
12. **제외:** 연락처 자동 승인, AI로 사적 여부 판별, 기존 녹음 전체 자동 가져오기. 자동 동기화는 C7에서 마지막 연결.

### F02. 홈서버 작업 대기열 및 PostgreSQL 상태 관리

1. **문제:** 워커가 꺼지거나 서버가 재시작해도 작업·결정이 유실되거나 중복되지 않게 한다.
2. **시나리오/완료:** 업무 선택과 작업 등록을 한 DB 트랜잭션으로 기록하고, 살아 있는 워커 하나가 처리한다.
3. **입력:** 승인된 recording_id, 콘텐츠 해시, 단계, 파이프라인 버전. 서버 CallOps DB에 저장한다.
4. **흐름:** 승인 → 파일 준비 → claim → heartbeat → 결과 검증·저장 → 완료 → 다음 단계/알림 등록.
5. **서비스:** PostgreSQL을 유일한 상태 기준으로, CallOps API를 전이 책임자로 사용. n8n은 API만 호출.
6. **데이터/상태:** jobs/attempts/workers. 작업 고유키는 녹음·단계·파이프라인 버전. 시도별 lease_token을 발급한다.
7. **보안:** 워커 토큰은 할당 작업·해당 입력 전사 조회·결과·heartbeat만 허용. DB 직접 접속, 분류 변경, Calendar 권한 금지.
8. **실패/재시도:** claim은 트랜잭션과 행 잠금으로 원자 처리. 임대 만료 후 새 시도 가능하되 구 임대 결과는 거부. 원격 파일 대기/워커 오프라인은 STT 실패 횟수에 포함하지 않는다. heartbeat와 별개인 execution_deadline을 두고 연산 정지는 STAGE_TIMEOUT으로 제한 재시도한다. 구 연산 종료가 확인되지 않은 워커는 새 작업을 받지 않는다.
9. **사람 승인:** 수동 재처리에는 이유와 새 처리 버전 기록. 기존 후보 승인·수정본을 덮어쓰지 않는다.
10. **테스트:** 워커 두 개 동시 claim, 임대 만료 후 늦은 결과, 결과 저장 뒤 응답 유실, 재부팅 후 대기 재개.
11. **운영:** 단계별 대기, 최장 임대, 재시도·수동 복구 건수. DB 유실 시 복구 모드에서 외부 작업을 차단한다.
12. **제외:** Redis/Kafka, 다중 GPU 스케줄러, 고가용성 클러스터. 초기 실제 워커는 1개.

### F03. GPU Whisper 전사 워커

1. **문제:** 홈서버에 GPU가 없어도 타임스탬프가 있는 전사본을 얻는다.
2. **시나리오/완료:** 업무 승인 파일을 워커가 검증·전사하고 서버가 결과 영속화를 확인한다.
3. **입력:** VPN 동기화된 업무 파일, job_id, lease_token, sha256. 데스크톱 저장소는 Git 밖.
4. **흐름:** claim → 해시·승인 유효성 확인 → Whisper → segment JSON → 서버 전사 파일 저장·DB 연결 → ACK.
   서버의 준비 구현은 합성 구간 전사의 저장·조회와 artifact/segment 출처 링크까지다. 실제 Whisper 결과 수락과 GPU 워커 통합은 후속 검증한다. [합성 전사 스키마와 조회](p2-p3-server.md#합성-전사-결과-스키마와-조회)
5. **서비스:** 데스크톱 워커·Whisper/faster-whisper, 서버 API·PostgreSQL. 모델과 실행 환경은 D0 후 확정.
6. **데이터/상태:** 구간 start/end/text, 모델 식별자, 언어, 길이, 처리시간, job/attempt/schema_version. STT 완료는 분석 완료와 구분.
7. **보안:** 승인 파일만 접근, 디코더를 제한된 계정으로 실행, 원문을 stdout·오류에 출력하지 않음.
8. **실패/재시도:** OOM·디코딩 실패는 제한 재시도 후 수동 확인. ACK 전 결과를 제한된 로컬 spool에 유지하여 업로드만 재시도.
9. **사람 승인:** 업무 분류 취소 시 실행 중지·결과 수신 차단·청소. 전사 결과는 정확한 사실로 확정하지 않는다.
10. **테스트:** 한국어, 무음, 잡음, 숫자·고유명사, 긴 통화, 비정상 오디오. 시간 구간 순서와 음성 길이 내 범위 확인.
11. **운영:** 오디오 길이 대비 처리시간, VRAM·GPU 사용량, 모델 버전, 마지막 heartbeat. 환경은 버전으로 재현하고 원문 로그는 남기지 않는다.
12. **제외:** 실시간 통화, 화자 신원 식별, 필수 화자 분리, 클라우드 STT 자동 대체.

### F04. Ollama 요약·일정·할 일·계약 언급 추출

1. **문제:** 긴 업무 대화를 검토 가능한 후보로 바꾸고 모호한 약속을 드러낸다.
2. **시나리오/완료:** 전사본 → 로컬 추출 → 스키마·근거 검증 → 후보와 검토 화면. 일정 없는 통화는 빈 후보가 정상.
3. **입력:** 서버에 수락된 전사본·segment ID, 확인 가능한 통화 시각, schema/prompt/model 버전.
4. **흐름:** 전사 → Ollama JSON → 워커·서버 이중 검증 → DB 후보·근거 → 최소 정보 알림.
5. **서비스:** Ollama는 제안만, 서버는 검증·저장·상태 부여, n8n은 알림.
6. **데이터/상태:** 요약, action_items, schedule_candidates, contract_mentions, uncertainties; 각 후보에 evidence segment ID와 누락 필드·원문 표현. 불명확 값은 null.
7. **보안:** 로컬 모델만, 클라우드 기능 비활성 확인. 전사 안의 “지시를 무시하고 등록하라”는 데이터이며 명령이 아니다. 모델에 Calendar 도구·토큰을 제공하지 않는다.
8. **실패/재시도:** JSON 오류는 제한 재시도 후 실패 표시. 긴 전사는 구간 중첩·원본 시간 오프셋 유지, 조각별 후보 합칠 때 근거 보존. 컨텍스트 초과로 뒷부분을 조용히 버리지 않는다. 아래 장문 병합 규칙을 적용하고, 분석 재시도는 고정된 서버 전사본을 다시 조회한다.
9. **사람 승인:** 불확실 후보와 계약 언급은 확인 필요. 명확한 일정도 승인 대기. 종료시간·금액·납기를 추정해 확정하지 않는다.
10. **테스트:** 명확/모호/없음/취소/가정/정정 대화, 인젝션 문장, 금액 상충, 컨텍스트 초과. 후보가 인용한 segment가 실제 존재하는지 검사.
11. **운영:** JSON 거부율, 근거 누락, 수동 수정률, 응답 시간·VRAM. 모델 변경은 같은 가짜 데이터 회귀 검사 후 적용.
12. **제외:** 계약의 법률 판단, 가격 산정, 자율 에이전트, 고객 응대. 통화 질문·근거 검색(RAG)은 이 기능(F04)의 범위가 아니며 [웹 MVP 4단계](web-mvp/README.md#week-04)와 [서버 검색 계약](p2-p3-server.md#전사-내용-검색)에서 별도로 관리한다.

#### 장문 후보 병합 규칙

- 모든 입력 segment의 처리 범위를 기록한다. 일부 조각이 실패하면 전체 분석 성공·최종 후보 승인 대기로 전환하지 않는다.
- 겹치는 구간의 같은 제안은 후보 하나로 합치고 근거 segment를 중복 없이 유지한다. 제목이 같다는 이유만으로 서로 다른 약속을 합치지 않는다.
- 같은 약속에 대한 명시적 정정은 이전 값과 정정 근거를 연결하고 최종 제안 하나로 만든다. 명시적 취소만 남으면 등록 가능한 일정은 0개다.
- 단순히 뒤에 등장했다는 이유로 우선하지 않는다. 대상 연결이나 정정 의도가 불명확하면 양쪽 근거와 충돌 이유를 보존하고 NEEDS_CONFIRMATION으로 둔다.
- 조각별 결과가 모두 모인 뒤 통화 전체의 정정·취소를 대조한다. 근거가 존재하는지뿐 아니라 후보 값과 의미가 맞는지도 평가한다. 병합 결과 역시 사용자 승인 전에는 외부로 보내지 않는다.

#### 날짜·시간 해석과 승인 검증

상대 날짜의 기준은 수신/분석 시각이 아니라 출처·신뢰 여부가 확인된 통화 시각과 시간대다. 기준을 모르면 '내일'을 날짜로 확정하지 않고 원문 표현·null·확인 필요를 유지한다. 승인 화면에서 사용자가 통화 기준 시각 또는 일정 날짜를 보완할 수 있어야 한다. 원문 표현과 해석 기준을 함께 보존한다.

MVP Calendar는 시작·종료 일시가 있는 단발 일정만 다룬다. 종일/반복 표현을 임의 시각으로 바꾸지 않는다. 서버는 실제로 유효한 날짜·명시적 시간대·종료 > 시작을 확인하고, 자정 넘김은 날짜를 명시하게 한다. 잘못된 값은 승인 불가, 모호한 값은 확인 필요다. 이미 지난 일정은 승인 시 경고·명시적 확인을 받으며, 전송 지연으로 승인 이후 시작 시각이 지난 미생성 작업은 재확인 전 전송하지 않는다. UNKNOWN인 기존 요청은 생성 재시도보다 결과 대조가 먼저다.

### F05. 해시 중복 방지·단계별 재시도

1. **문제:** 같은 녹음·클릭·응답 재전송이 비용과 중복 일정을 만들지 않게 한다.
2. **시나리오/완료:** 한 논리 작업의 여러 전달을 하나의 수락 결과로 합치고 실패 단계만 재개한다.
3. **입력:** 파일 SHA-256, 단계·버전, 요청 키, lease_token, 외부 요청 ID.
4. **흐름:** 수신 → 고유 제약 확인 → 기존 결과 재사용 또는 새 시도 → 성공 기록.
5. **서비스:** DB 고유 제약·트랜잭션이 기본, 서버/워커/n8n은 같은 요청 ID를 유지.
6. **데이터/상태:** attempt와 논리 job 분리, 오류 범주·next_attempt_at·상한. 외부 결과 불명은 UNKNOWN.
7. **보안:** 해시·ID도 연계 식별자이므로 공개하지 않는다. 같은 키로 다른 요청 본문을 보내면 거부한다.
8. **실패/재시도:** 최초 시도 이후 자동 재시도 최대 3회(총 4회 시도), 1/5/30분 backoff+jitter를 초기안으로 둔다. 인증 오류는 재인증 대기, 오프라인은 대기. 재연결 시 동시에 큐 전체를 실행하지 않는다.
9. **사람 승인:** 실패 상한 이후 수동 재개, 사적 제외 해시를 되살릴 때 명시적 새 분류와 삭제 기록 변경 이력 필요.
10. **테스트:** 중복 파일·버튼·결과, 성공 후 응답 유실, 워커 충돌, 재인코딩 파일은 별도 콘텐츠임을 확인.
11. **운영:** 차단 건수·재시도 분포·UNKNOWN 목록. DB를 잃으면 중복 방지도 잃으므로 Calendar 자동 재생성 금지.
12. **제외:** 음성 유사도 중복 판정, 분산 시스템에서 물리 연산이 항상 한 번만 실행된다는 보장. 중복 시도는 가능하나 최종 결과·부작용은 통제한다.

### F06. 분류·결과 승인 요청 알림과 검토 화면

1. **문제:** 서버를 열어보지 않아도 새 통화와 미확정 약속을 검토하게 한다.
2. **시나리오/완료:** 알림 → 인증된 검토 화면 → 업무 분류 또는 후보 수정·승인/거절 → 현재 상태 표시.
3. **입력:** DB 알림 outbox의 작업 ID·시각·길이·후보 개수. 외부 채널에는 허용 필드만.
4. **흐름:** DB 결정과 알림 outbox를 함께 저장 → n8n 조회 → 전송 → delivery 기록 → 사용자 POST 결정.
5. **서비스:** CallOps UI/API가 승인 주체와 DB 검증 담당, 공용 n8n이 전송 담당. 채널은 미정.
6. **데이터/상태:** notification_attempts, classification_events, approvals. 화면은 통화 목록·상세 근거·필드 편집·승인 결과를 제공.
7. **보안:** VPN만으로 사용자 인증을 대체하지 않음. 인증 세션·CSRF 방어 또는 검증된 채널 사용자+서명 구현. GET 링크 방문과 미리보기로 승인되지 않게 한다. 일회성 토큰도 해당 작업·행위·만료에 한정.
8. **실패/재시도:** 전송 성공 후 응답 유실은 중복 알림 가능, 버튼은 멱등 처리. 전송 실패가 STT를 다시 실행하지 않는다. 재알림이 72시간 만료를 무한 연장하지 않는다.
9. **사람 승인:** 업무 분류와 결과 승인 버튼을 구분. 최종 제목·시간·목적지를 보여준 revision만 승인. 미응답은 승인 아님.
10. **테스트:** 잘못된 사용자, 토큰 만료·재사용, 링크 스캐너 GET, 동시 버튼, 오래된 revision, 승인 후 수정, n8n 중단.
11. **운영:** 전송 성공/실패·미검토 수·최장 대기. 수신된 알림 삭제가 서비스의 보존 사본까지 삭제함을 보장하지 않으므로 내용 최소화.
12. **제외:** 공유 PC 무인 자동 승인, 개인정보가 보이는 전체 요약 푸시, 알림 봇이 직접 DB 승인 컬럼 수정.

#### 내부 할 일의 승인 이후 흐름

- P5에서 할 일 후보 승인과 tasks의 OPEN 생성은 한 트랜잭션으로 수행한다. 같은 후보 재승인은 기존 할 일을 반환하고 중복 생성하지 않는다.
- 최소 화면은 미완료/완료/취소 목록, 기한 초과 필터, 제목·기한 수정, 완료·취소·재열기다. 기한 미정은 null로 유지하며 자동 날짜를 넣지 않는다.
- 수정과 상태 변경은 인증된 사용자의 POST 및 revision 검사로 수행한다. 최초 승인 스냅샷은 해당 보관기한까지 유지하고 현재 할 일 revision을 증가시킨다. 재분석이 사용자 수정이나 완료 상태를 덮어쓰지 않는다.
- 할 일 완료는 후보 승인 철회가 아니다. 외부 할 일 서비스·담당자 배정 알림은 MVP에 추가하지 않는다.
- 승인된 할 일은 후보와 별도의 보관 대상을 갖는다. 후보 만료 시 할 일로 연쇄 삭제하지 않고 근거 만료를 표시한다. 구체적인 기한은 10절을 따른다.
- 검증: 중복 승인 1건, 동시 편집 충돌, 완료/재열기, 기한 미정·초과 필터, 후보 만료 후 할 일 유지, 통화 전체 삭제 시 연결 할 일 삭제.

### F07. 승인 기반 Calendar 등록·삼성 캘린더 표시

CallOps는 자체 월간 캘린더에서 통화 후보를 승인해 만든 일정과 직접 입력한 일정을 함께 표시한다. 날짜를 선택하면 해당 날짜의 일정 목록과 상세로 이동할 수 있다. 양방향 동기화는 사용자가 명시적으로 연결한 일정과 전용 Google Calendar 한 개를 대상으로 한다. CallOps에서 연결한 일정을 Google에 생성하고, 연결 이후에는 양쪽의 수정·삭제를 반영한다. 통화 당시 승인 스냅샷과 현재 일정은 구분한다. [웹 MVP 6단계](web-mvp/README.md#week-06)

1. **문제:** 확인한 약속을 다시 입력하는 수고를 줄인다.
2. **시나리오/완료:** 최종 일정 승인 → 등록 → 외부 ID 저장 → 삼성 앱 동기화 표시. API 성공과 휴대전화 표시 확인은 구분.
3. **입력:** 일정 제목·시작/종료·시간대와 허용 `calendar_id`. 최초 전송하는 통화 일정은 사용자가 승인한 revision을 사용한다. 장소·짧은 메모는 선택 항목으로 범위를 별도 확인한다. 원음·전사 원문은 전송하지 않는다.
4. **흐름:** CallOps 외부 작업 기록 → n8n claim → Google 요청 → 결과 저장 → 삼성 계정 동기화. Google에서 연결 일정이 변경되면 변경 내역을 조회해 CallOps의 현재 일정에 반영한다.
5. **서비스:** CallOps는 승인/멱등성 기준, n8n은 OAuth/전송, Google은 일정 저장, 삼성은 사용 화면.
6. **데이터/상태:** 일정 승인 상태와 전송 상태를 분리한다. 요청 전에 내부 일정 ID와 외부 `calendar_id`·`event_id`의 연결, 외부 요청 ID·해시·시도를 기록한다. Google 변경은 현재 일정에 반영하고 기존 승인 스냅샷은 보관 정책에 따라 유지한다.
7. **보안:** 참석자·첨부·전체 전사·계약 내용 제외. 대상 캘린더 allowlist. 캘린더 선택만으로 OAuth 권한이 그 캘린더 하나로 제한되는 것은 아님. 동의 화면과 자격증명 범위를 검증한다.
8. **실패/재시도:** event_id를 API 허용 형식으로 사전 결정하고 재시도 때 재사용한다. timeout은 UNKNOWN으로 조회·대조 후 재시도. 409는 기존 이벤트 비교, 401/권한 오류는 재인증/수동 확인, 429/5xx는 제한 backoff. 노드가 ID 지정을 못하면 n8n HTTP Request로 같은 계약 구현을 검토한다.
9. **사람 승인:** 통화 후보 승인과 Google 연결은 별도 행동이다. 연결한 일정은 사용자가 CallOps에서 확정한 수정·삭제를 Google에 반영하고, Google의 변경도 가져온다. 후보 재분석·편집, 통화 사적 전환, 보관 기한 만료 자체는 Google 일정의 수정·삭제 지시가 아니다. 양쪽에서 동시에 바뀐 경우 사용자 확인을 기다린다. 연결된 일정 삭제를 기록하고 동기화 재시도로 재생성하지 않는다.
10. **테스트:** 모의 Calendar와 임시 PostgreSQL에서 승인·연결·중복 생성 방지와 양쪽 수정·삭제, 동시 변경 충돌, 당시 합의 보존을 먼저 시험한다. 이후 별도 승인 받은 시험 캘린더에서 OAuth와 실제 양방향 반영을 확인하고, 삼성 표시를 별도로 확인한다.
11. **운영:** AUTH_REQUIRED·UNKNOWN·외부 반영 지연 확인. 백업 없는 DB 복구 시 Google 기존 이벤트부터 대조하고 자동 재생성 금지.
12. **제외:** 기본 캘린더 전체 접근을 전제로 한 기능, 자동 초대·메일·계약 확정, 반복 일정, 외부 할 일 시스템, 삼성 계정에 직접 쓰는 서버 API.

Google은 생성 요청에 자체 이벤트 ID를 지정해 성공 후 응답 유실에 따른 중복을 줄이는 방법을 설명한다. 구현 시 허용 형식과 조회·충돌 처리를 함께 검증한다. [공식 생성 안내](https://developers.google.com/workspace/calendar/api/guides/create-events)

### F08. 원본·전사·요약 보관과 삭제

1. **문제:** 사적·오래된 데이터가 여러 장비·캐시에 남지 않게 한다.
2. **시나리오/완료:** 보관기한/삭제 선택 → 처리 취소 → 각 복사본 청소 → 검증 → 최소 삭제 이력 유지.
3. **입력:** 분류·보관기한·파일 manifest. 휴대전화 원본은 서버 정책의 삭제 대상이 아니다.
4. **흐름:** 삭제 scope·대상 영속화 → 해당 데이터를 요구하는 claim/결과/미전송 작업 차단 → scope에 속한 서버·GPU 사본 청소 → 잔여 목록 확인. 음성 만료와 통화 전체 삭제는 아래처럼 구분한다.
5. **서비스:** 서버 청소 루프와 데스크톱 워커가 각 파일을 관리, 동기화 도구는 재수신 제어에 협력.
6. **데이터/상태:** 복사본별 경로 키·삭제 상태·오류, tombstone. 전체 완료는 모든 관리 장비 확인 후.
7. **보안:** 로그·임시 파일·동기화 버전 보관·crash dump까지 점검. SSD/ext4 파일 삭제는 물리 복구 불가 삭제를 보장하지 않는다.
8. **실패/재시도:** 오프라인 GPU는 청소 대기 표시. 수신 재등장 시 재처리 금지. tombstone 90일은 만료 최소 제안으로, 소스 재수신 가능성이 남으면 자동 제거하지 않는다. 승인된 재수집만 예외로 처리.
9. **사람 승인:** 보관 기간·명시적 조기 삭제를 사용자 선택에 연결. 서버 기록 삭제와 이미 만든 Calendar 삭제는 별개이며 자동 전파 금지.
10. **테스트:** 파일명 변경·재연결·동기화 복원·버전 사본·취소 중 결과 도착·오프라인 GPU·tombstone 만료.
11. **운영:** 요청/완료/미완료 수·잔여 복사본·기한 초과 확인. 백업은 현재 없음; 향후 백업 보존·삭제 만료도 정의해야 함.
12. **제외:** 휴대전화 원본 원격 삭제, 포렌식 삭제 보장, 영구 무제한 보관.

#### 삭제 범위와 검토 가능 범위

| scope / 계기 | 삭제·차단 범위 | 유지·화면 동작 |
|---|---|---|
| AUDIO_ONLY / 업무 음성 30일 만료 | 서버 수신·격리·outbox와 GPU inbox/work의 해당 음성, STT 신규 실행·진행 결과 수락 차단 | 수락된 전사 기반 분석·후보 검토는 각 만료 전까지 가능. 음성 재생 불가와 전사만으로 검토함을 표시 |
| DERIVED_ONLY / 전사·요약·후보 90일 만료 | 만료된 산출물·근거·관련 GPU 사본, 이를 입력으로 쓰는 분석과 미전송 일정 작업 차단 | 승인된 내부 할 일의 제목·기한·상태와 외부 중복 방지용 최소 ID는 별도 정책 적용. 새 후보 승인 불가 |
| RECORDING_ALL / 사적 전환·명시적 통화 전체 삭제·미분류 만료 | 해당 통화의 모든 관리 음성·산출물·근거·연결 할 일, 신규 처리와 미전송 외부 작업 차단 | 최소 삭제·중복 방지 식별 기록만 유지. 휴대전화 원본과 이미 생성한 Calendar는 자동 삭제하지 않음 |

삭제와 결과 수락은 서버에서 같은 대상 상태를 검사해 경합을 해결한다. 처리 중이라는 이유로 만료를 자동 연장하지 않는다. 이미 IN_FLIGHT인 Calendar 요청은 결과를 대조할 최소 식별 기록을 유지하고 7절 규칙을 적용한다. 부분 만료를 '통화 전체 삭제 완료'로 표시하지 않는다.

음성 만료 후에는 STT 재실행을 자동 요청하지 않는다. 전사도 없으면 분석을 INPUT_EXPIRED 사유로 중지하고, 필요한 경우 사용자가 원본을 다시 선택·분류한다. 사용자가 음성을 들어야 판단할 수 있는 후보는 승인하지 않고 보류/거절할 수 있어야 한다.

### F09. 복구·상태 모니터링·향후 백업

1. **문제:** 워커 중단과 처리 실패를 알아채고 데이터 유실 시 잘못된 재실행을 막는다.
2. **시나리오/완료:** 상태 이상 → 최소 정보 알림 → 원인 확인 → 해당 단계 재개. 빈 DB 복구는 외부 출력 비활성으로 시작.
3. **입력:** 상태 DB·heartbeat·서비스 health·디스크·GPU 메타데이터. 로그에 원문을 넣지 않는다.
4. **흐름:** 서비스 계측 → 제한된 상태 API → Uptime Kuma/운영 화면 → 관리자 알림.
5. **서비스:** 기존 Kuma 재사용, CallOps가 queue age/worker readiness 계산, n8n은 가능한 경우 알림.
6. **데이터/상태:** 마지막 응답·대기 시간·실패율·여유 공간·모델 시간, 복구 모드 플래그.
7. **보안:** health 응답에 환경변수·DB 문자열·파일명 노출 금지. n8n 장애 감지는 Kuma 자체 채널을 별도로 고려.
8. **실패/재시도:** 같은 장애 반복 알림 제한, 정상 복귀 알림. DB 유실과 프로세스 재시작을 구분. 설정 재설치로 승인 이력이 복구된다고 표시하지 않는다.
9. **사람 승인:** 데이터 유실 후 원본 재수집·기존 Calendar 대조·자동 출력 재개는 수동 확인.
10. **테스트:** 워커 전원 OFF, API 500, DB 장애, n8n 장애, 디스크 부족, 빈 DB 복구와 외부 쓰기 차단.
11. **운영:** 일일 실패/대기/삭제 점검, 주간 용량/버전 확인. 백업은 보류이며 성공 지표를 허위로 표시하지 않는다.
12. **제외:** 지금 백업 장치 구매·암호화 재구성·HA 구축. 향후 DB, n8n DB+키, 원본/결과, 환경 복구를 따로 설계.

## 7. API와 워커 경계 — 구현 전 확정할 계약

API 경로는 P1/P3에서 확정하되 다음 작업 경계는 유지한다.

| 요청 | 호출자 | 서버가 확인할 것 |
|---|---|---|
| 목록·녹음·후보 상세 | 인증된 사용자 | 본인 접근, 제한된 파일 스트리밍 |
| 분류·보류·취소 | 사용자 | 현재 상태·요청 키·CSRF/서명 |
| 후보 편집·승인·거절 | 사용자 | revision·필수값·내용 스냅샷 |
| 내부 할 일 조회·수정·완료·취소·재열기 | 사용자 | 본인 접근·CSRF·요청 키·revision·보관 만료 |
| job claim/heartbeat/result | 워커 | 작업 할당·임대·승인 유지·해시·스키마 |
| 실행 시작/결과 준비 보고 | 워커 | 현재 임대·상태별 기한·요청 키·결과 해시/크기, 같은 보고는 같은 상태·기한 반환 |
| 분석 입력 전사 조회 | 워커 | 할당된 분석 job/lease·고정 artifact ID/버전/해시·업무 승인·입력 만료/삭제 여부 |
| 삭제 지시 조회·복사본 청소 확인 | 워커 | 인증된 worker_id에 배정된 삭제 요청·복사본 키·요청 버전, 활성 연산 임대 불필요 |
| 알림/외부 작업 claim·결과 | n8n | 역할 범위·승인 revision·작업 임대 |
| health/readiness | Kuma/관리자 | 인증 범위·최소 메타데이터 |

성공한 결과를 같은 요청 키로 재전송하면 기존 수락 결과를 돌려준다. 같은 키에 다른 본문이면 충돌로 거부한다. 결과 업로드는 자유 경로/SQL/승인 상태 변경을 받지 않는다. 콘텐츠 길이·JSON 배열 수·문장 길이·오디오 시간 범위를 제한한다.

공용 n8n은 신뢰받는 운영 구성요소이지만, 태그나 워크플로우 이름은 보안 경계가 아니다. 관리자나 같은 권한의 워크플로우가 자격증명을 악용하지 못한다는 보장은 없다. 승인 검사는 CallOps API에도 두고 n8n의 raw DB UPDATE를 금지한다.

Calendar 전송 claim 시 현재 승인 revision을 다시 확인하고 전송할 스냅샷을 잠근다. 아직 전송 전이면 취소·수정으로 작업을 무효화할 수 있다. 이미 IN_FLIGHT인 요청은 취소가 외부 등록을 되돌린다고 보장하지 않으며, 화면에 전송 중/결과 확인 중을 표시한다. 결과를 확인한 뒤 필요한 일정 변경은 사용자가 수행한다.

### 분석 입력과 재시도 계약

STT 수락 트랜잭션에서 불변 전사 artifact와 이를 참조하는 분석 작업을 연결한다. 분석 claim은 input_artifact_id, input_artifact_version, input_sha256, schema_version, 통화 시각·신뢰 여부를 반환한다. 워커는 해당 임대로 전사를 제한 API에서 가져와 해시·버전을 검증한다. 서버 transcripts 폴더 직접 공유나 임의 경로 다운로드는 허용하지 않는다.

동일 분석 작업의 재시도는 같은 입력을 사용하며 '최신 전사'로 자동 교체하지 않는다. 재전사 결과를 분석하려면 새 처리 버전의 작업을 만들고 기존 후보·승인을 덮어쓰지 않는다. 결과에도 입력 artifact 식별자를 포함해 서버가 일치 여부를 검사한다. 입력 만료는 INPUT_EXPIRED, 삭제/승인 취소는 작업 취소, 저장소 파일 유실은 INPUT_MISSING으로 수동 확인하며 STT를 자동 재실행하지 않는다. 네트워크 조회 실패만 backoff로 재시도한다.

### 준비·연산·전송 제한시간 계약

임대는 워커 연결 유효성이다. heartbeat는 claim 직후부터 입력 다운로드·복사·해시 검사·연산·업로드와 독립적으로 유지한다. 상태별 상한은 최초 진입 때 서버가 한 번 확정하며 같은 요청 재전송으로 연장하지 않는다.

| 상태 | 시작과 종료 | 초기 시험안 / 실패 |
|---|---|---|
| PREPARING | claim 수락 → 입력 검증 후 실행 시작 요청 수락 | 10분, PREPARATION_TIMEOUT. 파일 미도착은 임대 반환 후 WAITING_FOR_FILE, 연산 실패 횟수 증가 없음 |
| RUNNING | 실행 시작 수락 → 결과 준비 보고 수락 | 모델 로드·전체 조각·병합 포함 STT 60분/분석 30분, STAGE_TIMEOUT |
| UPLOADING | 결과 준비 보고 수락 → 파일·DB 영속화 ACK | 30분, UPLOAD_TIMEOUT. 현재 임대와 삭제/승인 검사는 유지 |

워커는 결과 JSON을 spool에 완전히 기록한 뒤 현재 임대로 result_request_id·정확한 파일 바이트의 해시·크기를 보고한다. 서버는 실행 상한 안에서만 이 보고를 수락하고 UPLOADING으로 전환하며 upload_deadline을 반환한다. 이후 같은 해시·크기의 결과만 받는다. 연산 상한이 지나도 전송 상한 안에서는 업로드만 재시도할 수 있다. 전송 상한은 spool의 최초 생성 후 24시간 TTL이나 입력 보관기한을 넘을 수 없다. 재시작·재전송으로 TTL을 초기화하지 않는다.

실행 시작/결과 준비 보고의 응답 유실 시 같은 요청 키로 재조회해 기존 상태·기한을 받는다. 결과 준비 보고 자체가 실행 상한까지 서버에 도달하지 못한 경우는 로컬 완료 시각만 믿고 구 결과를 수락하지 않는다. 임대가 만료되거나 새 시도가 배정되면 보고·업로드 모두 거부한다. 이미 수락된 결과 재조회는 기한 이후에도 원문 없는 기존 ACK만 반환한다.

상한 도달 시 해당 상태의 갱신·새 결과 수락을 차단한다. 워커는 서버 응답의 남은 시간을 보수적으로 단조 시계에 적용하며 네트워크 지연·재부팅으로 기한을 연장하지 않는다. 연산 중단 → 30초 대기 → 자신이 시작한 연산 프로세스/요청 종료를 수행한다. 종료와 GPU readiness 확인 전에는 새 claim을 하지 않으며, 확인 실패는 수동 복구한다. 다른 사용자의 프로세스를 일괄 종료하지 않는다. 준비/업로드 시간 초과는 해당 단계 오류로 따로 집계하고 F05 상한 이후 수동 확인한다. UPLOAD_TIMEOUT 후 기존 시도를 새 임대로 위장해 재사용하지 않는다.

### 재분석 후보와 기존 출력 연결

같은 녹음의 새 처리 버전은 기존 후보를 덮어쓰지 않는다. 대신 승인 화면에서 기존 일정·할 일의 최소 식별 정보와 상태를 대조하고, 각 재분석 후보에 '기존 항목에 연결 / 별도 신규 항목 / 거절' 결정을 요구한다. 자동 의미 유사도 병합은 MVP에서 만들지 않는다. 기존 내용이 만료됐으면 내용 대신 ID·기존 출력 존재 여부를 표시하고 사용자가 Calendar/할 일에서 확인한다.

기존 항목 연결은 logical_item_id를 재사용하며 Calendar 생성·수정이나 새 할 일 생성은 하지 않는다. 화면에는 '기존 항목 연결됨, 내용 반영 없음'을 표시한다. 별도 신규 생성은 중복 가능성을 확인한 사용자 결정과 새 logical_item_id를 기록한다. Calendar 생성 멱등 키와 내부 할 일 고유 제약은 후보 revision 대신 logical_item_id를 기준으로 한다. 같은 후보의 재승인·revision 변경으로 logical_item_id를 새로 만들지 않는다. 동일 녹음의 승인 결정을 트랜잭션으로 직렬화하고 오래된 비교 화면은 다시 확인하게 한다.

첫 승인에서 logical_item_id를 발급하고 이후 후보 연결·출력 생성 결정 때 recordings.output_decision_version을 증가시킨다. 비교 화면은 이 버전도 제출해 동시 결정의 변경 여부를 검사한다. 후보 내용 만료 후에도 재생성 방지에 필요한 logical_item_id·외부 연결·삭제 여부는 최소 식별 기록으로 유지한다. 아직 외부 요청을 보낸 적이 없거나 미생성이 확인된 경우에만 새 승인 스냅샷으로 생성 작업을 다시 준비할 수 있다.

외부 생성이 이미 성공한 항목의 후보 수정은 새 Calendar 생성을 예약하지 않는다. MVP에서 외부 수정은 Calendar에서 수행한다. 최초 요청이 UNKNOWN/IN_FLIGHT이면 기존 결과 대조 전 새 생성 요청을 막는다.

### 외부 작업 취소와 불명 결과

아직 발송되지 않았거나 미생성이 확인된 작업만 CANCELLED로 종료하고 claim 대상에서 제외한다. UNKNOWN/IN_FLIGHT에 취소·만료가 겹치면 retry_allowed=false와 종료 사유를 기록하고 조회·대조만 허용한다. 생성 확인 시 SUCCEEDED와 '취소 전에 등록됨'을 표시하고, 미생성 확인 시 CANCELLED로 종료한다. 불명 상태를 확인 없이 CANCELLED로 바꾸거나 생성 요청을 재시도하지 않는다.

한 번의 조회 실패를 미생성 증거로 단정하지 않는다. 아직 요청이 처리 중이거나 조회 권한/네트워크가 불확실하면 UNKNOWN을 유지한다. 미생성 여부를 안전하게 확인할 수 없는 경우 수동 확인 대상으로 남긴다. 취소 완료 후 새로 보이는 과거 성공 응답도 버리지 않고 원래 delivery를 대조 대상으로 다시 표시한다.

외부 결과 수신은 현재 후보 revision과 다른 과거 요청이어도 해당 delivery·attempt의 사실 기록으로 수락한다. 새 승인을 만들거나 최신 스냅샷을 덮어쓰지는 않는다. 삭제된 내용은 복원하지 않고 최소 외부 ID·상태만 기록한다.

### 파일 저장과 DB 기록의 장애 경계

파일시스템 저장과 DB 트랜잭션을 하나의 원자적 작업으로 간주하지 않는다. 수신·전사 결과는 제한된 임시 경로에 기록·해시 검사·디스크 반영 후 같은 파일시스템의 정식 키로 원자적 이름 변경한다. 수신은 해시·분류/삭제 상태를 검사해 분류 대기 메타데이터만 등록하며 AI 작업을 만들지 않는다. 전사 결과는 임대/승인/삭제 상태를 다시 확인해 참조·작업 성공·다음 작업/outbox를 함께 커밋한 뒤 ACK한다.

이름 변경 후 DB 실패로 남은 파일은 재시작 시 작업 ID·해시로 대조해 유효한 재요청에서 연결하거나 청소한다. DB 참조만 있고 파일이 없으면 성공으로 표시하지 않고 INPUT_MISSING으로 중지한다. 진행 중 업로드와 청소가 경합하지 않도록 작업별 상태/manifest로 대상 파일을 잠그고, 활성 임시 파일을 나이만 보고 삭제하지 않는다. 취소가 먼저 확정되면 업로드 파일도 청소 대상으로 등록한다.

### 취소 후 청소와 수신 중단

워커는 활성 job 임대가 없어도 자신의 삭제 요청을 조회·확인할 수 있어야 한다. 삭제 지시는 자유 파일 경로 대신 관리 루트 안의 복사본 키와 요청 버전을 사용한다. 재연결 시 청소를 새 claim보다 먼저 수행하고, 서버는 요청한 버전의 모든 사본 제거 확인을 받아 완료 처리한다. 토큰 폐기/장비 고장으로 확인할 수 없으면 삭제 미완료를 유지한다.

디스크 부족·DB 복구 모드에서 '수집 중지'는 앱의 파일 탐색만 멈추는 것을 뜻하지 않는다. CallOps 전용 동기화 폴더 수신도 일시 중지하거나 해당 저장소 용량 제한으로 새 쓰기를 차단해야 한다. 제어는 해당 폴더에 한정하며 공용 서비스·휴대전화 원본에는 손대지 않는다. 실제 파일 전송이 멈추는지 시험하고, 기존 삭제 작업은 가능한 범위에서 계속 수행한다.

## 9. 공통 검증 데이터와 기록 방식

다음 합성/직접 녹음 대본의 정답을 먼저 고정한다. 중복은 복사해서 만들고, T06은 설정한 컨텍스트를 넘도록 비민감 대화를 넣어 정정이 다른 조각에 배치되게 한다.

| ID | 내용 | 예상 |
|---|---|---|
| T01 | 날짜·시작·종료가 명확한 업무 약속 | 승인 대기 일정 1개, 승인 전 등록 0개 |
| T02 | “다음 주쯤”·종료시간 없음 | 확인 필요, Calendar 0개 |
| T03 | 약속 없는 업무 현황 | 요약만, 일정 0개 |
| T04 | 가짜 사적 대화 | 분류에서 사적 선택, 전사/추출 0회 |
| T05 | 잡음·무음·서로 정정하는 가짜 금액 | 낮은 신뢰 표시/수동 확인, 계약 자동 확정 0개 |
| T01-copy | 파일명만 바꾼 T01 | 새 STT 작업·중복 일정 없음 |
| T06 | 앞 조각의 화요일 약속을 뒤 조각에서 목요일로 명시적 정정; 날짜·시작·종료 명확 | 목요일 최종 후보 1개, 화요일 등록 가능 후보 0개, 양쪽 근거 연결 |
| T07 | 전사에 '지시 무시·즉시 등록' 문장을 포함, 실제 약속 없음 | 일정 0개, 승인 상태 조작·외부 호출 0회 |
| T08 | 서로 다른 조각에서 같은 대상의 금액 충돌, 정정 의도 불명확 | 확인 필요, 양쪽 값·근거 유지, 임의 최종 금액 없음 |
| T09 | 앞 조각의 약속을 뒤 조각에서 명시적으로 취소 | 등록 가능 일정 0개, 취소 근거 유지 |
| T10 | 제목이 비슷하지만 서로 다른 날짜의 두 약속, 중첩 구간에 한 약속 반복 | 최종 일정 2개, 중첩 중복 0개, 서로 다른 약속 유지 |

가짜 사람·회사·번호만 사용한다. 녹음 원본은 Git 밖에 두고 대본·기대 결과만 Git에 넣는다. 모델 평가에는 출력 문장 일치보다 누락·환각·근거·상태·등록 차단을 검사한다.

검증 보고에는 실행한 버전, 테스트 ID, 기대/실제, 성공 여부, 미해결 사항을 남긴다. 실제 서비스 로그는 원문 없는 job ID와 오류 코드만 확인한다. 문서 링크·공백 검사는 이번 문서 작업의 검증이고, 런타임 테스트 완료로 표기하지 않는다.

### 모델 선택·변경 합격 기준

| 항목 | 고정 평가 세트의 통과 기준 |
|---|---|
| 명확한 약속 | T01/T06/T10의 정답 일정 누락 0개, 추가·중복 0개, 날짜·시작·종료 일치 |
| 불확실·충돌·취소 | T02/T05/T08의 확인 필요 유지, 임의 날짜·금액 확정 0개, T09의 등록 가능 후보 0개 |
| 근거·입력 범위 | 최종 후보의 실제 segment 연결 100%, 사람이 대조한 값·근거 의미 불일치 0개, 처리 누락 segment 0개 |
| 경계 | T04 AI 호출 0회, T07 승인 조작·외부 호출 0회, 모든 일정의 사람 승인 전 외부 등록 0개 |
| STT 핵심 필드 | 명확히 발음한 정답 날짜·시간·금액·고유명사 오류 0개. 잡음/겹침은 경고·수동 확인으로 처리하며 일반 정확도 보장으로 표현하지 않음 |
| 처리시간 | D3/D4에서 동일 버전으로 입력별 3회 실행, 최초 모델 로드 포함 시간과 이후 시간 기록. 지원 최대 길이 입력도 7절 상한 내 완료·OOM 0회 |

STT 평가는 음성→전사, 추출 평가는 정답 전사→후보로 나눠 원인을 확인하고 최종 음성→후보도 검증한다. 품질 기준은 각 평가 실행에서 충족해야 하며, 실패한 모델/프롬프트는 운영 선택을 보류한다. 더 느린 모델이 필요하면 상한 변경 근거를 기록하고 같은 시험을 다시 통과해야 한다. 이 기준은 소규모 고정 세트의 출시 조건이며 실제 통화 전체의 정확도 수치가 아니다.

추가 장애 시험: STT ACK 직후 로컬 파일 삭제·워커 재시작 후 분석 성공, 다른 작업/만료 임대의 전사 조회 거부, 입력 버전 불일치 거부, heartbeat 정상 상태의 연산 정지와 상한 종료, 종료 확인 실패 시 새 claim 차단. 보관 시험은 테스트 시계로 음성 30일/산출물 90일/할 일 기한 및 삭제·결과 수락 경합을 검증한다.

다음 경계 사례도 단계 완료 조건에 포함한다.

- P3/D5: 입력 준비가 5분을 넘어도 갱신된 임대는 유효, 준비 상한 초과 시 반환/종료. 실행 시작·결과 준비 보고 ACK 유실 시 기한 불변. 연산 상한 전 완료 보고 후 상한을 넘긴 업로드는 upload_deadline 안에서 성공. 보고 없이 상한 초과·해시 변경·구 임대 업로드는 거부.
- P4/C3: 파일 이름 변경 직후 DB 장애, DB 커밋 직후 ACK 유실, 파일 유실, 취소 중 업로드를 각각 주입해 중복·고아 파일·거짓 성공이 없는지 확인.
- P5/P7: 재분석 후보의 기존 항목 연결은 새 출력 0개, 명시적 별도 생성만 1개. 등록 후 수정·재승인은 새 Calendar 0개. 동시 승인 시 오래된 비교 화면 거부.
- P7/P8: 전송 전 취소는 CANCELLED, UNKNOWN 상태 취소는 조회만 수행. revision 변경 후 과거 성공 응답도 원래 delivery에 기록. 미생성 확인 전 재생성 0개.
- P2/P8/D6: 임대 취소 후 재연결에서도 청소 지시 조회·완료 확인 가능, 삭제 요청 버전 불일치는 완료 처리 금지. 앱 중단·디스크 제한 시 동기화 도구의 신규 파일 쓰기도 중단.
- P5/P7: 기준 통화 시각 미상의 '내일', 월말/연말, 잘못된 날짜, 종료 ≤ 시작, 종일/반복 표현, 전송 지연으로 지난 일정에서 임의 등록 0개.

할 일의 OPEN 보관 종료일은 생성 시 기록하고 명시적 연장 때만 갱신한다. 완료/취소 후 재열면 이 종료일을 다시 적용하며, 이미 지났다면 사용자 연장 없이는 재열 수 없다. 통화 전체 삭제는 이 기한과 무관하게 연결 할 일을 함께 삭제한다. 후보·근거 만료 시에는 연결 ID만 최소한으로 남기고 삭제한 제목·근거를 승인 스냅샷이나 이력에 중복 보관하지 않는다.

## 12. CallOps 배포·연동·운영 — 프로젝트 책임

다음 단계는 기존 서버 문서에서 옮긴 CallOps 전용 실행 절차다. 수행 장소는 주로 Ubuntu 홈서버이고, 소유권·명세·코드·테스트·운영 책임은 이 프로젝트에 있다. 공용 n8n의 설치 완료와 CallOps 워크플로우 연결 완료는 별개다.

### C0 — CallOps 배포 대상과 변경 범위 확인

#### 해야 할 일

- [ ] 홈서버의 기존 서비스·포트·볼륨과 충돌하지 않는 CallOps Compose 이름·경로를 정한다.
- [ ] CallOps 앱·DB·파일 저장소를 별도 운영 단위로 배포한다.
- [ ] 실제 CallOps 데이터 마운트·전용 계정·파일/DB 권한을 확인한다.
- [ ] CallOps API의 VPN 주소·프록시·TLS·데스크톱 경로를 프로젝트 설정으로 기록한다.
- [ ] CallOps 모니터와 알림 목적지는 프로젝트 요구에 맞춰 결정한다.
- [ ] 공용 n8n 사용 시 주소·버전·인증 방법을 인프라 담당에서 전달받는다. 관리자 비밀값을 저장소에 복사하지 않는다.

홈서버 자원은 사용자 출력상 약 25GiB RAM·415GiB 여유 공간이었다. 배포 전에 현재 자원을 재확인한다. 기존 chanvoca/finel DB는 변경하지 않고 CallOps 전용 PostgreSQL을 기본안으로 둔다. n8n용 DB는 공용 인프라가 별도로 관리한다.

#### 하면 안 되는 일 / 완료 조건

CallOps 배포·제거 명령에 공용 n8n이나 다른 프로젝트 볼륨을 포함하지 않는다. 변경할 경로·포트·컨테이너·권한과 배포 대상이 특정되면 C0 완료다.

### C1 — CallOps 앱·DB·저장소 준비

#### 해야 할 일

- [ ] 프로젝트의 승인된 코드/마이그레이션 버전을 배포한다.
- [ ] CallOps Compose와 데이터 루트는 공용 n8n과 분리한다.
- [ ] 앱 전용 계정과 DB 역할을 만든다. 앱 런타임 역할과 마이그레이션 권한은 구분한다.
- [ ] PostgreSQL을 호스트 포트에 공개하지 않는다.
- [ ] n8n은 CallOps API에만 접근하고 DB 네트워크에는 연결하지 않는다.
- [ ] API는 프록시 또는 VPN 인터페이스로 제한한다.
- [ ] 앱 health와 DB readiness, 디스크 부족 시 수집 중단을 구현한다.

#### 경로와 최소 권한

실제 경로는 배포 시 확정한다. 아래는 역할별 논리 경로다.

| 경로 | 용도 | 읽기/쓰기 |
|---|---|---|
| sync-inbox | 갤럭시 수신 | 동기화 계정, 수집·청소 계정 |
| quarantine | 분류 전 독립 사본 | CallOps 수집·검토·청소만 |
| gpu-outbox | 업무 승인 파일 전달 | CallOps 준비/청소, 전용 동기화 계정 |
| transcripts | 전사본 | CallOps 검증/검토/청소 |
| rejected | 형식 오류 파일의 제한된 임시 보관 | 수집·청소/관리자 |
| postgres-data | CallOps DB | DB 서비스 계정 |
| runtime-state | 로컬 수신·삭제 복구 목록 | 수집·청소만 |

n8n·GPU 계정에는 quarantine/transcripts 직접 접근을 주지 않는다. 수집 계정의 읽기 권한만으로 sync-inbox 삭제는 수행할 수 없으므로 삭제 담당에 필요한 디렉터리 쓰기 권한을 명시적으로 준다. 다른 경로는 수정하지 못하게 한다.

#### 하면 안 되는 일 / 완료 조건

`chmod 777`, DB 슈퍼유저로 앱 실행, 기존 DB 공유, 앱에 Docker 관리권 부여를 하지 않는다. 앱은 자기 DB/디렉터리만 접근하고 n8n은 음성 파일을 읽지 못하면 C1 권한 검증 완료다. 디스크 암호화와 별도 백업은 이 단계에서 강제로 추가하지 않는다.

### C2 — 가짜 녹음으로 수집·분류·삭제 시험

#### 해야 할 일

- [ ] 개인정보 없는 T01~T05 파일을 테스트 수신 폴더에 직접 넣는다.
- [ ] 완료 신호/임시 파일 여부/안정화/실제 형식/복사본 해시를 확인한다.
- [ ] 등록 중 DB 장애·서버 재시작을 넣어 중복이 없는지 확인한다.
- [ ] 업무/사적/나중에 결정 버튼을 CallOps 검토 화면에서 시험한다.
- [ ] P2에서 로그인·세션 만료·로그아웃·CSRF를 구현하고 미인증 목록/음성 조회·분류 변경을 차단한다. P6 알림 연결까지 인증을 미루지 않는다.

- [ ] 0바이트·너무 큰 파일·허위 확장자·경로 탈출·복사 중단을 거부한다.
- [ ] DB 장애 중에도 기존 삭제 계획을 수행하거나 수신을 중단하는 복구 절차를 시험한다.

#### 완료 조건

미인증 목록/음성 조회·상태 변경과 잘못된 CSRF 요청은 차단된다. 업무 선택 전 Whisper/Ollama 호출과 GPU 작업은 0건이다. 사적 선택/만료 시 서버 관리 사본이 사라지고 `삭제 완료`가 사실과 일치한다. 이 단계에서는 갤럭시 폴더와 실제 고객 녹음은 연결하지 않는다.

### C3 — VPN API·GPU 전달·결과 저장

#### 허용할 통신

| 출발 → 대상 | 목적 | 제한 |
|---|---|---|
| 사용자 VPN → CallOps UI | 분류/결과 검토 | 로그인·HTTPS·CSRF |
| n8n → CallOps API | 알림/외부 작업 claim·결과 | 서비스별 최소 토큰 |
| 데스크톱 VPN → CallOps API | claim/heartbeat/result | 할당된 작업 범위 |
| 동기화 장치 ↔ 지정 장치 | 승인 파일 전송 | 장치 ID·폴더·VPN 경로 제한 |
| CallOps 앱 → CallOps DB | 상태 관리 | Docker 내부 |
| n8n → Google/선택 알림 서비스 | 승인한 외부 전송 | 필요한 아웃바운드 |

홈서버가 Whisper/Ollama에 직접 요청할 포트는 기본 구조에서 필요 없다. 데스크톱 워커가 서버 작업을 가져간다. Docker 포트 바인딩과 방화벽은 실제 비 VPN 환경에서 확인한다. UFW 규칙 하나만으로 Docker 공개 포트가 모두 차단됐다고 판단하지 않는다.

#### 해야 할 일

- [ ] API 토큰은 워커·알림·Calendar 전송 역할별로 제한하고 폐기/재발급 절차를 정한다.
- [ ] 파일 경로 대신 UUID 저장 키·해시를 작업에 넣는다.
- [ ] 업무 승인 뒤에만 outbox 복사·작업 생성을 수행한다.
- [ ] 워커 가용성이 없으면 WAITING_FOR_WORKER를 유지한다.
- [ ] 임대 만료·늦은 결과·취소 후 결과·동시 claim을 검증한다.
- [ ] 전사 파일 저장과 DB 참조가 완료된 후에만 ACK한다.
- [ ] 외부 알림 outbox는 결과 저장 트랜잭션과 연결한다.
- [ ] 잘못된 JSON·근거 구간·과도한 크기의 결과를 거부한다.
- [ ] 분석 입력 artifact 재조회 권한·고정 버전·해시·만료를 검사하고 로컬 전사 삭제/재시작 후 분석만 재시도한다.
- [ ] heartbeat가 정상이어도 연산 상한에서 종료되고, 종료 확인 전 새 작업이 실행되지 않는지 검증한다.

#### 완료 조건

D5와 함께 가짜 업무 파일을 end-to-end 처리하고 데스크톱 OFF/ON, VPN 단절, 결과 ACK 유실을 통과한다. 모델 결과는 후보 생성까지만 허용하며 외부 등록은 발생하지 않는다.

### C4 — 공용 n8n에 CallOps 알림 연결

#### 프로젝트가 공용 n8n에 구성할 항목

- 워크플로우에 `CallOps /` 접두사와 가능한 태그/폴더를 사용한다. 권한 격리를 보장하는 기능으로 간주하지 않는다.
- 프로젝트의 API 역할별 토큰과 알림/Calendar 자격증명을 등록한다.
- 공용 n8n 시스템 DB나 다른 프로젝트 DB를 직접 수정하지 않는다.
- CallOps 원본 음성 폴더는 n8n에 마운트하지 않는다.
- CallOps 워크플로우의 성공/실패/수동 실행·pin data에 민감한 정보가 남지 않도록 설정한다.
- 프로젝트 요구 때문에 공용 전역 설정을 바꿔야 한다면 공용 운영과 조정한다.
- CallOps 비활성화가 공용 n8n·다른 자동화를 중지하지 않는지 확인한다.

#### 워크플로우 구성안

| 이름 | 입력 | 출력 |
|---|---|---|
| CallOps / 통화 분류 알림 | 미전송 분류 알림 작업 | 최소 정보·검토 링크 |
| CallOps / 결과 검토 알림 | 요약 완료와 후보 개수 | 검토 링크·확인 필요 여부 |
| CallOps / 승인 일정 등록 | 승인된 외부 작업 | Google event ID 또는 제한 오류 |
| CallOps / 운영 알림 | 실패·지연·삭제 미완료 | 상태 알림 |

여러 트리거가 같은 작업을 발견해도 CallOps API claim으로 한 전송 시도만 활성화한다. n8n 자체를 녹음 작업의 영속 큐로 사용하지 않는다.

#### 채널 선택 확인 사항

| 선택지 | 확인할 것 |
|---|---|
| Telegram 등 외부 메신저 | 외부 저장되는 최소 정보, 지정 사용자, webhook 인입 또는 polling 지원 |
| 이메일 | 전달·미리보기 봇의 링크 방문, 원문 없는 본문, 최종 승인은 VPN UI |
| 자체 호스팅 푸시 | 모바일 백그라운드 수신, VPN 필요 여부, 기기 알림 권한 |

VPN 전용 주소에 외부 서비스가 webhook을 보낼 수 있다고 가정하지 않는다. 초기 기본안은 서버에서 외부로 알림을 보내고 사용자가 VPN 내부 검토 페이지에 들어오는 방식이다. 메신저 버튼으로 즉시 결정하는 UX는 사용자 ID 검증과 인입 경로가 확인된 경우만 선택한다.

#### 해야 할 일

- [ ] 채널·채널 사용자 검증을 확정하고 P2에서 검증한 검토 화면 인증에 연결한다.
- [ ] 워크플로우를 비활성 상태로 가져와 URL·credential·목적지를 연결한다.
- [ ] 가짜 작업 한 건으로 알림·버튼·결정 이력을 시험한다.
- [ ] 링크 GET만으로 DB 상태가 바뀌지 않는지 확인한다.
- [ ] 토큰·원문·연락처가 실행 이력/에러/프록시 access log에 없는지 확인한다.
- [ ] 실패 알림만 다시 보내고 전사는 재실행하지 않는지 확인한다.
- [ ] 만료/이미 처리된 버튼에는 현재 상태만 보여준다.

#### 하면 안 되는 일 / 완료 조건

전사 원문이나 민감한 후보 전체를 n8n에 통과시키지 않는다. n8n은 승인 API를 운영자 대신 자유롭게 호출하는 권한을 갖지 않아야 한다. 가짜 데이터로 정상/중복/만료/미승인 요청을 검증하고 나서 해당 알림 워크플로우만 활성화한다.

### C5 — Calendar 연동과 삼성 캘린더 확인

기능 목적은 승인된 약속을 휴대전화에서 확인하는 것이다. 데이터 저장소는 Google의 CallOps 전용 캘린더, 사용 화면은 삼성 캘린더로 제안한다. 삼성 앱이 Google 계정 일정을 표시하도록 동기화를 켜야 한다. [삼성 공식 동기화 안내](https://www.samsung.com/ca/support/mobile-devices/how-to-sync-your-google-calendar-on-your-samsung-galaxy-device/)

#### 연결 전에 할 일

- [ ] P7 모의 Calendar 테스트를 완료한다.
- [ ] 대상 Google 계정·캘린더·OAuth 범위와 외부 전송 필드를 승인받는다.
- [ ] 제목·시작/종료·시간대의 최종 화면을 확인한다. 장소·짧은 메모는 연결 범위에 포함하기로 한 경우 확인한다.
- [ ] 참석자·첨부·반복 일정·계약 내용이 요청에서 제외되는지 확인한다.
- [ ] n8n과 별도 CallOps DB의 외부 작업 권한을 확인한다.

#### 승인 후 연결 순서

1. Google Cloud 프로젝트, Calendar API, OAuth 동의 화면·웹 클라이언트를 준비한다.
2. n8n이 표시하는 callback과 Google에 등록하는 redirect URI를 정확히 일치시킨다.
3. HTTPS 도메인을 쓰되 접근은 VPN에 제한한다. 브라우저가 VPN 내부 callback에 도달해야 한다.
4. 테스트용 localhost 예외를 사용한다면 SSH 터널·n8n 실제 callback 생성 주소를 함께 검증한다. VPN 원시 IP HTTP 주소가 허용된다고 가정하지 않는다.
5. 사용자 OAuth 승인 후 실제 부여된 권한을 확인하고 최소 범위인지 검토한다.
6. 시험 캘린더에서 가짜 일정 한 건을 승인·생성한다.
7. 서버 event ID 기록, 중복 호출 결과, 연결 일정의 양쪽 수정·삭제와 삼성 앱 표시를 확인한다.
8. 시험 통과 후 승인된 CallOps 캘린더에만 등록하도록 제한한다.

self-hosted n8n은 Custom OAuth2 설정이 필요하다. External/Testing 상태의 Calendar 권한 토큰은 7일 만료 문제가 있으므로 무기한 연결로 설명하지 않고 운영 전 게시 상태·동의·재연결 절차를 확인한다. [n8n Google OAuth 공식 안내](https://docs.n8n.io/integrations/builtin/credentials/google/oauth-single-service/)

Google의 웹 OAuth redirect 규칙은 HTTPS·허용 도메인과 정확한 URI 일치를 요구하며 localhost에 예외가 있다. 소유/사용 권한이 있는 도메인을 사용하고 VPN 접속 브라우저로 callback을 시험한다. [Google OAuth 공식 안내](https://developers.google.com/identity/protocols/oauth2/web-server)

#### 테스트 / 완료 조건

- 미승인·확인 필요·거절 후보는 생성 0건.
- 승인한 revision과 실제 Google 필드가 일치.
- 성공 후 응답 유실과 재전송에도 1개만 생성.
- 토큰 만료/철회 시 AUTH_REQUIRED로 중지하고 재인증 후 원래 작업을 이어감.
- Google에는 존재하지만 삼성에 안 보이면 계정 동기화·표시 선택부터 점검하고 재생성하지 않음.
- 삼성 앱에서 직접 편집한 Google 일정을 재분석 결과로 덮어쓰지 않음.
- 시험 일정 제거도 대상 ID를 확인한 뒤 명시적으로 처리하고 다른 일정에 손대지 않음.

### C6 — 운영 모니터링·보관·복구

보관 검증은 F08의 세 scope와 10절의 기한을 기준으로 한다. 테스트 시계로 음성만 만료된 뒤 전사 검토 가능, 전사/근거 만료 후 신규 승인 차단, 후보 만료 뒤 내부 할 일 유지, 할 일 자체 만료·명시적 연장, 통화 전체 삭제 시 연결 할 일 청소를 확인한다. 로그·승인 스냅샷·외부 전송 payload에도 삭제한 내용이 남지 않는지 확인한다.

#### 지표와 알림

| 확인 항목 | 위치 | 초기 조치 |
|---|---|---|
| 앱 응답·DB readiness | 제한 health API/Kuma | 신규 수신·작업 안전 대기 |
| GPU 마지막 응답·준비 상태 | CallOps 운영 화면 | 워커 대기, F03 실패 횟수 증가 금지 |
| 분류 대기·만료 | DB/운영 화면 | 재알림 또는 청소 |
| 단계별 실패·큐 지연 | job/attempt 목록 | 실패 단계만 재시도 |
| Calendar UNKNOWN/AUTH_REQUIRED | delivery 목록 | 조회 대조/재인증, 맹목적 재생성 금지 |
| 삭제 미완료 | 복사본 manifest | 서버/GPU별 청소 재시도 |
| 데이터·로그 크기 | 디스크 모니터링 | 알림·신규 수신 제한 |
| 백업 상태 | 운영 화면 | 현재 '미구성' 표시 |

모니터링 임계값은 초기 제안으로 여유 공간 20% 경고/10% 수신 중지, heartbeat 2분 경고를 두되 실제 부하·디스크 특성으로 조정한다. 워커 heartbeat는 살아 있어도 GPU가 준비되지 않을 수 있어 liveness와 readiness를 나눠 표시한다.

CallOps 상태는 준비된 Kuma 등 공용 도구에 프로젝트 모니터로 등록한다. n8n 자체의 장애 감지는 공용 서버 문서의 책임이며, CallOps는 n8n 중단 중 알림 대기·외부 출력 보류를 유지하는지를 검증한다.

#### 백업 보류 상태에서의 복구 구분

| 장애 | 복구 가능한 것 | 복구되지 않을 수 있는 것 |
|---|---|---|
| 앱 프로세스 재시작 | DB·파일 기반 대기/재시도 | 메모리상의 진행 상태 |
| GPU 고장 | 서버·갤럭시 원본으로 재처리 | ACK 전 유실 결과 |
| CallOps DB 유실 | Git 코드·마이그레이션으로 빈 DB 구축 | 승인·해시·삭제 이력·외부 ID |
| 공용 n8n 장애/재구축 | 인프라 복구 후 CallOps workflow·credential 재연결 | 기존 전송 상태가 불명확하면 프로젝트가 외부 결과 대조 |
| 서버 디스크 고장 | Git 구성, 남아 있는 갤럭시 원본 | 서버 음성·결과·상태 전체 |

빈 DB로 복구할 때는 녹음 자동 수집·AI claim·Calendar 전송을 꺼둔다. 먼저 Google 기존 CallOps 이벤트와 남은 파일을 대조하고 사적 제외 이력이 사라졌음을 인지한다. 갤럭시 전체 녹음을 자동 재수집하지 않는다. 사용자가 필요한 녹음만 다시 선택·분류하고 외부 중복 위험이 정리된 뒤 전송을 재개한다.

같은 디스크의 임시 덤프는 디스크 장애 백업이 아니다. 현재 백업을 요구하지 않지만 운영 DB 스키마 파괴·볼륨 초기화·검증 안 된 메이저 업그레이드를 자동 실행하지 않는다. 되돌릴 데이터 사본이 없는 변경은 복구 불가 가능성을 명시하고 진행 여부를 따로 판단한다.

#### 향후 백업을 추가할 때 구분할 항목 (현재 미실행)

- CallOps PostgreSQL과 전사 파일의 일관된 복구 지점.
- 공용 n8n 복구 이후 CallOps 워크플로우·외부 계정 연결의 재개 절차. n8n DB/키 자체의 복구는 공용 인프라 책임.
- 원본·전사·요약의 보관 기간 및 삭제 요청이 백업에서 소멸하는 시점.
- 코드/Compose의 버전과 비밀값 복구 경로.
- GPU 환경·모델 버전은 재설치로 복구.
- 다른 물리 장치/위치에서 복원 시험과 정해진 복구시간·허용 유실량.

### C7 — 갤럭시 실제 폴더 연결 (마지막)

#### 먼저 확인할 것

- [ ] 기기 모델·Android/One UI·통화 녹음 앱.
- [ ] 개인정보 없는 테스트 파일의 실제 폴더·확장자·파일명/메타데이터.
- [ ] 선택한 Android 동기화 앱의 현재 지원·설치 출처·폴더 접근 권한.
- [ ] 백그라운드/절전 중 전송, Wi-Fi/VPN/모바일 데이터 정책.
- [ ] 새 파일만 가져올 시작 시점과 기존 파일 제외 목록.
- [ ] 서버 보관과 무관하게 휴대전화 원본을 사용자가 관리한다는 점.

#### Syncthing을 선택할 때의 제한

휴대전화 Send Only + 서버 Receive Only는 서버의 로컬 변경이 휴대전화로 전파되는 것을 막는다. 그러나 휴대전화의 삭제는 서버 수신 폴더로 전달될 수 있고, 서버의 로컬 삭제는 'Revert Local Changes'로 되돌릴 수 있다. 따라서 이 설정만으로 독립 보관·영구 삭제·재수신 방지가 완성되지는 않는다. [Syncthing 폴더 유형](https://docs.syncthing.net/users/foldertypes.html)

#### 해야 할 일

1. 처음에는 실제 통화 폴더 대신 가짜 녹음 전용 폴더 한 개를 공유한다.
2. 휴대전화 Send Only, 서버 Receive Only, 지정 장치·VPN 경로를 확인한다.
3. 수신본을 별도 quarantine에 복사·해시 검증한 뒤 분류한다.
4. 사적 선택 시 서버 inbox/quarantine의 해당 복사본을 삭제하고 tombstone을 저장한다.
5. 동기화 폴더의 버전 보관·휴지통·충돌 사본에 음성이 남지 않게 정책을 확인한다.
6. 파일명 변경·재연결·앱 재시작·서버 재시작·로컬 변경 되돌리기를 테스트한다.
7. 삭제된 원본이 다시 내려오는 조건을 확인하고, 재수신 방지용 완료 파일 제외/전송 이력 방식을 확정한다.
8. 수신 제외를 신뢰할 수 없다면 실제 폴더 연결을 보류하고, 파일별 수신 확인을 가진 단방향 복사 도구로 전송 부분만 재검토한다.
9. 테스트 통과 후 신규 녹음 소수만 연결하고, 업무 분류→결과→최종 승인까지 확인한다.

DB 해시 기록은 재전사를 막지만 파일이 다시 전송되는 것 자체를 항상 막지는 못한다. 재등장한 사적 파일은 즉시 처리 제외·청소하되, 지속적인 사본 부재가 보장되지 않으면 '완전 삭제 유지'라고 표시하지 않는다. 수신 자체를 멈추고 전송 정책을 수정한다.

처리 완료 파일을 제외할 때 경로만으로 콘텐츠가 영구 동일하다고 판단하지 않는다. 원본 파일명 재사용·이름 변경·수신 제외 목록 소실을 시험한다. tombstone은 최소 90일 제안이며 재수신 가능성이 남아 있으면 무조건 만료시키지 않는다. 장기 운영 전 최소 식별 기록을 유지하는 정책과 사용자가 재처리를 요청하는 해제 절차를 승인받는다.

#### 하면 안 되는 일

- 기존 전체 통화 녹음을 첫 연결에서 한꺼번에 가져오기.
- 양방향 기본값 상태로 실제 녹음 폴더 연결.
- 서버 공간 정리를 위해 휴대전화 파일 삭제 요청 전송.
- '서버 음성 삭제' 확인 없이 분류 DB 행만 삭제하고 끝내기.
- 격리 폴더를 GPU 장치와 공유.
- 삭제 후 복원될 수 있는 버전 사본을 누락한 채 완료 표시.

#### 완료 조건

가짜 파일로 양쪽 삭제 방향·오프라인·중복·재등장·사적 미처리를 검증한다. 승인된 전송/보관 정책대로 동작할 때만 신규 실제 통화 소수로 운영을 시작한다. 개인정보·상대방 고지·계약상 의무의 적용 여부는 사용자가 확인할 수 있게 운영 안내에 남기며 시스템이 적법성을 자동 판단하지 않는다.

### 프로젝트 운영자가 정기적으로 할 일

| 시점 | 해야 할 일 | 하면 안 되는 일 |
|---|---|---|
| 매일/오류 알림 | 분류 대기·실패·삭제 미완료·GPU·외부 작업 확인 | 실패 목록 전체를 무조건 재실행 |
| 매주 | 디스크·로그·비밀값 노출·장기 미검토 점검 | 운영 데이터 디렉터리 전체를 Git에 추가 |
| 배포 전 | 승인 버전·DB 변경 영향·활성 작업 확인 | 변경 확인 없이 최신 이미지로 전체 업데이트 |
| 배포 후 | readiness·가짜 작업·기존 앱 응답 확인 | 정상 판정 전에 갤럭시 전체 수집 활성화 |
| 토큰 유출 | 관련 credential 폐기·재발급·로그 확인 | 원문 토큰을 이슈/채팅에 게시 |
| 삭제 장애 | 복사본별 실패 원인 확인·대기 표시 | GPU가 꺼져 있는데 삭제 완료로 표시 |
| DB 유실 | 자동 출력 중지·기존 Calendar 대조·선택 재수집 | 갤럭시 원본만 있으면 모든 상태가 복원된다고 판단 |

### 프로젝트 배포·연동 완료 확인표

| 단계 | 현재 상태 | 완료 증거 |
