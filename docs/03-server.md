# 3. 서버 — 프로젝트와 독립적인 공용 n8n 설치·운영

작성일: 2026-09-19 · 상태: 검토용 초안 · 서버 설치/설정 변경 미실행

연결 문서: [이 프로젝트](01-project.md) · [데스크톱](02-desktop.md)

여기서 “서버”는 공용 n8n 인프라의 책임 범위를 뜻한다. 이 문서는 CallOps가 없어도 필요한 n8n 설치·인증·저장소·접근 경로·업데이트·장애 대응만 다룬다. CallOps 앱과 DB가 같은 Ubuntu 장비에서 실행되더라도 그 개발·배포·운영은 프로젝트 문서의 책임이다.

## 1. 역할 경계와 산출물

| 공용 n8n 서버에서 담당 | 각 프로젝트에서 담당 |
|---|---|
| n8n 인스턴스 설치·버전 관리 | 프로젝트 코드·배포·자체 DB |
| n8n 시스템 DB와 영속 볼륨 | 프로젝트 데이터 모델·파일 저장소 |
| n8n 관리 계정·접근 권한 | 업무별 승인 규칙·사용자 화면 |
| n8n용 주소·HTTPS·VPN 접근 경로 | 프로젝트 API·네트워크·워커 연결 |
| n8n 암호화 키·자격증명 저장 기반 | 해당 프로젝트의 외부 계정 연결·토큰 범위 |
| 공통 실행 이력·자원 관리 기준 | 워크플로우 작성·가져오기·시험·활성화 |
| n8n 상태 확인·재시작·업데이트·복구 | 업무 처리 오류·중복·재시도·데이터 삭제 |

공용 n8n이 외부 서비스 자격증명을 저장하고 워크플로우를 실행하더라도, 어떤 계정에 연결하고 어떤 정보를 전송할지는 프로젝트가 결정한다. Google Calendar 연결, CallOps 알림, 통화 처리 테스트는 [프로젝트 문서의 배포·연동 절차](01-project.md#12-callops-배포연동운영--프로젝트-책임)에서 다룬다.

공용 인프라의 산출물은 다음과 같다.

- n8n 및 그 시스템 DB의 배포 설정과 버전 기록.
- n8n 전용 데이터 경로·계정·접속 주소.
- 암호화 키와 관리자 인증의 보관·교체 절차.
- 자원·실행 이력·업데이트·장애 대응 기준.
- 프로젝트에 전달할 n8n 접속 주소, 지원 버전, 인증·연결 방법.

실제 공용 n8n Compose와 비밀값은 이 CallOps 저장소 밖의 공용 인프라 디렉터리에서 관리한다. 이 파일은 전체 준비를 위한 안내서이며 공용 n8n을 CallOps 소유로 만들지 않는다.

## 2. 현재 확인된 환경

사용자가 제공한 출력 기준이다. 이번 문서 수정에서 원격 서버를 재조회하지 않았다.

| 항목 | 확인된 내용 |
|---|---|
| OS | Ubuntu 24.04.4 LTS |
| Docker / Compose | 29.7.2 / 5.4.0 |
| 메모리 | 당시 총 약 25GiB, available 약 22GiB |
| 디스크 | 루트 ext4 약 457GiB, 당시 available 약 415GiB |
| 기존 서비스 | chanvoca, finel, Uptime Kuma |
| 기존 DB | chanvoca PostgreSQL 17, finel PostgreSQL 18 컨테이너 |
| psql | 클라이언트 18.6; 호스트 DB 서버 설치를 의미하지 않음 |
| n8n | 미설치 |
| VPN | 접속 가능; 이름·주소·DNS·ACL은 미확인 |
| 암호화/별도 백업 | 추가 구축 보류 |

기존 프로젝트 DB를 n8n 시스템 DB로 임의 재사용하지 않는다. n8n 전용 PostgreSQL·역할·볼륨을 별도로 준비하는 기본안으로 검토한다. 기존 공용 DB 활용을 원하면 먼저 운영·권한·변경 영향을 확인한다.

## 3. S0 — n8n 설치 전 조사

### 해야 할 일

- [ ] 기존 컨테이너·Compose 프로젝트·볼륨·네트워크를 기록한다.
- [ ] n8n용 포트와 공용 인프라 설치 경로를 정한다.
- [ ] n8n 시스템 DB와 데이터 볼륨 위치·소유 계정을 정한다.
- [ ] 관리자가 VPN으로 접근할 주소와 HTTPS 구성을 확인한다.
- [ ] 시스템 시간 동기화와 재부팅 후 마운트를 확인한다.
- [ ] 기존 Uptime Kuma에서 n8n 상태를 확인할 경로를 정한다.

### 읽기 전용 점검 예시

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
docker compose ls
docker network ls
docker volume ls
ss -lnt
timedatectl status
df -hT /
free -h
```

환경변수를 포함할 수 있는 전체 inspect/config 출력은 공유하지 않는다. 포트·마운트 등 필요한 정보만 확인한다.

### 하면 안 되는 일 / 완료 조건

기존 서비스의 볼륨 삭제·DB 업그레이드·전체 Docker 정리를 하지 않는다. n8n 추가에 필요한 경로·포트·자원과 기존 서비스 영향 범위가 확인되면 완료다.

## 4. S1 — 공용 n8n과 시스템 DB 설치

### 해야 할 일

- [ ] 공용 인프라 디렉터리에서 별도 Compose 프로젝트를 구성한다.
- [ ] 검토한 n8n·PostgreSQL 버전을 고정한다.
- [ ] n8n 시스템 DB·계정·영속 볼륨을 만든다.
- [ ] DB 포트를 호스트/인터넷에 공개하지 않는다.
- [ ] 재배포와 재부팅 후 같은 볼륨을 사용하도록 한다.
- [ ] n8n·DB readiness와 재시작 정책을 구성한다.
- [ ] 로그 회전·디스크 사용량·자원 제한을 정한다.

### 하면 안 되는 일

- 각 프로젝트마다 이 공용 인스턴스를 중복 설치.
- 프로젝트 데이터 테이블을 n8n 시스템 DB에 추가.
- 자동화 편의를 위해 Docker socket·호스트 전체 경로를 마운트.
- 실제 업무 워크플로우를 설치 확인용으로 활성화.

### 테스트 / 완료 조건

외부 호출 없는 Manual Trigger와 가짜 값 변환으로 실행을 확인한다. n8n 재시작 뒤 설정·가짜 워크플로우가 유지되고 기존 서비스가 정상이어야 한다.

## 5. S2 — 관리 인증·접근 경로·비밀값

### 해야 할 일

- [ ] 관리자 계정과 로그인 방식을 구성한다.
- [ ] VPN 접근과 n8n 로그인을 각각 검증한다.
- [ ] n8n 주소·HTTPS·프록시·callback 기본 주소를 일관되게 설정한다.
- [ ] 프로젝트 연결에 필요한 네트워크는 지정 목적지만 허용한다.
- [ ] `N8N_ENCRYPTION_KEY`를 생성하고 권한을 제한해 보관한다.
- [ ] 키를 비밀번호 관리자 등 별도 위치에도 기록한다.
- [ ] DB 비밀번호·키·외부 credential이 Git/로그에 남지 않게 한다.
- [ ] 사용 중인 에디션에서 사용자·프로젝트·credential 권한 기능을 확인한다.

태그와 워크플로우 이름은 정리 수단이며 보안 격리로 설명하지 않는다. 공용 n8n 관리자 권한의 영향 범위를 기록한다. 외부 OAuth 공급자 등록과 권한 동의는 각 프로젝트에서 별도로 수행한다.

### 하면 안 되는 일 / 완료 조건

재배포마다 암호화 키를 새로 만들거나 프로젝트 개발자에게 관리자 권한을 자동 부여하지 않는다. 비 VPN 접근은 차단되고 승인된 관리자 로그인·재시작 후 credential 사용이 정상이어야 한다. Docker 바인딩과 실제 외부 접근도 함께 확인한다.

## 6. S3 — 공통 실행 이력·프로젝트 인계 기준

### 해야 할 일

- [ ] 성공·실패·수동 실행·진행 저장·pin data의 보관 동작을 설치 버전에서 확인한다.
- [ ] 기본 보관 기간·실행 횟수·자원 상한을 정한다.
- [ ] 프로젝트별 민감도에 맞춰 더 엄격한 저장 정책을 적용할 방법을 안내한다.
- [ ] 프로젝트가 사용할 n8n 주소·버전·인증·네트워크 연결 방법을 전달한다.
- [ ] workflow export에 credential 비밀값·실행 데이터가 포함되지 않는지 확인한다.
- [ ] 새 워크플로우는 비활성 상태에서 인계하고 프로젝트 담당자가 시험 후 활성화하도록 한다.

### 하면 안 되는 일

- 특정 프로젝트 때문에 전체 실행 이력을 확인 없이 삭제하거나 전역 정책 변경.
- 프로젝트의 업무 승인 상태를 공용 인프라 설정으로 결정.
- 모든 프로젝트의 외부 계정에 일괄 OAuth 승인.
- 다른 자동화의 credential을 편의상 공유.

### 테스트 / 완료 조건

가짜 민감 문자열로 입력·실행 DB·오류·컨테이너 로그 보존을 확인한다. 보관 정책과 프로젝트별 적용 범위를 설명할 수 있어야 한다. 업무 데이터나 실제 API 호출 없이 공용 기반 준비를 완료한다.

## 7. S4 — n8n 상태 확인·업데이트·장애 대응

### 정기적으로 해야 할 일

| 시점 | 확인/조치 | 금지 사항 |
|---|---|---|
| 매일/오류 시 | n8n 응답, DB readiness, 디스크·로그, 실패 실행 | 실패한 모든 프로젝트 작업 일괄 재실행 |
| 매주 | 사용량·실행 이력 증가·인증/버전 확인 | 워크플로우별 정책 무시하고 전체 이력 삭제 |
| 업데이트 전 | 영향 프로젝트와 실행 중 작업 확인, 버전·DB 변경 검토 | 무조건 latest로 자동 갱신 |
| 업데이트 후 | 가짜 워크플로우·로그인·credential·기존 기능 확인 | 검증 전 전체 워크플로우 활성화 |
| 장애 시 | 서비스·DB·네트워크 원인 구분, 업무 담당자에 영향 전달 | 불명확한 외부 실행 결과를 성공/실패로 단정 |
| 키/토큰 유출 | 영향 credential 폐기·재발급·로그 점검 | 비밀값을 이슈나 채팅에 붙여넣기 |

n8n 자체 장애 감지는 가능하면 기존 Kuma에서 확인한다. 외부 경보 채널 연결이 필요하면 공용 운영 용도로 결정한다. 녹음 작업 수, GPU heartbeat, Calendar 반영 상태 같은 업무 지표는 프로젝트 책임이다.

### 백업 보류 상태의 복구

현재 별도 백업 구축은 보류한다. 재시작과 DB 유실을 구분하고 데이터 손실을 없었던 것으로 처리하지 않는다.

| 상황 | 복구 범위 |
|---|---|
| n8n 프로세스 재시작 | 기존 DB·볼륨으로 복귀 |
| n8n DB 유실 | 배포 설정으로 재설치, 정제한 워크플로우를 각 프로젝트에서 다시 가져오기; credential·실행 상태 유실 가능 |
| 암호화 키 유실 | 기존 credential 복호화가 안 될 수 있어 해당 외부 계정을 재연결 |
| 디스크 고장 | 별도 데이터 사본이 없으면 설정만 재현 가능, 실행 DB 복구 보장 없음 |

복구 후 워크플로우는 비활성으로 두고 각 프로젝트 담당자가 외부 부작용·중복 위험을 점검한 뒤 재개한다. 같은 디스크의 덤프는 디스크 장애 백업이 아니다. 향후 백업을 도입하면 n8n DB, 필요한 영속 데이터, 암호화 키, 배포 버전을 함께 복구할 수 있는지 시험한다.

### 완료 조건

재시작·DB 일시 중단·n8n 중단·디스크 경고 시험에서 상태를 식별하고 복귀 절차를 확인한다. 데이터 사본 없는 파괴적 DB 변경이나 메이저 업그레이드는 자동 수행하지 않는다.

## 8. 공용 n8n 준비 완료 체크리스트

- [ ] S0: 기존 서비스 영향·경로·포트 확인.
- [ ] S1: n8n·시스템 DB 설치 및 영속성 확인.
- [ ] S2: 관리자 인증·VPN/HTTPS·암호화 키 보관 확인.
- [ ] S3: 공통 이력 정책·가짜 워크플로우 시험·프로젝트 인계 정보 작성.
- [ ] S4: 상태 확인·업데이트·복구 절차 확인.

공용 n8n의 완료 기준은 특정 프로젝트의 존재와 관계없이 안전하게 워크플로우를 실행할 기반이 준비된 것이다. CallOps 알림·Calendar 연결과 그 시험은 프로젝트 문서로 이어진다.
