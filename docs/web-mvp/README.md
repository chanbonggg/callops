# CallOps 웹 MVP 범위와 검증 기준

2026-11-13 문서 정리. 현재 상태와 다음 작업은 [전체 진행 체크리스트](../progress-checklist.md)에서만 관리한다. 아래 1~7 단계는 기존 주차 계획의 검증 기준이며 달력상 일정이 아니다. 검증 기록은 당시 결과이며 현재 기능 전체의 완료를 뜻하지 않는다. 제품 계약은 [프로젝트 계획](../01-project.md)을 참조하고, RAG·웹 업무 관리·Calendar 역방향 반영처럼 범위가 추가된 부분은 구현 시 해당 계약도 함께 갱신한다.

## 개발 범위

실제 사용자의 업무는 **거래처 영업 및 일정 생성**이다. 상담·방문 약속, 자료 전달 기한, 후속 연락 시점과 일정 정정·취소를 대표 사례로 사용한다. 통화 당시 합의와 현재 일정은 각각의 출처를 확인해 표시한다.

| 우선순위 | 이번에 만들 것 | 최종 시연 |
| --- | --- | --- |
| 필수 | 갤럭시 신규 녹음 자동 전송, 업무 지정, 로컬 전사·요약, 통화 RAG와 근거 구간 재생 | 녹음 1건이 웹에 들어오고, 사용자 질문에서 답변의 근거 원음을 열 수 있다. |
| 선택 · 이번 구현 목표 | 일정·할 일 후보 확인·수정·승인, 웹에서 직접 입력·관리, Google Calendar 1개와 연결 일정 양방향 동기화 | 후보 승인 후 일정 1건을 등록한다. Google에서 시간을 바꾸면 웹이 현재 일정과 당시 합의를 구분해 표시한다. |
| 후속 | Flutter 앱, 이메일 연동 | 이번 시제품은 PC·모바일 브라우저에서 사용한다. |

업무 지정과 일정 등록 승인은 별개다. 미분류·사적 통화는 AI 호출 0회, 사적 통화 삭제는 관리 사본에만 적용한다. 테스트 기본 경로는 합성 데이터·임시 PostgreSQL·모의 외부 어댑터다. 실제 기기·홈서버·GPU 환경 변경·OAuth는 연결 범위를 확인한 뒤 진행한다. [하네스와 승인 범위](../harness.md)

## 웹 앱의 기능 모듈

웹 앱은 Starlette로 구성하고 Uvicorn에서 한 배포 단위로 실행한다. `auth`는 사용자·워커 인증, `calls`는 수집·분류·목록·상세, `processing`은 작업 큐와 결과 검증, `search`는 전사 검색, `schedule`은 일정 후보 검토와 승인 기록을 맡는다. 데스크톱 AI 워커는 기존 서버 API로 연결한다. [저장소 구성](../01-project.md#3-소유권과-저장소-구성)

## 1단계 · 자동 수집의 입력과 완료 조건


**종료 목표** · WAV·M4A·MP3·AMR의 지원 목표와 검증 범위를 정하고, 갤럭시 테스트 녹음 한 건을 완전하게 수신·분류한다. RAG 개발에 사용할 첫 평가 세트를 준비한다.

<a id="week-01-작업"></a>

### 작업

- **완료:** 기존 `scripts/manage.py ingest` 경로에서 완료·해시 검증, 격리 복사와 분류를 처리한다. PCM WAV와 압축 음성의 허용 컨테이너·코덱을 검사한다.
- **당시 완료 기록:** 업무 승인 전에 상대 이름과 확인한 통화 시각을 입력하고 상대·날짜로 검색한다. 시각은 한국 시간으로 입력하고 DB에는 시간대가 있는 값으로 저장한다. 사적·만료 정리 시 통화 정보도 지운다.
- 실제 업무 음성 없이 갤럭시에서 가상 대화를 녹음한다. 파일 형식·길이, 파일명에서 확인 가능한 정보, 통화 시각과 상대 식별의 출처를 기록한다. 자동으로 판단할 수 없는 값은 웹에서 입력·보정하도록 정한다.
- 기획서의 FolderSync·SFTP를 테스트 폴더 하나로 검토한다. 휴대전화 → 서버 단방향, 신규 파일만 대상으로 설정한다. 기기 연결은 범위를 확인한 뒤 실행한다.
- 중단 파일과 완료 파일을 구분할 수 있는 신호를 정하고 확인한다. 수신 도구의 완료 신호나 검증한 임시 파일 → 최종 파일 전환을 사용한다. 완료가 확인된 파일의 해시만 기존 수집 API에 전달한다.
- WAV·M4A·MP3·AMR을 공통 수집 경로로 검증한다. 수신 시 실제 컨테이너·코덱과 크기·길이·채널 수 및 손상을 검사하고, 업무 승인 후 워커가 원본을 받는다. 갤럭시 샘플은 첫 실제 입력의 확인에 사용한다.
- 형식별 합성 샘플로 수신·분류, 확장자와 내용 불일치, 손상·부분 파일, 중복·삭제를 시험한다. 정상 형식은 실제 코덱과 실행 환경을 기록하고, 승인 후 전사까지 통과한 조합을 지원 완료로 표시한다.
- **당시 완료 기록:** [가상 전사 10건과 개발 질문 20개](../../tests/fixtures/rag-development.json)를 만든다. 질문별 상대·기간, 기대 답변, 근거 ID·타임스탬프, 답변 보류 여부를 기록한다. [질문 유형 배분](#week-02-평가-세트-확정)

## 2단계 · Whisper GPU 전사와 서버 수락


**종료 목표** · 업무로 지정한 가상 녹음 한 건을 실제 GPU에서 전사하고, 서버가 구간 ID·시간·텍스트를 검증해 수락한다. 평가 세트 20건·40문항을 확정한다.

GPU 데스크톱이 준비될 때까지 실제 전사·워커 시험은 대기한다. 현재는 [개발용 가상 전사](../../tests/fixtures/rag-development.json)로 서버 계약과 후속 웹 기능을 먼저 구현한다. 아래의 GPU 완료 항목은 실제 장비에서 검증한 뒤 체크한다.

<a id="week-02-작업"></a>

### 작업

- [전사 실행 안내](../../ai-worker/README.md#전사-실행--wsl-데스크톱)의 기존 환경에서 새 `app.transcriber`를 실행한다. 모델·연산 설정, 음성 길이, 처리시간, 구간 범위와 주요 날짜·시각 오류를 기록한다.
- [형식별 검증표](#week-01-형식별-검증표)에 따라 WAV·M4A·MP3·AMR 샘플을 실제 디코딩·전사 경로로 시험한다. 수신 때 검증한 길이와 실제 전사 타임스탬프를 대조한다. 호환 재생의 시간 구간은 3단계에서 확인한다.
- 전사 결과에 작업·시도·입력 버전과 결과 스키마를 묶는다. 서버 수락 경로에서 구간 ID, 음성 범위 내 시작·끝, 빈 전사의 경고, 현재 임대·기한·입력 일치 여부를 검증한다.
- **당시 완료 기록:** 합성 결과로 작업·시도·입력 해시·버전을 검증하고 구간 전사를 저장·조회한다. 실제 모델 출력 수락은 별도 검증한다.
- 기존 큐 API에 실제 워커 한 개를 연결한다. 승인 작업 임대 → 입력 조회 및 해시 확인 → 실행 시작·heartbeat → 전사 → 결과 준비·업로드 → 서버 ACK → 로컬 사본 청소 순으로 시험한다.
- 전사 성공 결과는 서버에서 다시 조회할 수 있게 저장한다. 워커 오프라인, 연산 상한 초과, 만료 임대, 저장 직후 ACK 유실, 취소 후 정리를 재현한다. 가짜 워커 회귀도 실행한다.
- 최종 평가용 가상 전사 10건·질문 20개를 작성해 개발용과 구분한다. 최종용 질문·정답은 튜닝에 사용하지 않는다.

## 3단계 · Qwen 요약과 통화 상세 웹


**종료 목표** · 승인된 녹음의 수신부터 전사·요약 표시까지 브라우저에서 확인한다. 이후 RAG와 후보 검토가 사용할 통화·전사 연결을 확정한다.

### 작업

### 작업

- 승인된 시험 계정과 전용 Google Calendar 한 개를 사용한다. 전송 항목은 일정 제목·시작·종료 등 등록에 필요한 최소 정보로 한정한다. 원음과 전체 전사는 CallOps에 보관한다.
- CallOps에서 승인한 일정의 생성, 웹에서 확인한 일정 수정·삭제의 외부 반영을 시험한다. 응답이 유실된 생성은 기존 이벤트를 확인한 뒤 재시도한다.
- Google에서 연결 일정의 변경분을 가져와 현재 일정을 갱신한다. Google 삭제는 웹에 삭제 상태로 표시하고 자동 재생성을 막는다. 동시 수정은 충돌로 표시해 사용자가 선택할 수 있게 한다.
- 일정 상세에 **통화 당시 합의와 현재 일정**을 구분한다. 원래 전사 근거는 유지한다. 시제품의 역방향 동기화 완료 기준은 CallOps와 연결된 일정의 수정·삭제 반영이다.
- 갤럭시 테스트 폴더에서 새 녹음 전송부터 업무 지정·AI 처리·근거 답변까지 통합 시험한다. 전송 중단·서버 재시작·사적 분류 후 원본 보존도 확인한다.
- 사용자 과제를 진행한다. ① 과거 합의의 근거 찾기 ② 후보를 수정해 등록하기 ③ Google에서 변경한 일정 확인하기. 기존 방식과 비슷한 난이도의 과제로 완료 여부, 시간, 잘못 선택하거나 수정한 횟수, 막힌 화면을 기록한다.

<a id="week-06-통과-기준"></a>

### 통과 기준

| 시험 | 기대 결과 |
| --- | --- |
| 승인 → Google 생성 → 동일 요청 재시도 | 연결된 이벤트는 한 건이다. |
| Google에서 오후 2시를 오후 3시로 수정 | 웹은 현재 오후 3시를 표시하고 통화의 오후 2시 근거를 보존한다. |
| 웹·Google 양쪽의 수정 및 삭제 | 각 방향의 반영 결과를 기록한다. 동시 수정은 확인이 필요하고 삭제된 일정을 자동 재생성하지 않는다. |
| 만료 인증 또는 일시 장애 | 동기화 실패·재연결 상태를 보여주고 사용자 승인 상태는 보존한다. |
| 사용자 과제 | 실제 사용자 1인의 결과는 사례 평가로 기록한다. 추가 참여자가 있으면 같은 과제를 별도 기록한다. |

<a id="week-07"></a>

## 7단계 · 통합 검증과 최종 시연


**종료 목표** · 가상 데이터로 전체 흐름을 다시 실행할 수 있고, 필수·선택 기능별 완료 증거와 남은 제약을 설명할 수 있다.

<a id="week-07-작업"></a>

### 작업

- 통합 시험과 사용자 과제에서 발생한 오류를 재현한다. 접근 노출·삭제 누락·중복 등록을 우선 수정하고 같은 조건으로 다시 시험한다.
- 정상 시연에 사용할 가상 음성과 질문, 예상 답변·근거, 시험 일정을 준비한다. 실행 절차와 필요한 테스트 설정을 기록한다.
- 하네스·P1~P3 PostgreSQL·전사 모의 테스트를 재실행한다. 새 수집·실제 워커·RAG·업무 관리·Calendar 동작은 해당 주차의 완료 기준으로 각각 재검증한다.
- [형식별 검증표](#week-01-형식별-검증표)의 지원 완료 조합을 수신부터 전사·재생·삭제까지 다시 확인한다. 결과 보고서에 검증한 컨테이너·코덱과 실제 장비 조건을 적는다.
- 평가 결과를 정리한다. 최종 RAG 정답·보류, 근거 검색, 실제 전사 오류와 후보 추출, 사용자 과제 소요 시간·수정 횟수를 포함한다. 참여자 수와 평가 조건을 함께 적는다.
- 결과 보고서에 구현됨, 모의 검증됨, 실제 장비·서비스에서 검증됨을 구분한다. 연결이나 환경 제약으로 실패한 부분은 재현 조건과 남은 작업을 남긴다.

<a id="week-07-시연-순서"></a>

### 시연 순서

1. **자동 수집과 분류** · 갤럭시에서 가상 녹음이 들어오면 업무로 지정한다. 전사·요약과 원음을 확인한다. 별도의 사적 가상 녹음은 서버 사본만 청소되는 것을 보여준다.
2. **근거 기반 답변** · 상대·기간을 지정해 연락 시점을 질문한다. 답변에서 해당 전사와 음성 구간을 연다. 정보가 없는 질문은 보류되는 것을 확인한다.
3. **후속 업무와 현재 일정** · 후보를 보정해 승인하고, Google에서 일정 한 건을 확인한다. Google에서 시간을 변경하면 웹의 현재 일정이 바뀌고 원래 합의 근거는 남는다. 직접 입력한 할 일을 완료한다.

<a id="week-07-제출-체크"></a>

### 제출 체크

- PC·모바일 웹에서 필수 흐름을 재현하는 시연 영상 또는 화면 기록
- 20건·40문항 평가 자료와 개발용·최종용 결과의 구분
- 일정 승인·중복 방지·역방향 수정 및 삭제 검증 기록
- 실행·재현 안내와 기능별 미검증 범위

실제 Calendar 시험이 막히면 통과한 모의 경로를 시연하고, 실패 사유와 검증되지 않은 방향을 명시한다. 핵심 시연은 검증된 녹음 수집·전사·요약·질의응답을 기준으로 구성한다.
