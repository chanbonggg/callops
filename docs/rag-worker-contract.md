# RAG 서버·워커 연동 계약

이 문서는 구현 기준이다. 배포와 실제 질문 화면 검증 결과는 [진행 체크리스트](progress-checklist.md)에 기록한다. 데스크톱 엔진의 JSON 스키마와 모델은 [데스크톱 실행 계약](../ai-worker/README.md#질문-모델-워커-실행)을 따른다.

## 작업과 소유권

| 단계 | 서버가 고정할 입력과 소유권 | 수락 시 동작 |
| --- | --- | --- |
| `RAG_EMBED` · 인덱싱 | 같은 업무 전사 artifact의 버전·해시와 순서가 고정된 검색 조각 최대 16개. STT 성공 후 현재 전사를 인덱싱한다. | 각 벡터를 같은 순서의 조각에 연결한다. 동일 전사 버전·조각 규칙 버전·모델 digest·조각 번호는 한 번만 저장한다. 해당 버전의 전체 조각이 준비되면 검색에 포함한다. |
| `RAG_EMBED` · 질문 | 로그인 사용자의 질문 요청 ID·소유자와 질문 문자열 한 개. 조건에 맞는 전사의 인덱스가 준비되면 생성한다. | 질문 벡터로 현재 인덱스에서 검색하고, 근거가 있으면 같은 질문의 `RAG_ANSWER`를 한 번 생성한다. |
| `RAG_ANSWER` | 질문 요청과 검색 조각 최대 5개에서 중복을 제거한 발화 최대 10개. 요청 안의 인용 ID를 통화·전사 artifact ID/버전/해시·구간 ID에 고정한다. | 답변 또는 보류 사유를 질문에 연결한다. 사용자에게 표시할 링크는 서버가 고정된 ID에서 생성한다. |

새 조각 규칙 버전 `1`은 D4의 폭 2 슬라이딩 창을 사용한다. 공백을 제거했을 때 빈 발화는 제외한다. 원본 순서대로 남은 발화에서 `(i, i+1)`을 한 칸씩 밀어 만들고, 발화가 하나뿐일 때만 단일 조각을 만든다. 남은 발화가 없으면 조각은 0개다. 한 조각의 발화는 공백 하나로 이어 붙인다. 이 버전은 기존 어휘 검색의 글자 수·시간 기반 창과 별도로 관리한다. 엔진 한도를 넘는 조각은 인덱싱 실패로 표시한다.

검색은 업무 승인, 최신 전사, 보관 기한, 거래처·한국 날짜를 먼저 적용한 뒤 조각 규칙 버전 1과 같은 BGE-M3 digest의 `vector(1024)`를 코사인 거리로 정렬한다. 거리 동률에는 조각 ID 순서를 적용한다. 조건에 맞는 전사나 검색 조각이 없으면 보류한다. 대상 전사 중 인덱싱이 끝나지 않은 버전이 있으면 질문을 인덱스 준비 상태에 두고 준비되면 같은 요청을 진행한다. 대상 인덱싱이 실패하면 질문에 실패를 표시한다.

기존 STT·ANALYSIS의 통화별 고유 제약과 artifact 참조는 유지한다. RAG 작업에는 전사 인덱싱과 질문 요청을 각각 명시적으로 소유자로 둔다. 여러 통화의 근거를 단일 녹음 ID로 대표하지 않는다. PostgreSQL에서 질문당 임베딩과 답변을 각각 하나로 제한하고, 작업 소유권, 단계 전이, 결과 수락, 다음 단계 생성은 트랜잭션과 제약으로 보장한다.

## 워커 API

VPN·HTTPS의 기존 `/worker` 경로와 인증을 사용한다. `GET /worker/readiness`는 기존 `real_results` 불리언을 항상 반환한다. 실제 결과를 제출할 수 있고 서버에서 RAG가 활성화된 등록 워커에는 정수 필드 `"rag_contract_version": 1`을 추가한다. 새 워커는 `real_results`가 `true`이고 지원 버전이 일치할 때 `POST /worker/claim`에 JSON `{"rag_contract_version":1}`을 보낸다. claim 라우트는 본문 없음과 JSON 객체를 모두 처리한다. 본문 없음, 버전 필드 없음, 지원하지 않는 정수 버전은 기존 STT·ANALYSIS 할당 규칙을 따른다. 잘못된 JSON이나 잘못된 타입은 `400`으로 거부한다. 서버는 실제 결과 워커 등록·RAG 활성화·버전 일치 조건을 claim에서도 검증한다. 같은 워커에는 활성 작업과 종료·청소 미확인 작업을 합쳐 하나만 허용한다.

- RAG claim은 `job_id`, `stage`, `lease_token`, `copy_key`, `lease_until`, `preparation_deadline`, `input_snapshot_id`(UUID), `input_snapshot_version`(양의 정수), `input_sha256`(소문자 64자리 hex), `schema_version: 1`을 반환한다. 스냅샷은 서버가 고정한 엔진 입력 JSON의 정확한 바이트를 뜻한다.
- `GET /worker/jobs/{id}/input`은 현재 임대로 내려받는 최대 80KiB의 UTF-8 JSON이다. 워커는 `X-Input-Snapshot-ID`, `X-Input-Snapshot-Version` 및 본문 SHA-256을 claim과 대조한 뒤 엔진 입력 파일을 확정한다. 재시도에서도 바이트와 스냅샷을 유지한다.
- `heartbeat → start → prepared → result`와 `status`·`failed`·`cleanup`은 기존 경로와 요청 키 규칙을 사용한다. `result`는 최대 1MiB의 JSON 객체이며 `schema_version: 1`, `job_id`, `attempt_id`(claim의 `copy_key`), `input_snapshot_id`, `input_snapshot_version`, `input_sha256`, `output`을 담는다. `output`은 엔진이 반환한 JSON 그대로다. 워커는 완성된 본문 바이트를 spool에 저장한 다음 그 크기·SHA-256과 요청 UUID를 `prepared`에 제출한다.
- 서버는 작업과 입력 바인딩을 검증한다. 임베딩은 고정 모델 digest, 입력 개수·순서, 각 벡터의 차원·유한성·단위 길이(오차 최대 `1e-5`)를 확인한다. 답변은 고정 모델 digest와 프롬프트 버전, 답변·보류 형식, 요청에 있는 중복 없는 인용 ID를 확인한다. 답변에는 최소 한 개의 인용이 필요하다. 보류는 `segment_ids: []`도 허용한다. 모델이 생성한 보류에도 모델명·digest·프롬프트 버전을 확인한다. 서버가 근거 없음으로 판단하면 워커 작업을 만들지 않고 보류한다.
- RAG 성공 응답은 `{"accepted":true,"result_id":"<uuid>"}`다. `status`와 동일 결과의 재전송에서도 같은 ID를 준다. 워커는 RAG에는 `result_id`, STT·ANALYSIS에는 기존 `artifact_id`를 확인하고 사본을 청소한다. 같은 요청 키의 다른 본문, 구 임대와 늦은 최초 결과는 거부한다.

## 처리 기한과 작업 순서

RAG의 초기 단계 상한은 준비 60초, 실행 120초, 업로드 120초다. 질문 처리 기한은 접수 후 15분이며 인덱스·워커 대기도 포함한다. heartbeat 간격은 30초, 임대 기간은 5분이다. heartbeat로 단계 기한이나 질문 처리 기한을 연장하지 않는다. 단계 기한은 연결된 전사의 가장 이른 만료와 질문 처리 기한 안으로 제한한다.

워크로드는 작업 경계에서만 순서를 정한다. 실행 중인 STT·ANALYSIS·RAG를 선점하지 않는다. 같은 워커에서 준비된 질문 임베딩·답변을 먼저 배정하되, 질문 작업을 연속 두 번 배정했고 준비된 배경 작업도 있으면 다음 배정은 배경 작업에서 한다. 같은 우선순위에서는 준비 시각·작업 ID 순서로 고른다. 배경 작업은 STT·ANALYSIS와 전사 인덱싱이다. 전사 인덱싱은 16개와 80KiB 한도 내에서 가능한 한 채워 배치하고, 배치별 Ollama 시작 비용을 실측한다. 질문이 인덱스나 워커를 기다리다 처리 기한에 도달하면 대기 중 기한 초과로 표시하고 새 claim을 차단한다. 실행 중 기한에 도달하면 취소·청소하고 처리 중 기한 초과로 표시한다.

RAG 단계별 자동 실행은 최초 포함 최대 두 시도다. 새 임대를 만들 때 시도 횟수를 증가시키며, 같은 임대에서 상태 조회나 결과를 재전송하는 것은 같은 시도다. 입력 만료·권한 철회·입력 불일치·결과 스키마 오류·`RAG_CONTEXT_TOO_LONG`은 자동 재시도하지 않는다. ACK가 유실되면 새 연산 전에 같은 요청 키로 상태를 조회한다. 미수락 결과는 유효한 임대·전송 기한 안에서 같은 바이트만 보내고, 기존 수락 ACK는 원문 없이 반환한다.

## 답변 한도와 보관

서버는 답변 입력 JSON의 80KiB 상한을 직렬화한 바이트로 확인한다. 그 상한 안에서도 워커가 각 Qwen 호출 직전에 시스템 프롬프트와 직렬화한 JSON의 합계 7168바이트를 검사한다. 검토 단계 JSON에는 초안도 포함한다. 초과는 엔진에서 일반 모델 실패와 구분해 워커가 `failed`에 `RAG_CONTEXT_TOO_LONG`으로 보고한다. 서버의 JSON 상한 초과나 워커의 이 코드에는 근거를 잘라 재실행하는 대신 사용자 확인 필요 상태와 질문 범위를 좁히라는 안내를 표시한다.

완료된 답변과 보류는 완료 시각부터 최대 24시간 표시한다. 입력 근거의 전사가 그 전에 만료되거나 권한이 사라지면 즉시 숨긴다. 질문 벡터는 검색이 끝나면 제거하고, 완료 후 표시용으로는 질문·답변/보류와 인용 참조를 보관한다. 처리 기한 초과 또는 표시 기간 종료 시 질문 본문과 관련 입력·결과를 청소하고, 상태 표시에는 원문 없는 상태·식별자만 사용한다.

## 권한·사본

서버는 claim, 입력 조회, 실행 상태 갱신, 결과 수락, 검색 및 웹 표시에서 소유자와 해당 작업의 모든 원본을 확인한다. 사적 전환·삭제·전사 교체·만료가 발생하면 관련 진행 작업과 질문 결과를 무효화한다. 답변에 인용되지 않은 발화도 모델이 사용했을 수 있으므로 전체 입력을 기준으로 한다. 같은 트랜잭션에서 검색과 결과 노출을 차단하고 벡터·서버 입력·결과 사본을 청소한다. 온전한 전사만 남고 원음이 만료되면 텍스트 인용은 제공하며 재생을 숨긴다.

워커는 취소 또는 임대 상실을 감지하면 소유 프로세스 그룹을 종료하고, 관리 키에 해당하는 `work`·`spool`을 청소한다. 서버는 사본별 청소 확인을 기록한다. 재연결 시 청소 지시와 spool 상태를 새 claim보다 먼저 확인한다. 워커가 오프라인이어도 질문 사본은 고정한 질문 처리 기한을 넘겨 재사용할 수 없으며, 물리 삭제 확인은 별도 상태로 남긴다.

웹은 기존 인증 세션과 CSRF가 적용된 `POST /questions`에서 질문을 만든다. 양끝 공백을 제거한 질문은 1~200자, 선택 거래처는 최대 100자다. 선택 날짜는 실재하는 `YYYY-MM-DD`만 받으며 시작일이 종료일보다 늦으면 거부한다. 누락되거나 빈 필터는 생략한다. 검색에 적용한 거래처·한국 날짜 범위를 `RAG_ANSWER.scope`의 `counterparty`, `from_date`, `to_date`로 전달한다. 검증 실패는 작업을 생성하지 않는다.

성공한 POST는 `303`으로 `GET /questions/{request_id}`에 이동한다. GET은 소유자에게만 인덱스 준비 중, 워커 대기, 처리 중, 완료, 보류, 사용자 확인 필요, 실패, 대기 중 기한 초과, 처리 중 기한 초과, 결과 만료, 원본 이용 불가 상태를 보여준다. 다시 열어도 작업이 새로 생성되지 않는다.

## 구현 순서와 완료 기준

1. 임시 PostgreSQL과 모의 워커로 작업 생성부터 ACK까지 확인한다. readiness·claim의 기존 워커 호환과 버전 협상, 우선순위·비선점·대기 만료, 다중 통화 고정 입력, 동시 claim, 중복·늦은 제출, 사적·미분류·삭제·만료 입력의 모델 호출 차단을 시험한다.
2. pgvector와 질문 화면을 연결한다. 조각 중첩·공백 제거, 권한·필터 뒤 검색, 컨텍스트 초과의 비재시도, 보류의 빈 인용과 결과 24시간 경계, 인용의 전사 버전 매핑, 질의 도중 삭제, 원음만 만료된 경우, 결과 저장 직후 ACK 유실과 재시작을 통합 테스트한다.
3. 별도 합성 데이터로 배포한 홈서버에서 WSL GPU 워커의 VPN·HTTPS claim과 실제 결과 제출, 답변·인용·원음 재생을 확인한다. 업로드 중 VPN 단절과 워커 재시작 뒤 결과 한 건과 사본 청소를 확인하면 배포 검증을 완료한다.
