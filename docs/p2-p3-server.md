# P2/P3 서버 구현과 재현

이 구현은 가짜 데이터로 수집·분류·삭제와 PostgreSQL 큐 계약을 검증한다. 실제 통화, Whisper/Ollama, Google, n8n, 동기화 서비스에 연결하지 않는다. 실제 모델 결과는 아직 허용하지 않는다.

## 실행 환경

Python 3.12와 [requirements.txt](../requirements.txt)의 psycopg·Starlette·Uvicorn을 사용한다. 인증, 통화 관리, 워커 API는 한 ASGI 앱에 등록하고 Jinja로 브라우저 화면을 렌더링한다. DB 준비와 역할 분리는 [P1 안내](p1-foundation.md)를 따른다. `009_manual_tasks.sql`까지 명시적으로 마이그레이션해야 앱이 시작된다.

```text
python -m pip install -r requirements.txt
python scripts/check.py
python scripts/test_postgres.py --pg-bin E:/PostgreSQL/bin --phase P2
python scripts/test_postgres.py --pg-bin E:/PostgreSQL/bin --phase P3
```

마지막 두 명령은 각각 새 테스트 클러스터를 생성하고 `scripts/check.py --phase P2/P3`를 실행한 뒤 정리한다. 로컬 검증에는 Windows PostgreSQL 18.0을 사용한다. 미리 준비한 빈 전용 테스트 DB를 사용하는 실행 방법은 하네스 안내를 따른다. [하네스 실행](harness.md#실행)

## 수집·분류

- 데이터 루트는 Git 밖의 전용 경로다. `sync-inbox`, `quarantine`, `artifacts`만 관리한다. 휴대전화 원본 경로를 받지 않는다.
- 수신 형식은 PCM WAV, AAC·ALAC M4A, MP3, AMR-NB·WB다. 입력 상한은 500MiB·2시간·1~2채널이다. 확장자와 파일 헤더의 일치를 확인하고 PCM 프레임을 읽거나 PyAV로 단일 음성 스트림을 디코딩해 코덱·채널·길이·손상을 검사한다. 이때 모델을 호출하거나 디코딩 결과를 저장하지 않는다. 상한 부하·실기기 호환은 별도 검증한다.
- 수신 도구가 파일을 닫고 완료를 확정한 뒤 제공한 SHA-256을 입력한다. `.part`는 완료 해시를 전달해도 무시하며, 앱이 파일 크기 안정만 보고 완료 신호를 만들지 않는다. 복사 전후 속성·두 번의 해시·격리 사본 판독을 검사한다. 유효한 프레임 경계에서 잘린 파일의 원래 길이는 디코더에서 확인할 수 없어 송신 측 원본 해시가 필요하다.
- SHA-256으로 녹음을 중복 제거하고 수신별 사본을 기록한다. 파일명은 화면·로그에 노출하지 않으며 경로 구분자·스트림·심볼릭 링크·Windows reparse point를 거부한다. 전용 루트와 그 상위 디렉터리는 신뢰된 서비스 계정만 수정할 수 있어야 한다. 실제 ACL 구성은 C1/C7 검증 대상이다.
- 미분류·보류는 최초 수신 72시간 후 만료한다. 보류는 기한을 연장하지 않는다. 업무 분류와 STT 작업 INSERT는 같은 트랜잭션이다. 중복 승인으로 작업을 늘리지 않는다.
- 사적 선택/미분류 만료는 inbox·격리·파생 파일을 복사본별로 청소한다. 한 사본에서 실패해도 나머지는 정리하며, 실패나 워커 미확인이 남으면 완료로 표시하지 않는다. 같은 이름의 새 수신 파일은 보존한다. 새 콘텐츠 수신이 검증되면 해당 경로의 이전 수신 기록을 정리된 것으로 표시한다.
- 완료 검사까지 넘겨진 뒤 거부된 파일은 처음 거부한 때부터 24시간 청소 대상으로 등록한다. 같은 파일을 다시 거부해도 기한은 연장되지 않는다. 같은 경로에서 교체된 파일이 새로 거부되면 새 파일 기준으로 24시간을 계산한다. 전송 중인 `.part`는 수신 도구가 관리한다.

가짜 파일을 전용 inbox에 수신 완료한 뒤 사용하는 명령:

```text
python scripts/manage.py ingest --name completed.wav --sha256 PRODUCER_COMPLETION_SHA256
python scripts/manage.py maintain
```

수집 CLI는 완료 해시 불일치·임시 파일을 `TRANSFER_INCOMPLETE`, 잘못된 해시 표기를 `INVALID_HASH`, 미지원 확장자·코덱·스트림을 `UNSUPPORTED_AUDIO_FORMAT`, 형식 위장·손상·상한 초과를 `INVALID_AUDIO`로 표시한다. 파일명과 비밀값은 오류 출력에서 제외한다.

`maintain`은 만료·사본 청소·임대 회수·파일/DB 복구를 한 번 실행한다. 주기 실행 서비스는 아직 설치하지 않았다. 운영 전 C1에서 주기를 설정해야 한다. 조회 GET은 만료 데이터를 차단하지만 삭제나 업무 상태 변경을 수행하지 않는다.

DB가 불가하면 앱은 신규 격리 복사 전에 실패한다. 실제 동기화 수신을 멈추는 어댑터는 연결하지 않았으므로 C2/C7의 실제 수신 중단 시험까지 완료한 것은 아니다. 사용자가 수동으로 inbox에 쓰는 것까지 막는다고 해석하지 않는다.

## 로그인 화면

환경 변수는 `.env.example`에 이름만 설명하며 자동 로드하지 않는다. 서버에 소유자 이름, Werkzeug `generate_password_hash`로 생성한 scrypt 해시, 서로 다른 충분히 긴 세션 비밀값·워커 토큰을 명시해야 한다. 예제 placeholder는 실제 비밀값이 아니다.

```text
python scripts/manage.py serve --cert ABSOLUTE_CERT_PATH --key ABSOLUTE_PRIVATE_KEY_PATH
```

이 명령은 Uvicorn으로 `https://localhost:8443/login`에서 로컬 개발 서버를 실행한다. 인증서와 키를 인자로 받으며 신뢰 호스트는 localhost/127.0.0.1로 제한한다. 운영 도메인과 프록시 신뢰 설정은 C1에서 확정한다.

로그인 CSRF, Secure/HttpOnly/SameSite 쿠키, DB 세션 8시간 만료, 로그아웃 시 서버 세션 폐기, 로그인 실패 제한을 적용한다. 목록·음성·분류 모두 사용자 세션이 필요하다. 분류/로그아웃은 POST와 CSRF를 검사한다. 워커 Bearer 토큰은 워커 API에 사용한다. 브라우저 요청 본문은 16KiB, 워커 요청 본문은 8MiB로 제한한다. 기존 Flask 세션 쿠키를 사용하던 브라우저는 Starlette로 전환 후 다시 로그인한다. 기존 scrypt 비밀번호 해시로 로그인할 수 있다. [Starlette 미들웨어 문서](https://starlette.dev/middleware/)

목록은 최근 200건이며 페이지 이동·원격 배포·브라우저 시각 검수는 아직 없다. 음성 응답은 한 파일을 메모리로 읽으므로 최대 크기 동시 재생의 성능은 검증하지 않았다.

원음 응답은 확인된 컨테이너에 맞는 MIME 타입을 반환한다. 통화 목록과 상세의 오디오 플레이어는 원음 재생에 실패한 경우 업무 승인된 M4A·AMR을 모노 16kHz PCM WAV로 변환해 재생할 수 있다. 호환 응답은 요청 시 메모리에서 만들며 디스크에 추가 사본을 생성하지 않는다. 변환 중 사적 전환이나 만료가 발생하면 응답을 차단한다.

### 통화 상대와 실제 통화 시각

미분류·보류 상태에서는 상대 이름과 확인한 통화 시각을 저장할 수 있다. 상대 이름은 최대 100자이며, 빈 값은 미확인으로 남는다. 입력 시각은 한국 시간으로 해석하고 `call_started_at`·`USER_CONFIRMED` 출처·확인 여부를 함께 기록한다. 수신 시각을 실제 통화 시각으로 대신하지 않는다.

검색의 날짜 범위는 실제 통화 시각의 한국 날짜를 기준으로 양 끝 날짜를 포함한다. 상대 이름은 부분 일치이며 `%`·`_`는 문자 그대로 검색한다. 날짜가 없는 기존 녹음은 날짜 필터를 쓰지 않을 때 조회할 수 있다. 사적·만료·삭제 대상 정보는 검색에서 제외하며, 실제 정리 시 상대·통화 시각·출처를 함께 비운다.

업무 승인 이후 통화 정보는 잠근다. 향후 상대 날짜 분석의 입력을 수정하려면 입력 버전·재분석 결과와 연결하는 별도 경로가 필요하다. 정보 저장은 업무 승인을 실행하지 않으며 사용자 세션과 CSRF를 요구한다.

## 큐와 가짜 워커

| 요청 | 목적 |
|---|---|
| `POST /worker/claim` | 승인된 작업의 임대와 고정 입력 식별자 발급 |
| `GET /worker/jobs/{id}/input` | 할당된 워커/현재 임대의 입력만 조회 |
| `POST /worker/jobs/{id}/heartbeat` | 임대만 갱신 |
| `POST /worker/jobs/{id}/start` | 요청 ID에 고정된 실행 기한 확인 |
| `POST /worker/jobs/{id}/prepared` | spool 요청 ID·정확한 해시·크기·생성 시각 고정 |
| `POST /worker/jobs/{id}/result` | 같은 결과 바이트 수락 및 멱등 ACK |
| `POST /worker/jobs/{id}/failed` 또는 `waiting-file` | 제한 재시도 또는 파일 대기 반환 |
| `POST /worker/cleanup` | 자기 장비의 사본별 청소 조회/종료·삭제 확인 |

작업 키는 녹음·단계·파이프라인 버전으로 유일하다. claim에 행 잠금과 `SKIP LOCKED`를 사용한다. 초기 한 서버의 파일/DB 경합은 공통 PostgreSQL advisory lock으로 직렬화했다. 여러 서버의 처리량 최적화는 아직 하지 않는다.

임대는 5분이며 준비 10분, STT 실행 60분, 분석 실행 30분, 업로드 30분이다. heartbeat는 상태별 기한을 연장하지 않는다. 입력 만료와 spool 24시간도 적용한다. 모든 API 시간은 UTC로 반환한다. 상태 변경/응답 유실 재요청은 같은 요청 ID를 사용한다. 구 임대·다른 워커·다른 입력 버전·다른 결과 바이트는 거부한다. 이미 수락한 결과는 나중에도 원문 없이 같은 ACK를 반환한다.

실행 오류는 초기 시도와 추가 3회(1/5/30분) 후 수동 확인으로 멈춘다. 파일 대기·오프라인 임대 만료는 모델 실패 횟수에 넣지 않는다. 종료와 사본 삭제가 미확인인 워커는 다음 작업을 받지 않는다. 청소 조회/확인은 활성 임대 없이 자기 copy key와 요청 버전으로 수행한다.

수락 파일은 part 기록·fsync·rename 후 artifact 참조, 작업 성공, 다음 분석 작업을 한 DB 트랜잭션으로 저장한다. 성공 확정 직전에 임대·업로드·입력 보관 기한을 다시 검사한다. 기한을 넘긴 결과는 후보와 DB 참조를 롤백하고 해당 파일을 삭제한다. 재시작 때 참조 없는 생성 파일을 정리하고, 참조 파일이 없으면 INPUT_MISSING으로 수동 확인한다. 프로세스/DB 실패 복구를 검증하며 전원 차단에 대한 파일시스템 내구성 시험은 하지 않았다.

`src/callops/processing/fake_worker.py`는 실제 워커 API를 통해 합성 결과를 처리한다. 전사 ACK 후 로컬 파일을 지워도 새 워커가 서버 artifact를 받아 분석한다. 결과에는 job·attempt·input ID/버전/해시가 포함된다. 가짜 STT 워커는 수신과 같은 디코더에서 읽은 재생 길이와 가상 텍스트로 구간 결과를 만든다. 가짜 분석 워커는 기본으로 합성 텍스트를 반환하고, `events`를 명시하면 합성 일정 후보를 반환한다. 실제 모델과 장시간 워커 heartbeat 스레드·연산 프로세스 종료·지속 spool 재개는 P4/P5/D5 구현 대상이다.

### 합성 전사 결과 스키마와 조회

공통 필드는 `schema_version`·`job_id`·`attempt_id`·`input_artifact_id`·`input_artifact_version`·`input_sha256`·`synthetic`다. `synthetic`은 true여야 한다. 기존 버전 1은 `text` 필드를 사용하며 STT·ANALYSIS 결과로 계속 수락한다. STT 버전 2는 `segments`, ANALYSIS 버전 2는 `events`를 사용한다.

각 구간은 `segment_id`·`start`·`end`·`text`만 포함한다. ID는 1부터 연속된 정수이고 시작 시각은 비감소 순서다. 시각은 0부터 수신 시 검증한 음성 길이 이내이며 bool·비유한 값·역순·잘못된 범위를 거부한다. 최대 10,000구간·전체 텍스트 100,000자·결과 파일 8MiB를 적용한다. 빈 구간 배열은 구간 없는 합성 결과로 표시한다.

`GET /recordings/{id}`는 통화 상세와 최신 수락 STT 전사를 보여준다. `GET /recordings/{id}/transcripts/{artifact_id}#segment-{segment_id}`는 전사 버전과 구간을 고정한다. 사용자 세션이 필요하며 다른 통화의 artifact, 사적·삭제·만료 자료를 거부한다. 파일 해시·크기를 확인하고 기존 텍스트 결과는 시간 구간 없이 표시한다. GET은 보관 상태나 파일을 변경하지 않는다.

원음의 초기 30일 기한이 지나도 유효한 전사 90일 기한 안에서는 전사를 조회할 수 있다. 원음을 사용할 수 없거나 구간 길이가 0이면 구간 재생 링크를 숨긴다. `GET /recordings/{id}/transcripts/{artifact_id}/audio/{segment_id}`는 저장된 시작·끝 시각으로 해당 구간만 WAV로 반환한다. 압축 원음은 메모리에서 PCM으로 디코딩하며 구간 파일을 보관하지 않는다. 응답 직전에 업무 승인과 원음 기한을 다시 확인한다.

### 전사 내용 검색

로그인 후 통화 목록의 **전사 내용 검색**을 열면 거래처·한국 날짜 범위와 검색어를 입력할 수 있다. `POST /search`는 사용자 세션과 CSRF를 확인한다. 공백으로 나눈 검색어가 모두 포함된 한 전사 구간을 찾고, 최근 수신 통화 순으로 최대 5개를 표시한다. 결과는 전사 버전과 구간 ID에 고정된 상세 링크를 제공한다.

업무 승인 상태, 삭제 여부와 최신 전사의 보관 기한을 확인하고 상세 화면과 같은 해시·스키마 검사를 적용한다. 검색 결과에서 유실·손상된 파일을 제외하고 화면에 일부 전사를 확인할 수 없다고 표시한다. 구간 정보가 있는 합성 전사가 검색 대상이다. 최근 수신 최대 50건과 파일 합계 16MiB를 확인하며 한도로 범위가 줄어들면 화면에 알린다. 검색 인덱스는 두지 않아 별도 전사 사본이 생기지 않는다.

### RAG 근거 검색 함수

서버 내부 `retrieve_evidence()`는 같은 후보 조회와 전사 파일 검사를 사용한다. 통화별 연속 구간을 600자·45초 이내로 묶는다. 한 발화가 범위를 넘으면 그대로 두고, 이전 조각의 마지막 발화가 다음 조각에 들어갈 여유가 있으면 함께 넣는다. 600자·45초는 개발 시작값이다.

주입한 임베딩 함수로 질문과 조각을 비교해 코사인 유사도 순으로 최대 5개를 반환한다. 각 조각은 통화·전사 ID, 거래처·통화 시각과 원본 구간별 시각·링크를 포함한다. 임베딩 계산 중 상태가 바뀔 수 있어 결과를 반환하기 전에 업무 승인, 삭제, 만료 및 최신 전사 여부를 다시 조회한다.

### 합성 일정 후보 검토

통화 목록에서 업무 통화의 **전사 상세 → 일정 후보 검토**를 연다. 후보마다 전사 버전과 구간을 고정한 근거 링크가 표시된다. 제목과 시작·종료 시각은 한국 시간으로 수정한다. 시간이 비어 있으면 확인 필요 상태를 유지하고, 둘 다 저장한 뒤 별도로 승인한다. 이미 시작 시각이 지난 후보는 승인할 때 확인란을 선택해야 한다.

ANALYSIS 버전 2의 `events`는 최대 10개다. 각 항목은 `title`, `start`, `end`, `time_hint`, `segment_ids`를 사용한다. `start`와 `end`는 시간대 오프셋이 포함된 ISO 일시 또는 null이며 종료는 시작보다 늦어야 한다. `time_hint`에는 통화의 시간 표현을 보존한다. 서버는 분석 작업에 고정된 버전 2 전사의 해시와 구간 ID를 확인한다. 같은 분석 결과 안에서 제목, UTC 기준 시각, 시간 표현, 근거 ID 집합이 모두 같은 후보는 한 건만 저장한다. 가짜 분석 입력은 시간을 직접 제공하고, 상대 날짜의 자동 해석과 실제 추출 품질 검증은 후속 작업이다.

기존 워커 API에 연결한 `FakeWorker`로, 대기 중인 업무 녹음이 한 건인 합성 개발 DB에서 다음 순서로 결과를 만든다.

```python
worker.once(transcript_text='1월 3일 오후 2시에 견적 검토하러 방문할게요. 종료 시각은 다시 정하죠.')
worker.once(events=[{
    'title': '가상 거래처 견적 검토',
    'start': '2030-01-03T14:00:00+09:00',
    'end': None,
    'time_hint': '1월 3일 오후 2시',
    'segment_ids': [1],
}])
```

후보 저장과 분석 결과 수락은 같은 PostgreSQL 트랜잭션으로 처리한다. 수정과 승인·거절은 사용자 세션, CSRF, 후보 revision과 업무 상태를 검사한다. 승인한 내용은 revision별로 저장하며 같은 revision의 승인 재시도는 기록을 추가하지 않는다. 승인한 후보를 수정하면 다시 검토한다. 통화를 사적으로 바꾸면 후보와 승인 기록도 삭제하며, 전사 기한이 지나면 후보 접근을 막고 `maintain`에서 정리한다.

### 승인된 일정과 모의 Calendar

통화 목록의 **일정 목록**(`/schedules`)은 `schedules`에서 직접 입력 일정과 통화 승인 일정을 시작 시각순으로 조회한다. 일정의 현재 값과 승인 스냅샷을 따로 저장한다. 후보를 편집 중일 때는 마지막으로 승인한 값이 목록에 남고 신규 전송은 차단된다. 재승인하면 같은 일정 ID의 현재 값이 갱신된다.

통화 일정에는 유효한 승인 스냅샷의 근거 구간과 모의 전송 상태를 표시한다. **모의 Calendar로 전송**은 로그인·CSRF를 검사하는 별도 POST다. 서버는 현재 채택된 후보와 승인 revision, 통화의 업무 상태, 근거 보관 기한과 파일 무결성을 확인한다. 이미 시작한 일정의 신규 생성은 차단한다.

기존 전송 경로 `POST /schedules/{candidate_id}/send`는 통합 목록의 `candidate_id`와 `approval_revision`을 사용한다. 목록의 `id`와 `revision`은 현재 일정의 키와 버전이다.

전송 기록은 `calendar_deliveries`에 저장하며, 모의 Calendar는 `mock_calendar_events`에 이벤트 ID와 제목·시작·종료의 해시를 별도 트랜잭션으로 기록한다. 이벤트 ID는 내부 일정 ID를 재사용한다. 응답 유실 시 목록에 **전송 결과 확인 필요**를 표시한다. **등록 확인 후 재시도**는 기존 이벤트를 먼저 조회한다. 기존 이벤트의 해시가 일치하면 등록 완료로 확정하고, 등록되지 않은 것이 확인되면 현재 유효한 승인으로 생성한다. 이미 등록된 일정을 수정·재승인하면 기존 모의 등록과 변경 사실을 표시한다.

전사 근거가 만료되면 현재 일정은 남고 합의 상세·근거 링크·신규 전송은 차단된다. 통화 전체 삭제나 사적 전환 시 일정의 제목·시각·원본 연결을 지운다. 이미 생성된 이벤트의 중복 방지를 위해 일정 ID와 전송 식별 기록을 유지한다.

이 경로는 로컬 PostgreSQL의 모의 제공자를 사용한다. 실제 Google Calendar와 OAuth, 할 일 관리는 후속 범위다.

### 직접 입력 일정 화면

일정 목록(`/schedules`)에서 **새 일정**을 열고 제목, 시작·종료 시각을 입력한다. 표시와 입력은 한국 시간 기준이며 종료는 시작보다 늦어야 한다. 직접 입력 일정의 **수정**에서 기존 값을 편집하고, **일정 삭제**를 누르면 별도의 확인 화면을 연다. 통화에서 승인된 일정은 같은 목록에서 전사 근거 조회와 모의 전송을 제공한다. [승인된 Figma 시안](https://www.figma.com/design/FTB08BRgu0d4mXnIWlg8MP?node-id=9-595)

등록(`/schedules/manual/new`), 수정(`/schedules/manual/{id}`), 삭제 확인(`/schedules/manual/{id}/delete`) 화면은 각 주소에 폼을 제출한다. 아래 API와 같은 입력 검증과 저장 로직을 사용한다. 입력 오류 시 제출값과 등록 키 또는 편집 revision을 유지하고, 다른 탭에서 먼저 변경했다면 제출을 거부하고 **최신 일정 목록**으로 안내한다. 저장·삭제에 성공하면 목록으로 이동한다.

### 직접 입력 일정 API

로그인한 세션으로 조회하고, 쓰기 요청에는 `application/x-www-form-urlencoded` 본문과 `csrf`를 제출한다. `start`와 `end`는 `YYYY-MM-DDTHH:MM` 형식의 한국 시간이며 초를 붙일 수 있다. 둘 다 입력하고 종료는 시작보다 늦어야 한다. JSON 응답의 `start_at`과 `end_at`은 UTC로 반환한다.

| 요청 | 입력과 동작 |
|---|---|
| `GET /api/schedules` | `csrf`와 `schedules`를 반환한다. `id`·`revision`은 현재 일정 기준이며 `source`는 `manual` 또는 `call`이다. 유효한 통화 근거의 `candidate_id`·`approval_revision`·`agreement`와 전송 가능 여부를 별도로 반환한다. |
| `POST /api/schedules/manual` | `request_id` UUID, `title`, `start`, `end`로 등록한다. 최초 등록은 201, 등록 내용이 그대로인 동안 동일 요청 재전송은 기존 일정을 200으로 반환한다. |
| `POST /api/schedules/manual/{id}` | `action=edit`와 현재 `revision`, `title`, `start`, `end`를 보내면 수정한 일정과 새 revision을 반환한다. |
| `POST /api/schedules/manual/{id}` | `action=delete`와 현재 `revision`으로 삭제한다. 성공과 동일 삭제 요청 재시도는 204다. |

`id`는 서버가 발급한다. 오래된 revision과 다른 내용으로 재사용한 등록 키는 409로 거부한다. 삭제 시 제목과 시각을 지우고, 이전 요청의 재전송으로 되살아나지 않도록 ID·등록 요청 키·revision·삭제 시각을 유지한다. 직접 입력 일정은 CallOps 내부 일정이며, 기존 모의 Calendar 전송은 통화 후보 승인 경로를 사용한다.

### 직접 입력 할 일 화면

로그인 후 통화 목록의 **할 일 목록**을 열면 `/tasks`에서 미완료와 완료를 볼 수 있다. 제목만 입력해 추가하거나 한국 시간 기준 기한을 함께 설정한다. **수정**에서 제목·기한을 바꾸거나 **기한 지우기**를 누르고 저장한다. 미완료만 완료할 수 있으며, 수정 화면에서 삭제 확인으로 이동한다.

HTML 폼과 아래 JSON API는 같은 입력 검증과 저장 함수를 쓴다. 입력 오류는 입력값과 등록 키 또는 편집 revision을 유지한다. 다른 탭에서 먼저 변경했다면 이전 제출을 거부하고 최신 목록으로 돌아가는 링크를 표시한다. [승인된 Figma 화면](https://www.figma.com/design/FTB08BRgu0d4mXnIWlg8MP?node-id=3-301)

### 직접 입력 할 일 API

`tasks`에 제목, 선택 기한, 상태(`OPEN` 또는 `DONE`), `revision`, 완료 시각을 저장한다. 소유자 세션이 필요하고 POST는 폼으로 `csrf`를 보낸다. `due`는 한국 시간 기준 `YYYY-MM-DDTHH:MM` 또는 초까지 포함한 일시다. 생략하거나 빈 문자열을 보내면 기한은 `null`이다. 응답의 `due_at`과 `completed_at`은 UTC ISO 일시 또는 `null`이다.

| 요청 | 폼 필드 | 성공 응답 |
|---|---|---|
| `GET /api/tasks` | 없음 | 200. `csrf`와 삭제되지 않은 `tasks` 목록 |
| `POST /api/tasks` | `request_id`(UUID), `title`, `due`(선택) | 201. 서버가 발급한 `id`와 `revision=1`. 수정 전 같은 입력 재전송은 200과 기존 항목 |
| `POST /api/tasks/{id}` | `action=edit`, `revision`, `title`, `due`(선택) | 200. 제목과 기한을 수정하고 revision 증가 |
| `POST /api/tasks/{id}` | `action=complete`, `revision` | 200. `OPEN`을 `DONE`으로 바꾸고 완료 시각 기록 및 revision 증가 |
| `POST /api/tasks/{id}` | `action=delete`, `revision` | 204. 내용 삭제. 같은 삭제 요청의 재전송도 204 |

오래된 revision, 이미 완료한 항목의 재완료, 다른 내용으로 사용한 등록 키는 409로 거부한다. 없는 항목은 404를 반환한다. 삭제된 항목의 제목·기한·상태·완료 시각을 비우고 ID·등록 키·revision·삭제 시각을 보존해 지연된 등록 재시도를 막는다. 통화 후보 연결과 보관 만료는 후속 단계다. [마이그레이션](../migrations/009_manual_tasks.sql) · [화면·API 검증](../tests/p3/test_tasks.py)

## 확인 범위

2026-11-11 전사 검색 추가 후 하네스·P1~P3 46개를 통과했다. 임시 데이터로 로컬 HTTPS에서 수신·업무 승인·가짜 워커 처리 후 전사 검색과 고정 근거 링크를 확인했다.

2026-11-11 Starlette 전환 후 임시 PostgreSQL에서 하네스·P1~P3 44개를 통과했다. Uvicorn 로컬 HTTPS에서 합성 WAV 수신, 로그인, 업무 승인, 가짜 워커, 전사 상세 조회, 한도를 초과하는 스트리밍 업로드의 413 응답을 확인했다. 브라우저 구간 재생과 운영 배포는 별도 검증 범위다.

2026-11-11 합성 전사 상세 추가 후 검증은 하네스 7개·P1 3개·P2 15개·P3 17개, 총 42개 통과, skip 없음이다. 구간 ID·시간·텍스트·Unicode 검증, 실제 큐의 저장·ACK 재시도·분석 입력 연결, 고정 출처 링크·인증·다른 통화 차단, 취소·사적·유실·변조·만료를 확인했다. 기존 텍스트 결과 조회와 원음 만료 후 전사 조회도 시험했다. 임시 클러스터를 종료·정리했다. 실제 GPU·브라우저 구간 재생은 미검증이다.

2026-11-11 추가 검증은 통화 정보의 사용자 세션·CSRF, 업무 승인 전 입력과 승인 후 잠금, 실제 통화 날짜의 한국 시간 경계, 상대 이름의 문자 그대로 검색, 사적·만료 정보 청소를 포함한다. 기존 마이그레이션 2개를 적용한 DB에 녹음을 먼저 넣고 `003`을 적용해 데이터 보존도 확인했다. 하네스 7개·P1 3개·P2 15개·P3 10개, 총 35개 통과, skip 없음. 실제 GPU·브라우저 시각 검수는 포함하지 않는다.
