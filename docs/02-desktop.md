# 2. 데스크톱 — GPU 환경 준비·워커 실행·운영 절차

작성일: 2026-09-19 · GPU 환경과 워커 운영 계획. 실행 환경 재현, 모델 시험, 실제 워커 연결의 진행 상태는 [데스크톱 GPU 체크리스트](progress-checklist.md#데스크톱-gpu)를 따른다.

연결 문서: [이 프로젝트](01-project.md) · [공용 n8n 서버](03-server.md)

이 문서는 Windows GPU 데스크톱에서 해야 할 작업이다. 워커 코드·통신 계약·프로젝트 배포 절차는 프로젝트 문서에서 관리하고, 여기서는 GPU 실행 환경과 장비 운영을 다룬다. 아래의 “서버”는 홈서버에 배포된 CallOps 백엔드를 뜻하며 공용 n8n 인프라를 뜻하지 않는다. 코드의 원본은 CallOps 저장소에 두고 실제 실행 환경·모델·토큰·음성은 장비의 별도 저장소에 둔다. 승인 전에는 설치·드라이버 변경·방화벽 변경을 실행하지 않는다.

## 1. 역할과 완료 목표

홈서버가 GPU 없이도 업무 통화를 전사하고 검토용 후보를 만들 수 있도록 연산을 맡는다. 데스크톱은 업무 여부나 외부 등록 여부를 결정하지 않는다.

```text
서버 API에서 작업 임대 → 서버 API로 승인 음성 직접 수신(폴더 동기화 없음) → 파일 해시 확인 → Whisper → 전사 결과 반환
분석 작업 임대 → 고정된 서버 전사본 API 조회·해시 확인 → Ollama → 구조화 결과 반환
서버 ACK → 로컬 임시 파일 청소 → 다음 작업
```

| 구성요소 | 역할 | 허용 데이터 |
|---|---|---|
| GPU 워커 | claim·승인 음성/전사 조회·진행·결과 업로드·청소. 서버에서 pull만 하며 서버가 워커로 연결하지 않음 | 할당 작업의 입력과 처리 결과 |
| Whisper/faster-whisper | 구간별 전사 | 승인된 음성 |
| Ollama 로컬 모델 | 요약·일정/할 일/계약 언급 초안 | 승인 작업의 전사 |
| Windows 작업 스케줄러 또는 선택 환경 서비스 관리자 | 재부팅 후 시작·중복 프로세스 방지 | 실행 구성 |

완료 기준은 가짜 업무 녹음을 처리하고, 전원 OFF·VPN 단절·재부팅 뒤에도 서버 승인·중복 방지 규칙이 유지되는 것이다.

## 2. D0 — 사양과 기존 환경 확인

### 해야 할 일

- [ ] GPU 제조사·모델·VRAM·드라이버 버전을 확인한다.
- [ ] Windows 버전, RAM, 디스크 여유 공간을 확인한다.
- [ ] Python, WSL2, Docker Desktop, Ollama가 이미 설치되어 있는지 확인한다.
- [ ] 데스크톱과 서버가 같은 VPN에서 통신 가능한지 확인한다.
- [ ] Windows 재시작·로그아웃·잠금 시 실행 환경이 어떻게 동작하는지 확인한다.
- [ ] 절전·최대 절전·Windows 업데이트 재부팅 정책을 기록한다.
- [ ] BitLocker 여부는 현황만 기록한다. 이번 단계의 필수 구매·재설정 조건으로 만들지 않는다.
- [ ] 모델 다운로드 저장소와 작업용 디렉터리가 OneDrive 등 외부 동기화 경로인지 확인한다.

### 읽기 전용 확인 명령

아래 명령은 사용자가 데스크톱에서 실행할 때의 점검용이다. 없는 명령의 오류는 미설치 증거이며 바로 설치하라는 의미가 아니다.

```powershell
nvidia-smi
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
Get-Volume | Select-Object DriveLetter, FileSystem, Size, SizeRemaining
wsl --status
wsl --list --verbose
docker version
python --version
ollama --version
powercfg /getactivescheme
```

VRAM은 NVIDIA 장비라면 `nvidia-smi` 출력을 우선한다. `Win32_VideoController.AdapterRAM`만으로 최신 대용량 GPU 메모리를 확정하지 않는다. NVIDIA가 아니라면 모델·런타임 지원 여부부터 다시 확인하고 CUDA 설치를 진행하지 않는다.

### 하면 안 되는 일

- 기존 개발용 Python·드라이버·Docker 환경을 확인 없이 덮어쓰기.
- GPU 메모리가 확인되지 않은 상태에서 큰 모델이나 동시 실행 수를 확정.
- 접근 토큰·환경변수 전체·개인 파일 목록을 진단 출력에 포함.
- 서버 또는 GPU 사양 확인을 위해 실제 고객 녹음을 투입.

### 완료 조건

GPU·VRAM·드라이버·실행 환경·VPN·여유 공간 기록이 있어 D1의 한 가지 실행 방식을 선택할 수 있다. 프로젝트 P1~P3 개발은 이 확인과 독립적으로 진행 가능하다.

## 3. D1 — 하나의 실행 방식 선택

| 후보 | 준비할 것 | 확인할 것 |
|---|---|---|
| Windows 네이티브 | 전용 Python 가상환경, GPU 런타임, 로컬 Ollama, 작업 스케줄러 | 계정별 모델 경로, CUDA 관련 라이브러리, 로그아웃 후 동작 |
| WSL2 Linux | GPU가 보이는 WSL2, Linux 환경·모델 경로, 자동 시작 | Windows 재부팅 후 WSL 시작, VPN 경로, 파일 권한 |
| Docker GPU 환경 | Docker Desktop/WSL2 GPU 지원, 고정 이미지, 볼륨 | 컨테이너 안 GPU, 네트워크 localhost 의미, Desktop 시작 의존 |

세 방식을 동시에 설치하지 않는다. 이미 정상 동작하는 환경을 우선 사용하고, D0 결과에 따라 Python/CTranslate2/CUDA/cuDNN 조합과 모델 버전을 잠근다. 드라이버가 설치돼 있다는 사실만으로 전사 런타임 GPU 사용이 검증된 것은 아니다.

faster-whisper는 CTranslate2 기반이며 지원 런타임 조합이 버전에 따라 달라진다. 선택한 버전의 공식 요구사항을 설치 직전에 확인한다. 시스템 FFmpeg가 항상 필수인 것은 아니므로 메타데이터 검사·변환 도구의 실제 필요를 확인한 뒤 추가한다. [faster-whisper 공식 README](https://github.com/SYSTRAN/faster-whisper)

### 해야 할 일

- [ ] 선택 환경과 선택 이유를 이 문서에 기록한다.
- [ ] 설치·모델 다운로드 위치와 필요한 디스크 용량을 산정한다.
- [ ] 가짜 음성 한 건으로 GPU 연산 여부를 확인한다.
- [ ] 재현 가능한 패키지 잠금 파일 또는 이미지 버전을 기록한다.
- [ ] 이전 정상 버전으로 되돌리는 방법을 정한다.

### 하면 안 되는 일 / 완료 조건

`latest`만으로 운영 버전을 기록하거나 실행 시 자동 업데이트하지 않는다. 가짜 음성의 GPU 실행과 재시작 후 동일 버전 재실행이 확인되면 D1 완료다. 전체 드라이버 다운그레이드는 다른 작업에 영향을 주므로 별도 판단 없이 수행하지 않는다.

### 2026-11-21 D0~D1 검증 기록

- Windows 11 Home 빌드 26200, RAM 31.6 GiB, C: 여유 626.5 GiB. 균형 조정 전원 계획에서 S3 절전과 최대 절전이 지원된다. WSL2 Ubuntu 24.04.4 LTS는 RAM 15 GiB, ext4 여유 937 GiB였다.
- WSL에서 RTX 4060 Ti 8188 MiB와 Windows 드라이버 610.88을 확인했다. `nvidia-smi`의 CUDA UMD 표시는 13.3이다. Whisper 실행에는 가상환경의 cuBLAS 12.9.2.10과 cuDNN 9.26.0.51 라이브러리 경로를 사용했다.
- **실행 환경은 기존 WSL2와 `~/callops-runtime/.venv`를 선택했다.** 가상환경 2.6 GiB, Hugging Face 캐시 2.0 GiB, Ollama 모델 저장소 4.9 GiB가 이미 있다. 작업 경로와 Whisper 캐시는 WSL ext4에 있다. 재현용 패키지 버전은 [D1 패키지 스냅샷](../ai-worker/requirements-d1.txt)에 기록했다. Python은 3.12.3이다. 변경 후 복귀가 필요하면 별도 가상환경을 패키지 스냅샷으로 구성하고 아래 모델 식별값과 대조한 뒤 합성 WAV로 확인한다.
- Whisper `mobiuslabsgmbh/faster-whisper-large-v3-turbo` 캐시 리비전은 `0a363e9161cbc7ed1431c9597a8ceaf0c4f78fcf`다. Ollama CLI는 0.34.2이며 점검 시 서버에 연결되지 않았다. 로컬 `qwen3:8b` 매니페스트 SHA-256은 `500a1f067a9f782620b40bee6f7b0c89e17ae61f686b92c24933e4ca4b2b8b41`이다.
- 커밋 `150013a`의 `app.transcriber`로 2초 합성 톤 WAV를 CUDA `int8_float16`에서 처리하고 권한 600인 JSON 저장을 확인했다. 모델 로드 포함 5.46초였으며 톤에서 전사 구간 1개가 생성됐다. 한국어 음성 품질은 D3에서 평가한다.
- Windows Tailscale이 실행 중이며, 온라인 Linux 피어 한 대에 Windows Tailscale ping과 WSL ICMP ping이 모두 성공했다. 해당 피어가 CallOps 홈서버인지와 CallOps HTTPS API 응답은 별도 확인이 필요하다.
- Windows C:의 BitLocker 암호화는 0%였고 Docker Desktop 기본 설치 경로에 실행 파일이 없었다. Windows Update의 AU 그룹 정책 레지스트리 키가 없었다. 실제 재부팅 일정과 정책의 최종 적용 상태는 확인하지 않았다.
- Windows 재부팅(18:14 KST) 후 GPU 드라이버, Python 3.12.3, 패키지 스냅샷과 Whisper 캐시 리비전이 일치했다. 같은 2초 합성 WAV를 CUDA `int8_float16`에서 모델 로드 포함 4.93초에 처리했고 권한 600인 JSON을 저장했다. D1 재실행 기준을 충족했다. 잠금·로그아웃 시 런타임 동작은 확인이 남아 있다.

## 4. D2 — 파일·계정·VPN 경계 준비

### 저장 위치 제안

아래는 예시일 뿐 실제 드라이브는 D0 결과로 결정한다. 저장소 checkout과 분리한다.

```text
전용 CallOps 런타임 디렉터리/
  work/        # 서버 API로 받은 임대 작업의 처리용 독립 사본
  spool/       # 서버 수락 전 전사·추출 JSON
  models/      # 모델 캐시, 사용자 개인정보 없음
  logs/        # 내용 없는 운영 로그
  config/      # 권한을 제한한 실설정과 워커 토큰
```

### 해야 할 일

- [ ] 전용 사용자 또는 제한된 서비스 계정과 폴더 ACL을 정한다.
- [ ] 서버와 데스크톱 사이에 폴더 동기화를 만들지 않는다. 서버 `sync-inbox`·`quarantine`은 어떤 장치 공유 목록에도 없어야 한다.
- [ ] STT 음성은 `GET /worker/jobs/{id}/input`으로 받아 `work`에 저장하고 claim 응답의 `input_sha256`과 대조한 뒤 처리한다. 해시가 다르면 처리하지 않고 오류를 보고한다.
- [ ] 워커 토큰은 작업 조회·할당 작업의 입력(음성·전사) 조회·결과·heartbeat만 허용한다. 입력 조회도 현재 임대·artifact ID/버전·업무 승인·만료 여부를 검사한다.
- [ ] 취소 후에도 자기 worker_id의 삭제 지시 조회·복사본 청소 확인은 허용한다. 이 통신은 활성 연산 임대를 요구하지 않고 관리 루트 안의 복사본 키·요청 버전으로 제한한다.
- [ ] 워커가 서버 API로 나가는 pull 통신을 구성한다.
- [ ] Ollama는 워커와 같은 환경의 localhost에서만 접근하게 한다.
- [ ] Whisper는 워커 내부 라이브러리 호출을 우선하여 별도 공개 API를 만들지 않는다.
### 주의할 연결 방식

Windows의 localhost와 WSL/컨테이너 내부 localhost는 다를 수 있다. 한쪽 서비스가 다른 환경에서 보이지 않는다고 `0.0.0.0`으로 무제한 공개하지 않는다. 같은 환경에 묶거나 필요한 브리지 경로·방화벽만 명시적으로 허용한다. 불가피하게 모델 API를 다른 호스트에 노출하는 변경은 인증 프록시·VPN 제한 설계를 먼저 검토한다.

### 하면 안 되는 일

- 서버 DB 비밀번호·n8n 관리자 계정·Google OAuth 토큰을 데스크톱에 복사.
- OneDrive·공개 공유 폴더·Git 디렉터리에 음성/전사/spool 저장.
- 실제 파일명·전화번호를 작업 이름과 로그에 사용.
- 서버에서 받은 파일이라는 이유만으로 임대·작업 승인 확인 없이 전사.

### 테스트 / 완료 조건

- 잘못된 토큰과 다른 작업 ID는 거절된다.
- 서버 API 접근은 성공하고 다른 장비에서 모델 API 접근은 실패한다.
- 사적·미분류 가짜 파일은 데스크톱에 존재하지 않는다.
- 다운로드가 중단된 파일·해시 불일치 파일이 처리되지 않는다.

## 5. D3 — Whisper 전사 단독 검증

입력은 개인정보 없는 승인 테스트 음성이다. 단독 실행은 구간별 시간과 텍스트를 로컬 JSON에 저장한다. 결과의 `segments`는 프로젝트 F03의 전사 구간 형식을 따른다.

### 로컬 검증 체크리스트

- [x] 한국어 테스트에서 GPU 모델을 비교해 `large-v3`를 선택하고 모델 리비전·연산 형식·언어·VAD 설정을 기록했다.
- [x] 짧은 음성과 분할된 장문에서 시작·끝과 원본 시각 범위를 검사하고, 무음에는 `NO_SPEECH`를 기록했다.
- [x] 합성 날짜·시간·금액·고유명사·전화번호를 대조하고, 잡음·겹침에서 경고와 수동 확인이 필요한 경계를 기록했다.
- [x] segments 이터레이터를 끝까지 소비한 뒤 결과를 저장하고, 음성 길이·GPU 메모리·모델 로드와 전사 시간을 각각 측정했다. [공식 사용 안내](https://github.com/SYSTRAN/faster-whisper#usage)
- [x] 디코딩 실패와 취소, 메모리 오류 주입에서 GPU 메모리와 결과·임시 파일 정리를 확인했다.
- [x] 21개 입력을 각각 3회 실행했다. 최대 529.09초 입력은 로드와 전사를 합쳐 약 2분 40초로 초기 실행 상한 60분을 충족했다.

사용자 결정에 따라 이번 로컬 검증에서 최대 2시간 실전사 시험을 생략했다. 따라서 지원 최대 길이의 메모리·실행 시간과 운영 상한 확정은 남아 있다.

### 로컬 출력

- schema_version, model_name, 모델 실행 설정
- duration_seconds, language, processing_seconds
- segments: segment_id, start, end, text

서버에 제출할 작업·시도·녹음 식별자와 모델 버전은 D5 워커 연결 계약에서 검증한다.

## 6. D4 — Ollama 추출 단독 검증

입력은 수락된 가짜 전사본과 근거 구간이다. 출력은 요약·일정·할 일·계약 언급·불확실 항목의 JSON이다.

정답 전사 실험은 [AI 모듈 실행 안내](../ai-worker/README.md#d4-정답-전사-평가--wsl-데스크톱)의 `python -m app.evaluate_analysis`를 사용한다. 발화에는 원본 ID, 시작·끝 초, 화자 A/B 또는 `null`을 지정한다. 확인한 통화 시각과 시간대가 있으면 원문 날짜를 그 기준으로 해석한다. 종료나 담당자를 판단할 수 없으면 값을 비우고 확인 항목을 남긴다. `confirmed`는 통화의 합의 상태다. 등록은 사용자 승인과 서버 검증을 거친다.

분할은 UTF-8 바이트 수의 보수적 상한으로 계산한다. Ollama `format`의 JSON Schema는 응답을 제한하고, 프롬프트에는 별도로 복제하지 않는다. 컨텍스트 8,192에서 응답 2,048과 템플릿 여유 256을 빼고 발화가 온전히 들어갈 때만 다음 조각과 경계를 겹친다. 최대 8조각이며 병합에는 같은 바이트 예산을 적용한다. 모든 조각이 성공하면 각 조각이 인용한 원본 발화를 시간순으로 다시 대조한다. 인용 ID·시간 표현·이전 후보의 근거 보존을 검사하고, 어느 요청이든 실패하면 최종 후보를 반환하지 않는다. [Ollama 구조화 출력](https://docs.ollama.com/capabilities/structured-outputs) · [Ollama 요청·응답 필드](https://docs.ollama.com/api/chat)

## 7. D5 — CallOps 백엔드와 실제 워커 연결

초기 동시 실행 수는 1개다. Whisper와 Ollama를 순차 실행하고 필요하면 모델을 해제하여 VRAM 경합을 줄인다. STT와 분석은 서로 다른 단계로 저장하므로 분석 실패가 STT 재처리로 이어지지 않는다.

로컬 시험에는 [WSL 워커 실행 안내](../ai-worker/README.md#d5-워커-실행--wsl-데스크톱)와 [서버의 실제 결과 계약](p2-p3-server.md#d5-실제-모델-결과)을 사용한다.

### 작업 실행 순서

1. 모델·폴더·서버 연결을 검사하고 readiness를 보고한다.
2. 준비된 단계만 claim하고 job_id·lease_token·preparation_deadline·입력 식별자·해시를 보관한다. 즉시 별도 heartbeat 루프를 시작한다. 분석 입력은 input_artifact_id, input_artifact_version, input_sha256으로 고정한다.
3. 업무 승인·임대·입력 보관기한이 유효한지 확인한다. STT 음성 다운로드 실패나 서버 입력 미준비면 임대를 반환하고 WAITING_FOR_FILE로 보고한다. 분석은 할당된 입력 전사를 서버 API에서 조회한다.
4. STT는 서버 API로 받은 음성을 work에 저장하고 해시를 검사한다. 분석은 받은 전사 artifact의 버전·해시를 검증해 work에 둔다. 로컬 STT 잔여 파일이나 '최신 전사'로 임의 대체하지 않는다.
5. 입력 준비 후 멱등한 실행 시작 요청으로 execution_deadline을 받는다. 응답 후 연산을 시작한다. 입력 준비부터 업로드까지 heartbeat는 30초 갱신/5분 임대 기본안으로 계속 유지한다.
6. 해당 단계를 상한 안에 실행하고 결과를 spool에 완전히 기록한다. 분석 결과에는 입력 artifact 식별자도 포함한다. 실행 상한 전에 결과 준비 보고(요청 ID·바이트 해시·크기)를 서버에 수락시켜 UPLOADING과 upload_deadline을 받는다.
7. 고정한 요청 ID·해시로 서버에 결과 JSON을 전송한다. 최대 크기는 스키마 계약으로 제한한다. 결과 준비 보고 응답이 유실되면 같은 키로 기존 상태·기한을 조회한다.
8. 서버는 임대·승인·결과 해시를 검증하고 파일/DB 영속화 후 ACK한다.
9. 응답이 없으면 수락 상태를 조회하고 같은 ID로 결과만 재전송한다. UPLOADING 결과는 현재 임대·upload_deadline·입력 보관기한 안에서 수락되며 이전 execution_deadline 경과만으로 거부하지 않는다. 이미 수락된 결과는 기한 이후 조회에서도 원문 없는 기존 ACK를 받는다.
10. 해당 단계 ACK 뒤 work/spool을 청소하고 수신 사본 청소 절차를 수행한다. 다음 분석 단계는 서버 전사본을 다시 받을 수 있으므로 로컬 STT 결과 유지에 의존하지 않는다.

폴더 동기화가 없으므로 삭제가 동기화로 되살아날 경로는 없다. 서버의 수신·격리 사본과 데스크톱 work/spool은 서로 다른 복사본으로 추적하고 각각 삭제 확인을 받는다. 작업 중인 work 파일은 이동·삭제하지 않는다. 전달 방식의 근거와 한계는 [프로젝트 7절](01-project.md#승인-음성의-gpu-전달-방식)을 따른다.

분석 입력 조회는 다른 작업 ID·만료 임대·취소된 승인을 거부한다. 네트워크 실패는 조회만 재시도하고, INPUT_EXPIRED/INPUT_MISSING은 STT 자동 재실행으로 바꾸지 않는다. 서버가 입력을 삭제했거나 업무 승인이 취소되면 로컬 캐시로 분석을 계속하지 않는다. 원본 음성만 만료된 경우에는 아직 유효한 서버 전사본으로 분석할 수 있다.

### heartbeat와 별도인 연산 상한

- 프로젝트 7절의 단일 계약을 따른다. 초기 시험안은 준비 10분·STT 60분·분석 30분·업로드 30분·중단 대기 30초이며 D3~D5 측정 후 운영값을 기록한다.
- 준비·연산·전송을 별도로 감시한다. 서버가 준 남은 시간을 보수적으로 단조 시계에 적용하고 heartbeat·재전송·조각 전환으로 기한을 초기화하지 않는다. 연산 상한 전에 서버가 결과 준비 보고를 수락하면 이후에는 upload_deadline을 적용한다. 보고 미수락 상태로 연산 상한을 넘으면 로컬 완료 주장만으로 업로드를 허용하지 않는다.
- 연산 상한에서는 STAGE_TIMEOUT으로 중단을 요청하고 30초 후에도 남으면 자신이 시작한 연산 프로세스/요청을 종료한다. 준비/업로드 상한은 각각 PREPARATION_TIMEOUT/UPLOAD_TIMEOUT으로 보고한다. Ollama 요청 연결을 닫았다는 사실만으로 GPU 연산 종료로 판단하지 않는다.
- 종료와 메모리 정리·readiness를 확인한 뒤에만 제한 재시도나 다음 claim을 허용한다. 종료 확인이 불가능하면 워커를 준비 안 됨으로 두고 수동 복구한다. 다른 사용자의 프로세스를 일괄 종료하지 않는다.
- 연산 정지 시험은 heartbeat만 정상인 가짜 엔진과 단축된 테스트 상한으로 수행한다. 모델 연산을 통제할 수 있는지는 실제 환경에서도 확인한다.

### 임대 상실·취소

- heartbeat 실패로 임대 유효성이 사라지면 새 연산을 시작하지 않고 현재 작업 중단을 시도한다.
- 이미 끝난 연산의 구 임대 결과를 서버가 수락하도록 강요하지 않는다.
- 사용자 취소를 다음 heartbeat에서 받고 연산 중지와 청소를 수행한다.
- 오프라인 중 취소되어 임대가 이미 사라졌어도 삭제 전용 API로 지시를 받고 처리한다. 재연결 시 새 claim보다 청소를 먼저 수행하고 요청 버전별 확인을 반환한다.
- 서버는 업무 승인 취소/통화 전체 삭제 직후 모든 결과를 차단한다. 음성만 만료되면 STT만 차단하고, 산출물 만료는 이를 사용하는 분석을 차단한다. 분산 처리이므로 물리 연산 중단까지 지연될 수 있음을 상태에 표시한다.
- 연산 중단 성공과 모든 사본 삭제 완료를 별도로 보고한다.
- 서버가 끊겨도 로컬 TTL이 지난 민감 spool/work 파일은 청소한다. 제안 TTL은 24시간이다. 실패 결과는 해당 단계 입력이 서버에 유효하게 남아 있을 때만 재생성 가능하며, 원본·전사 만료 후 자동 재수집하지 않는다.

### 테스트 / 완료 조건

- 서버 결과 저장 후 응답을 끊어도 같은 전사가 여러 번 저장되지 않는다.
- 워커 재시작 후 미수락 spool만 전송하고 이전 시도의 완료를 위조하지 않는다.
- 새 임대를 받은 뒤 늦게 온 구 결과가 거절된다.
- 업무 취소 후 결과와 일정 후보가 새로 생성되지 않는다.
- Ollama 실패 후 STT 산출물을 재사용하여 분석만 재시도한다.
- STT ACK 직후 work/spool 삭제·워커 재시작 후에도 서버 전사 조회로 분석이 성공한다.
- 다른 작업·구 임대의 입력 조회와 입력 버전/해시 불일치 결과를 거부한다.
- heartbeat 정상·연산 정지 시 상한에서 종료하고, 종료 미확인 워커는 새 claim을 하지 않는다.
- 입력 준비가 임대 기본 길이보다 길어도 heartbeat로 유지되며 준비 상한에서는 중지한다. 결과 준비 보고 후 연산 상한을 넘어도 전송 상한 내 업로드는 성공한다.
- 실행 시작/결과 준비 보고의 응답 유실·워커 재시작에도 기한이 바뀌지 않는다. 서버에 등록한 결과 해시 변경·구 임대 결과는 거부한다.
- 음성만 만료되면 STT가 중단되지만 유효한 전사 분석은 가능하다. 전사 만료/전체 삭제 후 로컬 사본으로 분석을 재개하지 않는다.

STT 수락과 청소 뒤 워커를 새로 실행해 서버가 고정한 전사로 분석했다. Chromium 390px·1090px에서 T01과 D4-TASK의 로그인, 원음 재생, 요약에서 고정 근거 열기, 인용 구간 재생, 일정 또는 할 일 후보 화면을 확인했다. 인용 WAV 길이는 저장된 시작·끝 구간과 일치했다.

실제 API와 모의 연산으로 업로드 요청과 결과 ACK 유실을 각각 주입했다. 다시 실행하면 원래 결과를 조회·재전송하고 전사와 분석 작업을 각각 한 번만 저장했다. 분석 실패 뒤 같은 전사로 분석만 재시도했다. 재전송 전 고정 전사가 유실된 분석은 수동 확인으로 전환했다. 취소·만료 임대의 늦은 업로드는 거부했고 관리 사본을 제거했다. heartbeat가 갱신되는 동안 멈춘 시험 프로세스 그룹을 실행 상한에서 종료했다. 워커 모의 검사 54개와 Ubuntu의 하네스 포함 P3 103개가 통과했다. [검사 안내](harness.md) · [워커 모의 검사](../ai-worker/tests/test_worker.py)

별도 장비 시험에서 실제 Whisper와 Ollama가 GPU 메모리를 사용하기 시작한 뒤 중단했다. 워커가 각각 소유한 프로세스 그룹을 종료했고 결과 파일이나 종료 미확인 표식이 남지 않았다. 전체 GPU 메모리는 관측 시 Whisper 1,800MiB, Ollama 4,844MiB에서 중단 후 각 시험 직전의 81MiB로 돌아갔다.

배포 환경에서는 홈서버 웹 기동 뒤 VPN·HTTPS로 재현하고, 최대 입력 500MiB·2시간의 전송·연산, 늦은 링크의 재개 및 실제 음성 형식을 확인한다. [홈서버 상태와 다음 작업](progress-checklist.md#실제-장비외부-연결이-필요한-작업)

| 매일 또는 오류 알림 시 | 마지막 heartbeat, 현재 작업, GPU/VRAM, stage 처리시간 | 준비 안 됨/과도한 대기 원인 확인 |
| 매일 | ACK 전 spool·삭제 미완료·디스크 사용량 | TTL·서버 수락 상태 대조 |
| 매주 | 모델/라이브러리 버전·로그 크기·Windows 재시작 이력 | 필요 업데이트 계획 |
| 업데이트 전 | 새 claim 중지, 활성 작업 종료, 기존 정상 버전 기록 | 가짜 음성으로 변경 검증 |
| 업데이트 후 | 프로젝트 9절 전체 평가 세트와 합격 기준, 처리시간·근거·품질 비교 | 실패하면 이전 버전으로 복귀 |

로그 허용: job/attempt ID, 단계, 시작/종료, 처리시간, 오류 코드, 모델 버전, GPU 지표. 금지: 전사 텍스트·녹음명·전화번호·토큰·HTTP Authorization 헤더. 사용자 세션의 진단 도구가 프롬프트를 수집하는지도 점검한다.

## 10. 백업 없는 복구와 보관 경계

현재 별도 백업은 보류한다. 데스크톱은 재생성 가능한 워커로 운영하되, 서버 ACK 전 결과를 잃으면 해당 단계 재처리가 필요하다.

1. 기존 워커 토큰이 노출됐을 가능성이 있으면 서버에서 폐기한다.
2. CallOps 저장소의 승인된 버전을 가져온다.
3. 기록한 모델·런타임 버전을 설치한다.
4. 새 워커 토큰과 경로를 주입한다.
5. 테스트 작업 후 서버에서 남은 업무 작업을 다시 받는다.
6. 기존 승인 이력이나 Calendar 등록을 데스크톱 복구 과정에서 생성하지 않는다.

다음은 반드시 구분한다.

- 모델 파일: 다시 받을 수 있음.
- 환경 설정: 비밀값 제외하고 Git에서 재현.
- 워커 토큰: 재발급 가능.
- 원본: 갤럭시 또는 서버에 남아 있어야 재처리 가능.
- 분석 입력 전사: 서버의 고정 artifact가 남아 있고 승인·보관기한이 유효해야 분석만 재시도 가능. 음성만으로 승인·전사 이력을 복구했다고 간주하지 않음.
- 서버에 없는 전사 spool: 삭제·장애 시 유실 가능.
