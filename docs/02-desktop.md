# 2. 데스크톱 — GPU 환경 준비·워커 실행·운영 절차

작성일: 2026-09-19 · 상태: 검토용 초안 · 데스크톱 사양과 설치 상태 미확인

연결 문서: [이 프로젝트](01-project.md) · [서버](03-server.md)

이 문서는 Windows GPU 데스크톱에서 해야 할 작업이다. 코드의 원본은 CallOps 저장소에 두고 실제 실행 환경·모델·토큰·음성은 장비의 별도 저장소에 둔다. 승인 전에는 설치·드라이버 변경·방화벽 변경을 실행하지 않는다.

## 1. 역할과 완료 목표

홈서버가 GPU 없이도 업무 통화를 전사하고 검토용 후보를 만들 수 있도록 연산을 맡는다. 데스크톱은 업무 여부나 외부 등록 여부를 결정하지 않는다.

```text
서버 승인 파일 동기화 → 데스크톱 inbox
서버 API에서 작업 임대 → 파일 해시 확인 → Whisper → 전사 결과 반환
서버에서 수락된 전사 → Ollama → 구조화 결과 반환
서버 ACK → 로컬 임시 파일 청소 → 다음 작업
```

| 구성요소 | 역할 | 허용 데이터 |
|---|---|---|
| 동기화 도구 | 승인된 서버 폴더 수신 | 업무 승인 음성만 |
| GPU 워커 | claim·진행·결과 업로드·청소 | 할당 작업과 처리 결과 |
| Whisper/faster-whisper | 구간별 전사 | 승인된 음성 |
| Ollama 로컬 모델 | 요약·일정/할 일/계약 언급 초안 | 승인 작업의 전사 |
| Windows 작업 스케줄러 또는 선택 환경 서비스 관리자 | 재부팅 후 시작·중복 프로세스 방지 | 실행 구성 |

완료 기준은 가짜 업무 녹음을 처리하고, 전원 OFF·VPN 단절·재부팅 뒤에도 서버 승인·중복 방지 규칙이 유지되는 것이다.

## 2. D0 — 사양과 기존 환경 확인

### 해야 할 일

- [ ] GPU 제조사·모델·VRAM·드라이버 버전을 확인한다.
- [ ] Windows 버전, RAM, 디스크 여유 공간을 확인한다.
- [ ] Python, WSL2, Docker Desktop, Ollama가 이미 설치되어 있는지 확인한다.
- [ ] 데스크톱과 서버가 같은 VPN에서 통신 가능한지 확인한다.
- [ ] Windows 재시작·로그아웃·잠금 시 실행 환경이 어떻게 동작하는지 확인한다.
- [ ] 절전·최대 절전·Windows 업데이트 재부팅 정책을 기록한다.
- [ ] BitLocker 여부는 현황만 기록한다. 이번 단계의 필수 구매·재설정 조건으로 만들지 않는다.
- [ ] 모델 다운로드 저장소와 작업용 디렉터리가 OneDrive 등 외부 동기화 경로인지 확인한다.

### 읽기 전용 확인 명령

아래 명령은 사용자가 데스크톱에서 실행할 때의 점검용이다. 없는 명령의 오류는 미설치 증거이며 바로 설치하라는 의미가 아니다.

```powershell
nvidia-smi
Get-CimInstance Win32_OperatingSystem | Select-Object Caption, Version, BuildNumber
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
Get-Volume | Select-Object DriveLetter, FileSystem, Size, SizeRemaining
wsl --status
wsl --list --verbose
docker version
python --version
ollama --version
powercfg /getactivescheme
```

VRAM은 NVIDIA 장비라면 `nvidia-smi` 출력을 우선한다. `Win32_VideoController.AdapterRAM`만으로 최신 대용량 GPU 메모리를 확정하지 않는다. NVIDIA가 아니라면 모델·런타임 지원 여부부터 다시 확인하고 CUDA 설치를 진행하지 않는다.

### 하면 안 되는 일

- 기존 개발용 Python·드라이버·Docker 환경을 확인 없이 덮어쓰기.
- GPU 메모리가 확인되지 않은 상태에서 큰 모델이나 동시 실행 수를 확정.
- 접근 토큰·환경변수 전체·개인 파일 목록을 진단 출력에 포함.
- 서버 또는 GPU 사양 확인을 위해 실제 고객 녹음을 투입.

### 완료 조건

GPU·VRAM·드라이버·실행 환경·VPN·여유 공간 기록이 있어 D1의 한 가지 실행 방식을 선택할 수 있다. 서버 P1~P3 개발은 이 확인과 독립적으로 진행 가능하다.

## 3. D1 — 하나의 실행 방식 선택

| 후보 | 준비할 것 | 확인할 것 |
|---|---|---|
| Windows 네이티브 | 전용 Python 가상환경, GPU 런타임, 로컬 Ollama, 작업 스케줄러 | 계정별 모델 경로, CUDA 관련 라이브러리, 로그아웃 후 동작 |
| WSL2 Linux | GPU가 보이는 WSL2, Linux 환경·모델 경로, 자동 시작 | Windows 재부팅 후 WSL 시작, VPN 경로, 파일 권한 |
| Docker GPU 환경 | Docker Desktop/WSL2 GPU 지원, 고정 이미지, 볼륨 | 컨테이너 안 GPU, 네트워크 localhost 의미, Desktop 시작 의존 |

세 방식을 동시에 설치하지 않는다. 이미 정상 동작하는 환경을 우선 사용하고, D0 결과에 따라 Python/CTranslate2/CUDA/cuDNN 조합과 모델 버전을 잠근다. 드라이버가 설치돼 있다는 사실만으로 전사 런타임 GPU 사용이 검증된 것은 아니다.

faster-whisper는 CTranslate2 기반이며 지원 런타임 조합이 버전에 따라 달라진다. 선택한 버전의 공식 요구사항을 설치 직전에 확인한다. 시스템 FFmpeg가 항상 필수인 것은 아니므로 메타데이터 검사·변환 도구의 실제 필요를 확인한 뒤 추가한다. [faster-whisper 공식 README](https://github.com/SYSTRAN/faster-whisper)

### 해야 할 일

- [ ] 선택 환경과 선택 이유를 이 문서에 기록한다.
- [ ] 설치·모델 다운로드 위치와 필요한 디스크 용량을 산정한다.
- [ ] 가짜 음성 한 건으로 GPU 연산 여부를 확인한다.
- [ ] 재현 가능한 패키지 잠금 파일 또는 이미지 버전을 기록한다.
- [ ] 이전 정상 버전으로 되돌리는 방법을 정한다.

### 하면 안 되는 일 / 완료 조건

`latest`만으로 운영 버전을 기록하거나 실행 시 자동 업데이트하지 않는다. 가짜 음성의 GPU 실행과 재시작 후 동일 버전 재실행이 확인되면 D1 완료다. 전체 드라이버 다운그레이드는 다른 작업에 영향을 주므로 별도 판단 없이 수행하지 않는다.

## 4. D2 — 파일·계정·VPN 경계 준비

### 저장 위치 제안

아래는 예시일 뿐 실제 드라이브는 D0 결과로 결정한다. 저장소 checkout과 분리한다.

```text
전용 CallOps 런타임 디렉터리/
  inbox/       # 업무 승인 음성 동기화 영역
  work/        # 임대 작업의 처리용 독립 사본
  spool/       # 서버 수락 전 전사·추출 JSON
  models/      # 모델 캐시, 사용자 개인정보 없음
  logs/        # 내용 없는 운영 로그
  config/      # 권한을 제한한 실설정과 워커 토큰
```

### 해야 할 일

- [ ] 전용 사용자 또는 제한된 서비스 계정과 폴더 ACL을 정한다.
- [ ] 서버 `gpu-outbox`만 inbox와 공유한다. `sync-inbox`·`quarantine`은 장치 공유 목록에 없어야 한다.
- [ ] `inbox`의 완료 파일을 `work`로 복사하고 해시 재검증 후 처리한다.
- [ ] 워커 토큰은 작업 조회·할당 작업 결과·heartbeat만 허용한다.
- [ ] 워커가 서버 API로 나가는 pull 통신을 구성한다.
- [ ] Ollama는 워커와 같은 환경의 localhost에서만 접근하게 한다.
- [ ] Whisper는 워커 내부 라이브러리 호출을 우선하여 별도 공개 API를 만들지 않는다.
- [ ] 동기화 관리 화면을 외부에 공개하지 않고 장치 ID·VPN 경로를 제한한다.

### 주의할 연결 방식

Windows의 localhost와 WSL/컨테이너 내부 localhost는 다를 수 있다. 한쪽 서비스가 다른 환경에서 보이지 않는다고 `0.0.0.0`으로 무제한 공개하지 않는다. 같은 환경에 묶거나 필요한 브리지 경로·방화벽만 명시적으로 허용한다. 불가피하게 모델 API를 다른 호스트에 노출하는 변경은 인증 프록시·VPN 제한 설계를 먼저 검토한다.

### 하면 안 되는 일

- 서버 DB 비밀번호·n8n 관리자 계정·Google OAuth 토큰을 데스크톱에 복사.
- OneDrive·공개 공유 폴더·Git 디렉터리에 음성/전사/spool 저장.
- 실제 파일명·전화번호를 작업 이름과 로그에 사용.
- 파일이 동기화됐다는 이유만으로 작업 승인 없이 전사.

### 테스트 / 완료 조건

- 잘못된 토큰과 다른 작업 ID는 거절된다.
- 서버 API 접근은 성공하고 다른 장비에서 모델 API 접근은 실패한다.
- 사적·미분류 가짜 파일은 데스크톱에 존재하지 않는다.
- 동기화 중단 파일·해시 불일치 파일이 처리되지 않는다.

## 5. D3 — Whisper 전사 단독 검증

입력은 개인정보 없는 승인 테스트 음성, 출력은 segment별 시간과 텍스트다. 서버 F03 명세의 스키마를 사용한다.

### 해야 할 일

- [ ] 작은 한국어 테스트부터 GPU 지원 모델을 비교하고 한 모델로 고정한다.
- [ ] 모델 ID·버전·compute type·언어 설정·VAD 설정을 기록한다.
- [ ] `start <= end`, 음성 범위 내 timestamp, 빈/무음 전사를 검증한다.
- [ ] 가짜 전화번호·금액·날짜·고유명사·겹치는 발화의 오류를 확인한다.
- [ ] 긴 녹음은 구간 분할 시 전체 녹음 기준 오프셋을 유지한다.
- [ ] GPU 모델 사용 여부·VRAM 최대치·전사 시간·오디오 길이를 측정한다.
- [ ] OOM·디코딩 실패·사용자 취소 시 메모리와 파일이 정리되는지 확인한다.

### 출력 계약

- recording_id, job_id, attempt_id, schema_version, model_version
- duration_seconds, language, processing_seconds
- segments: segment_id, start, end, text
- warnings: 낮은 품질 등 기계 판독 가능한 코드, 사용자에게 보여줄 제한 사항

Whisper의 텍스트와 시간 구간은 추정치다. 신뢰 점수를 사람이 읽는 정확도 퍼센트로 임의 변환하지 않는다. 텍스트만으로 발화자의 신원을 확정하지 않는다.

### 하면 안 되는 일 / 완료 조건

처리 실패 시 클라우드 STT나 임의의 CPU 엔진으로 자동 대체하지 않는다. 테스트 음성에서 전사·타임스탬프·GPU 측정이 정상이며 무음과 오류 케이스가 실패/경고로 구분되면 D3 완료다. 이 단계에서 Ollama나 Calendar는 호출하지 않는다.

## 6. D4 — Ollama 추출 단독 검증

입력은 수락된 가짜 전사본과 근거 구간이다. 출력은 요약·일정·할 일·계약 언급·불확실 항목의 JSON이다.

### 해야 할 일

- [ ] 한국어와 구조화 출력이 가능한 로컬 모델을 실제 VRAM에 맞춰 선택한다.
- [ ] 모델 이름·digest/버전·양자화·context 크기·프롬프트 버전을 기록한다.
- [ ] 로컬 전용 운영 설정을 적용하고 클라우드 모델 호출이 없는지 확인한다.
- [ ] 서버 출력 스키마와 같은 규칙으로 JSON을 검증한다.
- [ ] 필수 정보가 없으면 null·확인 필요로 남긴다.
- [ ] 각 후보에 실제 전사의 segment ID와 시간 구간을 연결한다.
- [ ] “확정했다”와 “제안했다”, “취소했다”, “만약”을 구분하는 대본을 시험한다.
- [ ] 컨텍스트를 넘는 입력은 분할·근거 병합하고 전체 입력 처리 범위를 기록한다.
- [ ] 모델 JSON 밖의 설명·허구 필드·승인 지시를 수락하지 않는다.

Ollama의 네트워크 바인딩과 로컬 전용 설정은 선택 버전에서 확인한다. Windows 기본 실행·로그 위치도 운영 전 확인하여 민감한 프롬프트가 로그에 남지 않게 한다. [Ollama FAQ](https://docs.ollama.com/faq), [Windows 안내](https://docs.ollama.com/windows)

### 하면 안 되는 일

- 전사 내용을 시스템 명령으로 실행하거나 AI에 Calendar·메일 도구 제공.
- 누락된 종료시간을 자동으로 1시간 뒤로 채워 승인 완료 처리.
- 계약 언급을 실제 체결/채무 인정으로 표시.
- 긴 입력의 뒤쪽을 버린 채 전체 요약 완료라고 표시.
- 모델이 만든 근거 문장을 원문 확인 없이 저장.

### 테스트 / 완료 조건

프로젝트 T01~T05에서 후보 개수·날짜·불확실 이유·근거를 확인한다. “등록하라” 같은 악성 지시가 들어 있어도 외부 호출 0회여야 한다. 품질이 부족하면 모델/프롬프트를 조정하되 버전을 기록하고 같은 데이터로 회귀 검사한다.

## 7. D5 — 홈서버와 실제 워커 연결

초기 동시 실행 수는 1개다. Whisper와 Ollama를 순차 실행하고 필요하면 모델을 해제하여 VRAM 경합을 줄인다. STT와 분석은 서로 다른 단계로 저장하므로 분석 실패가 STT 재처리로 이어지지 않는다.

### 작업 실행 순서

1. 모델·폴더·서버 연결을 검사하고 readiness를 보고한다.
2. 준비된 단계만 claim하고 서버가 준 job_id·lease_token·sha256을 보관한다.
3. 업무 승인과 임대가 유효한지 확인한다. 파일 미도착이면 WAITING_FOR_FILE로 보고한다.
4. 파일 완료·해시 검사 뒤 work 사본을 만든다.
5. heartbeat를 연산과 별도로 유지한다. 기본안은 30초 갱신/5분 임대다.
6. 해당 STT 또는 분석 단계를 실행하고 결과를 제한된 spool에 쓴다.
7. 같은 요청 ID로 서버에 결과 JSON을 전송한다. 최대 크기는 스키마 계약으로 제한한다.
8. 서버는 임대·승인·결과 해시를 검증하고 파일/DB 영속화 후 ACK한다.
9. 응답이 없으면 수락 상태를 조회하고 같은 ID로 결과만 재전송한다.
10. ACK 뒤 work/spool을 청소하고 수신 사본 청소 절차를 수행한다.

inbox 삭제가 동기화에 의해 되돌아오지 않도록 서버의 전달 manifest와 조정한다. 서버 outbox와 데스크톱 inbox/work/spool은 서로 다른 복사본으로 추적한다. 공유 폴더의 파일을 작업 중 이동·삭제하지 않는다.

### 임대 상실·취소

- heartbeat 실패로 임대 유효성이 사라지면 새 연산을 시작하지 않고 현재 작업 중단을 시도한다.
- 이미 끝난 연산의 구 임대 결과를 서버가 수락하도록 강요하지 않는다.
- 사용자 취소를 다음 heartbeat에서 받고 연산 중지와 청소를 수행한다.
- 서버는 취소 직후 모든 결과를 차단한다. 분산 처리이므로 물리 연산 중단까지 지연될 수 있음을 상태에 표시한다.
- 연산 중단 성공과 모든 사본 삭제 완료를 별도로 보고한다.
- 서버가 끊겨도 로컬 TTL이 지난 민감 spool/work 파일은 청소한다. 제안 TTL은 24시간이며 실패 결과는 나중에 원본에서 재생성할 수 있음을 기록한다.

### 테스트 / 완료 조건

- 서버 결과 저장 후 응답을 끊어도 같은 전사가 여러 번 저장되지 않는다.
- 워커 재시작 후 미수락 spool만 전송하고 이전 시도의 완료를 위조하지 않는다.
- 새 임대를 받은 뒤 늦게 온 구 결과가 거절된다.
- 업무 취소 후 결과와 일정 후보가 새로 생성되지 않는다.
- Ollama 실패 후 STT 산출물을 재사용하여 분석만 재시도한다.

## 8. D6 — 상시 실행·재시작·청소 검증

### 해야 할 일

- [ ] 선택 환경에 맞는 자동 시작 방식 하나를 구성한다.
- [ ] VPN·모델·네트워크가 늦게 준비되면 backoff로 대기하도록 한다.
- [ ] 재부팅 후 로그인 필요 여부를 실제로 시험하고 무인 가동 조건을 기록한다.
- [ ] 중복 워커 실행을 차단한다.
- [ ] 컴퓨터 잠금 상태에서 정상 처리되는지 확인한다.
- [ ] 절전 정책은 사용자 승인 범위에서 조정한다. 화면 꺼짐과 시스템 절전을 구분한다.
- [ ] Windows 업데이트·재부팅 시간을 정하고 작업 완료 대기/취소를 제공한다.
- [ ] 시작 시 남은 `.part`, work, spool을 서버 상태·로컬 TTL과 대조한다.
- [ ] 로그 회전과 디스크 사용 상한을 적용한다.

### 장애별 조치

| 상황 | 워커 조치 | 서버 표시 |
|---|---|---|
| 데스크톱 꺼짐 | 없음, 재부팅 후 시작 | GPU 워커 대기 |
| VPN 끊김 | 새 claim 중지, 임대 갱신·취소 규칙 적용 | 대기/임대 만료 |
| GPU OOM | 작업 종료·모델 메모리 해제·오류 코드 | 해당 단계 제한 재시도 |
| 잘못된 파일 | 연산 금지, 해시/형식 오류 보고 | 수신/동기화 재확인 |
| 결과 업로드 실패 | 제한 spool 유지, 같은 ID로 재시도 | 결과 수신 대기 |
| 임시 디스크 부족 | 새 claim 중지, 안전한 만료 데이터만 청소 | 워커 준비 안 됨 |
| 취소 후 오프라인 | 재연결 시 청소부터 수행 | 삭제 미완료 |

### 완료 조건

실제 전원 OFF/ON, Windows 재시작, VPN OFF/ON, Whisper/Ollama 중단 시험을 거친다. 서버가 오프라인을 영구 실패로 바꾸지 않고, 사적/취소 작업이 재부팅 후 처리되지 않아야 한다.

| 주기 | 확인할 것 | 조치 |
|---|---|---|
| 매일 또는 오류 알림 시 | 마지막 heartbeat, 현재 작업, GPU/VRAM, stage 처리시간 | 준비 안 됨/과도한 대기 원인 확인 |
| 매일 | ACK 전 spool·삭제 미완료·디스크 사용량 | TTL·서버 수락 상태 대조 |
| 매주 | 모델/라이브러리 버전·로그 크기·Windows 재시작 이력 | 필요 업데이트 계획 |
| 업데이트 전 | 새 claim 중지, 활성 작업 종료, 기존 정상 버전 기록 | 가짜 음성으로 변경 검증 |

로그 허용: job/attempt ID, 단계, 시작/종료, 처리시간, 오류 코드, 모델 버전, GPU 지표. 금지: 전사 텍스트·녹음명·전화번호·토큰·HTTP Authorization 헤더. 사용자 세션의 진단 도구가 프롬프트를 수집하는지도 점검한다.

## 10. 백업 없는 복구와 보관 경계

현재 별도 백업은 보류한다. 데스크톱은 재생성 가능한 워커로 운영하되, 서버 ACK 전 결과를 잃으면 해당 단계 재처리가 필요하다.

1. 기존 워커 토큰이 노출됐을 가능성이 있으면 서버에서 폐기한다.
2. CallOps 저장소의 승인된 버전을 가져온다.
3. 기록한 모델·런타임 버전을 설치한다.
4. 새 워커 토큰과 경로를 주입한다.
5. 테스트 작업 후 서버에서 남은 업무 작업을 다시 받는다.
6. 기존 승인 이력이나 Calendar 등록을 데스크톱 복구 과정에서 생성하지 않는다.

다음은 반드시 구분한다.

- 모델 파일: 다시 받을 수 있음.
- 환경 설정: 비밀값 제외하고 Git에서 재현.
- 워커 토큰: 재발급 가능.
- 원본: 갤럭시 또는 서버에 남아 있어야 재처리 가능.
- 서버에 없는 전사 spool: 삭제·장애 시 유실 가능.
